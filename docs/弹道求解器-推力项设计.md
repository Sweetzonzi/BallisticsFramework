# 弹道求解器 — 推力项设计

**状态**：已实现。`api/trajectory/ThrustProfile.java`，以及 `RealisticTrajectory` 的正解、反解、提前量三个推力重载；测试见 §6。

**定位**：本文拥有「发动机推力」在 `RealisticTrajectory` 中的契约。外弹道的整体结构、既有数据结构与退化路径归 `docs/外弹道设计文档.md`；本文定义推力这一项能力本身。Machine-Max 侧的消费方式（预测游标、区块预载）见 Machine-Max 仓库的 `docs/plan/计划中/武器系统-投射物弹道预测与区块预载设计.md`。

---

## 一、范围

**目标**：让 `api/trajectory/RealisticTrajectory.java#forwardSolve`、`#solveFiringAngle` 与 `#solveWithLead` 支持“沿速度方向、恒定推力、有限燃烧窗口”的发动机。

**动机**：带助推的弹种在燃烧段速度显著增长，纯重力 + 阻力的正解会把射程低估数倍。以 Machine-Max 的 `9m133_kornet` 为例：出膛 50 m/s、推力 2600 N / 质量 26 kg、燃烧 2.5 s，2.5 s 内加速到约 300 m/s；按初速直线预测只有 250 m，实际射程约 7 km。

**边界**：`MinecraftTrajectory` 不引入推力——原版物理模型没有发动机概念，它的参数常量（`dragH` / `dragV` / `gravity`）也不足以表达推力。

设计取舍：

| 决策 | 结论 | 理由 |
|---|---|---|
| 推力方向 | **恒沿速度方向** | 与 Machine-Max 积分器的施加方式一致（`thrustAcc × v / |v|`）。不做 `Alignment` / 方向字段：固定方向电机在本模型中没有调用方，为它保留一条解析分支会得到死代码；将来需要时按“加字段 + 加解析分支”的方式扩展 |
| 时间表达 | **求解器时间窗** `[startSeconds, endSeconds)` | 中途续算时调用方只需传 `(force, 0, burnEnd − burnElapsed)`（结果 ≤ 0 即 `NONE`）；求解器不需要“已燃时长”这个概念 |
| 参数承载 | **新重载**，不塞进 `BallisticConfig` | `BallisticConfig` 是 record，加字段会破坏所有构造点（本模块、Machine-Max、下游模组）；新重载加默认值对调用方零改动 |
| 三个入口一次加完 | `#forwardSolve` / `#solveFiringAngle` / `#solveWithLead` 同时加重载，旧签名一律委托 `NONE` | 提前量的唯一入口是 `#solveWithLead`；只给前两个加推力，助推弹的提前量仍会按初速低估飞行时间数倍，等于半个功能。三个旧签名都委托，`NONE` 路径逐位不变（T1），调用方一次加参即可 |
| 质量 | 使用 `BallisticConfig#mass`，**不做质量流失** | 恒定推力 + 恒定质量才使二维 ODE 与解析分支成立；质量流失见第七节 |
| 单位 | `force` 为牛顿，加速度 `a_T = force / config.mass` | 与仓库既有 SI 约定一致 |

## 三、物理与积分

受力（SI）：

```
a = −g·ŷ + a_T·v̂ − ½·ρ(h)·Cd·A·|v|·v / m
```

**平面性**：两项加速度都落在 `span(v, ŷ)` 内，因此轨迹恒在初始速度所在的竖直平面内。实现把状态降到该平面的两个速度分量（沿水平方向 `u`、竖直 `w`）加两个位置分量：

```
dv/dt = a_T·v̂ − ½·ρ·Cd·A·|v|·v / m − g·ŷ
dx/dt = u,   dy/dt = w
```

这一步不是近似：只要推力沿速度，横向分量恒为零。二维推进（`#solveThrustReducedSI`）因此比三维全积分少一个恒为零的分量与一次向量加法。

**为什么不用极坐标 `(s, γ)`**：极坐标的半隐式欧拉与笛卡尔半隐式欧拉是两种离散化，10 s、300 m/s 量级的弹道累计差约 0.16 m；调用方的积分器（Machine-Max 的 `ProjectileManager#updateProjectiles`）是三维半隐式欧拉，预测必须与之同式，否则预测与实际飞行会系统性地分家。平面笛卡尔分量逐步骤与三维全积分同式，代价只是一次 `sqrt`（阻力本来就需要 `|v|`）。副产物是 T5 能把容差压到 1e-3 m。

**步进顺序**与既有全积分一致：先算加速度并更新速度，再用新速度更新位置（半隐式欧拉）。

**时间窗判定**：第 `i` 步覆盖 `[(i−1)Δt, iΔt)`，当且仅当 `(i−1)Δt ∈ [startSeconds, endSeconds)` 时该步施加推力（`#thrustAppliedAtStep`）。判定只看步序号与 `Δt`，不依赖“是否已经施加过推力”，所以“最后一个施加推力的步”是确定的——T5 的尾部外推以它为准。窗口与 `Δt` 不对齐时，实际燃烧时长与请求值最多相差一个步长（见第七节）。

**退化运算也按这条判定走**：窗口内外的 `v` / `p` 拼接必须用同一条递推，不能对“窗口内”另用连续解（理由见第四节末的离散语义）。

## 四、退化路径

| 受力组合 | 解法 | 复杂度 |
|---|---|---|
| 无推力、无阻力、`g = 0` | 匀速直线（`#solveLinearMotionSI`） | O(1) |
| 无推力、无阻力、`g ≠ 0` | 解析抛物线（`#solveParabolicMotionSI`） | O(1) |
| 无推力、`g = 0`、有阻力 | 直线减速（`#solveStraightDecelerationSI`） | O(N)，一维 |
| 无推力、有阻力、`g ≠ 0` | 三维全积分（`#solveFullIntegrationSI`） | O(N)，六状态 |
| 推力、`g = 0`、无阻力 | 分段直线加速（`#solveThrustNoDragSI`）：窗口内 `v += a_T·Δt`，窗口外匀速 | O(N)，每步只有加乘（无三角函数、无密度查询；与匀速直线同一条递推，不做闭式跳跃） |
| 推力、`g = 0`、有阻力 | 一维 `s` ODE（`#solveThrustStraightDragSI`，方向恒定） | O(N)，一状态 |
| 推力、`g ≠ 0` | 平面二维 ODE（`#solveThrustReducedSI`，第三节） | O(N)，四状态（含位置） |

复杂度列指搜索/迭代层面的开销，采样点始终按 `maxSteps` 逐点生成。

两条硬约束：

1. **推力激活时不得进入前四条捷径**——它们不含推力项，会把助推结果的射程压低数倍。分派顺序按“先看 `thrust.isActive()`，再看 `isNoDrag` / `gravity == 0`”。前四条捷径本身的定义与判定规则归 `docs/外弹道设计文档.md` §4.4，本文只加门禁。
2. **`NONE` 与非重载版本走完全相同的代码路径**，结果逐位一致。这既是零回归的验收口径，也保证既有调用方（弹道表、瞄准反解）行为不动；三个旧签名都委托 `NONE`，因此这条对正解、反解、提前量同时成立。

**离散语义（无阻力的加速路径用离散递推，不用连续解）**：半隐式欧拉在恒定加速度下的采样点是

```
v_n = v_0 + n·a_T·Δt
p_n = p_0 + v_0·nΔt + a_T·Δt²·n(n+1)/2
```

与连续解 `p = p_0 + v_0t + ½a_Tt²` 相差 `½a_T·Δt·t`——按 Kornet 参数（`a_T = 100 m/s²`）、`Δt = 0.01 s`、`t = 2.5 s` 约 1.25 m。取离散式，是因为调用方的积分器也是半隐式欧拉、同 `Δt`（§9），只有离散式才让预测与实际飞行一致（第七节）；同一配置下 O(1) 路径与一维/二维推进也不会因为“一条用闭式、一条用递推”而在米级上分家。既有抛物线路径就是同一取舍（`src/test/java/io/github/sweetzonzi/ballistics_framework/api/trajectory/RealisticTrajectoryInvariantTest.java#parabolicPathMatchesDiscreteSemiImplicitEuler` 以离散闭式解为基准）。

## 五、反解与提前量

### 5.1 反解结构

双分支二分（`#binarySearchAngleSI`）的骨架不变：给定 θ 做一次正解，判断这次是“越过”还是“不够”，缩掉一半区间。内层求值使用推力版 `forwardSolve`。

**判据取“目标水平距离处的弹道高度”**（`#heightAtHorizontalDistanceSI`）：沿方位角找到第一个越过目标水平投影的采样点，线性插值出该处高度，与目标高度比较——高了就收 `thetaHigh`，低了就抬 `thetaLow`；高度差 < 0.1 m 即收敛。不能用“任一采样点的水平投影超过目标”：弹道水平坐标单调递增，任何足够长的模拟都满足它，区间会被压到最小仰角。两个半区（`[0°, 45°]` 与 `[45°, 90°]`）各自单峰，因此各做一次二分，得到低抛与高抛解。

**精度由 `angleEpsilon` 决定**：0.01 rad（≈0.57°）在 1 km 射程上对应十米级落点偏差，是默认值；需要米级精度时传 1e-4（T8 即如此）。高度差判据让较小的 `angleEpsilon` 提前退出，不会白跑满 50 次。

两点必须处理：

1. **解析捷径要加推力门禁**。`#solveFiringAngle` 的退化分派（匀速直线、纯抛物线反解公式、直线减速）在没有推力时成立；推力激活时必须改走完整二分。实现即如此：三条捷径包在 `if (!thrust.isActive())` 内。
2. **单峰性要验证，不能假设**。无推力时射程随仰角在 `[0°, 45°]` 上单峰、在 `[45°, 90°]` 上递减，这是二分的收敛前提。恒定推力会改变最优仰角，理论上仍单峰，但这是经验结论。T7 用 Kornet 参数以 1° 步长扫描验证了 `(0°, 90°)` 内恰有一个局部极大；若换参数组后破坏单峰，退化为“粗扫 + 局部二分”（粗扫 1°，峰值两侧各 2° 收紧后二分），并以一条新的扫描测试守住。

### 5.2 动目标提前量

迭代结构不变：`#solveWithLead` 以飞行时长为不动点（反解 → 飞行时间 → 目标预测点 → 再解），推力只改变“给定仰角的飞行时长”本身，而这已经由推力版 `#solveFiringAngle` 提供。改动是加一个 `ThrustProfile` 参数并透传给内部的 `#solveFiringAngle` 调用，迭代、收敛判据、返回最优猜测的行为都不动。**结论：不复杂，结构上是“加参数 + 换首轮粗估”。**

四处会变，实现时必须处理：

1. **首轮粗估要用燃烧段平均速度**。现在是 `distance / speed`（`#solveWithLead` 的 `roughTime`），对 Kornet 这类出膛 50 m/s、燃尽 300 m/s 的弹会低估 3~4 倍，首轮预测点偏出数百米，4~7 次迭代不足以收敛。实现改为 `distance / (speed + a_T·(endSeconds − startSeconds) / 2)`（忽略阻力）。
2. **收敛对飞行时长更敏感**。助推弹飞行 15~20 s，目标预测点 = 当前位置 + `v·t`；`t` 的 1% 误差就是目标位移的 1%。`convergeEpsilon` 取 0.1 m 时要相应放大 `maxIterations`。参数由调用方给，语义不变（T9 用默认值验证闭环）。
3. **最小射程会返回“最近接近”解**。距离小于助推弹最小射程时任何仰角都会超射，`#binarySearchAngleSI` 此时返回 `bestDist` 对应的最近接近解，而 `FiringSolution` 不携带“未命中”标记。提前量沿用它，就会把系统性偏差当成命中解。这是既有语义，本文不改；消费方需按射程表过滤（“给 `FiringSolution` 加命中标记”见第八节）。
4. **低抛解优先不变**。`solutions.get(0)` 是低抛解，提前量只跟它；高抛解在长飞行时间下对提前量更不稳定，不引入新分支。

成本：单次提前量迭代 = 一次反解（每分支至多 50 次求值），再乘 `maxIterations`；推力激活时每次求值是二维推进而非三维积分。弹道表一类的高频调用方按（弹种、初速、距离档）缓存结果。

## 七、误差与边界

- **质量流失**：本模型是恒定加速度。真实固体火箭的加速度随质量下降而上升；若将来需要，加 `massFlow` 并用 `a_T(t) = F / (m − ṁ·t)`，二维 ODE 结构不变，解析分支仍只覆盖 `NONE`。
- **密度随高度变化**：带阻力时没有闭式解，与既有模型一致（每步用当前位置查 `DensityFunction`）。
- **窗口超出模拟步数**：只模拟到 `maxSteps`，窗口剩余部分被截断；步数由调用方按 `(endSeconds − startSeconds) / timeStep` 给足。
- **窗口边界最多差一个 `Δt`**：第三节的判定让实际燃烧段与请求值最多相差一个步长；要求精确的调用方应让 `startSeconds` / `endSeconds` 落在 `Δt` 的整数倍上。
- **`timeStep` 与调用方积分器不一致**：截断误差会与“穿透后速度损失”同量级。Machine-Max 的积分器用 0.01 s，预测必须同值；`BallisticConfig#simple` 的默认 0.05 s 只适合粗算。
- **反解不报告未命中**：见 §5.2 第 3 条——最近接近解会被提前量当成命中解，消费方需按射程表过滤。

---

## 八、明确不做

- 质量流失、推力曲线（推力随时间变化）、多段点火、末端机动发动机；
- 姿态与转向（推力恒沿速度，不做侧向推力 / 攻角）；
- 风、科氏力等其它外力；
- `MinecraftTrajectory` 的推力支持；
- 制导律——它属于消费方（Machine-Max 的 `GuidanceLaw`），求解器只认识推力；
- 给 `FiringSolution` 加“命中/最近接近”标记（§5.2 第 3 条的根治方案，独立提案）。

## 九、与 Machine-Max 的衔接

- 时间窗来自内容包字段 `external.thrust`（`force` / `duration` / `ignition_delay`），发射时换算为 `(force, ignitionDelay, ignitionDelay + duration)`。
- 中途重解（初速因命中改变、燃尽校核）传入 `(force, 0, burnEnd − burnElapsed)`，其中 `burnElapsed` 是该发弹已累计的燃烧秒数。
- 动目标提前量走 `#solveWithLead` 的推力重载；`maxIterations` / `convergeEpsilon` 按飞行时长给（§5.2 第 2 条）。
- 预测步长取 0.01 s，与 `ProjectileManager#updateProjectiles` 的积分一致。
- 消费方如何组织预测、过滤区块、滚动预载，全部归 Machine-Max 仓库的 `docs/plan/计划中/武器系统-投射物弹道预测与区块预载设计.md`，本文不重复。
