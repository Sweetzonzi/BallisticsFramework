## 一、目标与边界

| 能力 | 本计划 |
| --- | --- |
| **多次点火**：一条弹可以有多个燃烧窗口，窗口之间是纯弹道滑行 | 做 |
| **燃烧期质量流失**：推进剂在段内匀速烧掉，推力加速度随质量下降上升 | 做，按段可选、缺省关闭 |
| 推力曲线 / 推力随时间连续变化 | 不做 |
| 分级分离（级间分离、质量与迎风面积跳变） | 不做 |
| 推力方向（非沿速度）、攻角、侧向推力 | 不做 |
| 风、科氏力等其它外力 | 不做 |

两条理由决定了"做"的范围：

1. **段表是闭包**：单窗口是段表的一个元素，`NONE` 是空段表，因此分派门禁只需判"段表是否为空"这一条静态条件，不必引入按步分派。
2. **质量由两个既有量拼出**：基础质量在 `BallisticConfig#mass`，每个推力段带一个质量。于是 `m(t) = 基础质量 + Σ 未燃尽的段质量` 是这两个量的确定性函数，没有第三个输入、不需要新增运行期状态，也不需要给 `BallisticConfig` 加字段（它是 record，加字段会破坏所有构造点）。

## 二、API

```java
public record ThrustProfile(List<Segment> segments) {

    /** 单个推力段：forceN 是推力（N），delaySeconds 是点火延迟，durationSeconds 是持续时长；massKg 段内匀速消耗、段末归零 */
    public record Segment(float forceN, float delaySeconds, float durationSeconds, float massKg) {}

    public static final ThrustProfile NONE = new ThrustProfile(List.of());

    /** 单段、恒质量："一次助推"的规范写法，等价于一个 Segment、段质量 0 */
    public static ThrustProfile of(float forceN, float delaySeconds, float durationSeconds);

    public boolean isActive();                 // 段表非空
    public List<Segment> segments();           // 规范化后的段表（不可变、按点火时刻升序）

    public float forceAt(double seconds);      // 段内推力（N），段外与空隙为 0
    public float massAt(double seconds, float baseMass);  // baseMass + Σ 未燃尽的段质量

    public float startSeconds();               // 首段点火时刻；NONE 为 0
    public float endSeconds();                 // 末段熄火时刻；NONE 为 0
    public float burnDuration();               // Σ durationSeconds（不是末段熄火时刻）
    public ThrustProfile remainingSince(double elapsedSeconds);
}
```

时间参数一律取 `double`，理由见 §3.1：积分器用 `(step − 1) × (double) Δt` 算步初时刻，这里若收 `float`，窗口边界会因多一次窄化而翻转。返回值仍是 `float`，`aT = forceAt / massAt` 因此保持 float 除法，§四「单段剖面与单窗口等价」的逐位前提不变。

**质量只有两个来源**：`BallisticConfig#mass` 是基础质量（弹体自重），`Segment#massKg` 是该段的质量。`massAt(t, baseMass)` 把两者相加、再扣掉已燃尽的部分，因此只依赖剖面与时间，调用方不需要在求解前统计"当前质量是多少"，也不需要区分结构质量与装药质量——内容包里一个推力段只有一个质量。

两个入口，分工明确：

- **规范构造器** `new ThrustProfile(List<Segment>)` 是唯一能表达多段与段质量的形态；
- **`of(forceN, delaySeconds, durationSeconds)`** 是"一次点火、恒质量"的规范写法，等价于 `new ThrustProfile(List.of(new Segment(forceN, delaySeconds, durationSeconds, 0f)))`。

第三个参数是**持续时长**而不是熄火时刻：单段的冲量就是 `forceN × durationSeconds`，多段的冲量直接相加，与内容包的 `delay + duration` 一一对应，不需要再做 `start + duration` 的加法。

只做一次助推的消费方（绝大多数使用场景）只需要 `of`，不必接触 `Segment` 与 `massKg`。

`force()` 不提供：多段剖面没有单一推力，保留它只会诱导调用方按单段写代码。调用点分两类写法：**逐点取力**（三个推力积分器的 `aT`）用 `thrust.forceAt(t)`；**摘要量**（`#solveWithLead` 的 `estimateSpeed`）按段累加（§四）。

## 三、语义

### 3.1 窗口与 `forceAt`

窗口是 `[delaySeconds, delaySeconds + durationSeconds)`，左闭右开，与 `RealisticTrajectory` 的步进判定一致：第 `i` 步覆盖 `[(i−1)Δt, iΔt)`，判定取步初时刻。段外与段间空隙返回 `0`。

窗口右端在 `double` 里算（`(double) delaySeconds + (double) durationSeconds`），不经过两个 `float` 相加后再窄化的二次舍入；段边界本身仍是 `float` 字段。**边界比较必须在 `double` 里做。** 积分器用 `(step − 1) × (double) Δt` 算步初时刻、再与段边界比较。用 `Δt = 0.01f`、窗口下界 `0.5f` 即可看出差别：第 51 步的步初时刻是 `0.4999999888241291`（不施加推力），若中途窄化成 `float` 会舍入成 `0.5f`（施加推力），整步判定翻转。因此 `forceAt` / `massAt` / `remainingSince` 的时间参数都是 `double`。

段表在构造时按 `delaySeconds` 升序排列，`forceAt` 线性扫描并在越过点火时刻后提前退出（段数是个位数量级）。

### 3.2 质量与 `massAt`

段质量在段内匀速消耗，基础质量守恒：

```text
mdot_i     = massKg_i / durationSeconds_i                                      （kg/s）
burned_i(t)= massKg_i · clamp01( (t − delaySeconds_i) / durationSeconds_i )
m(t)       = max(baseMass + Σ (massKg_i − burned_i(t)), ε)
```

`burned` 先算比值再乘 `massKg`，而不是"钳位到秒再乘 `mdot`"。差别在段末：比值被钳到 1 时结果**恰好**是 `massKg_i`，段末质量精确归零；写成 `clamp(t − delay, 0, duration) · mdot` 时 `duration · mdot` 可能比 `massKg_i` 大出 1e-6 kg 量级（`massKg = 29.742`、`duration = 14.257` 得 `29.742002`），残余会被记成负数，§五 T17 的逐位断言与 §3.4 的"丢弃已燃尽段"就不再等价。

- 质量曲线只由段质量与持续时长决定，与 `forceN` 无关——推力大小不影响烧掉多少药。
- 排气速度 `ve_i = forceN_i / mdot_i` 是派生量，不是构造参数。
- 所有段的 `delaySeconds ≥ 0` 时，`m(0) = baseMass + Σ massKg_i` 就是发射质量；求解器内部按上式算，调用方不必自己求和。
- 段质量为 0 的剖面（`of(...)`、`NONE`）不改变质量：`massAt` 逐位返回 `baseMass`（`baseMass` 本身高于下限 `ε` 时）。这是单段剖面与单窗口形态逐位一致的依据。
- `ε` 取 `1e-6 kg`（`MASS_FLOOR`），只用于避免除零。
- **累加在 `float` 里按段序逐步做**：`float total = baseMass; for each segment: total += massKg_i − burned_i(t);` 最后 `Math.max(total, ε)`。不是"在 `double` 里求和再窄化"——那样每段多一次舍入，`remainingSince` 裁剪后的剖面与原剖面会在末位分家，§五 T17 的逐位断言就不成立。
- 段表允许全部落在 `t = 0` 之前。此时 `forceAt` 全程为 0、`massAt` 已扣完全部段质量，正是「先 `remainingSince` 再求解」的等价结果——它不需要额外校验，也不是错误配置。

### 3.3 规范化

构造器内完成四件事，调用方不必预处理：

1. **丢弃无效段**：`forceN` 或 `durationSeconds` 为非正、`massKg` 为负、任一值为非有限，或派生量 `mdot_i = massKg_i / durationSeconds_i` 非有限。丢弃一段的效果是**这一段从此不存在**：`forceAt` 与 `massAt` 都看不到它，既不产生推力也不贡献质量——它不等于 `NONE`，`isActive()` 看的是剩余段。最后一条判据防的是笔误而不是 NaN：按 §3.2 的先除后乘形态，`mdot` 溢出不会产出 NaN，只会把弹丸变成 `3e38 kg`、推力项退化为 0 的近直线弹道；丢弃它倒是落回一条能读的曲线，但两种结果都不是用户想要的，所以真正的防线在内容包侧的数值校验，这里只保证不把荒谬值带进解算。
2. **按 `delaySeconds` 升序排序**（稳定排序，相等时保持书写顺序）。
3. **相邻段若有重叠，抛 `IllegalArgumentException`**（允许空隙，空隙即滑行；重叠是调用方笔误，静默接受会悄悄改变弹道，因此与无效段不同——一个丢弃、一个拒绝）。判定容差 `1e-6 s`：两个十进制写法在二进制里可能相差几个 ulp（`0.3 + 0.1` 与 `0.4f` 差 7.5e-9 s），小于该值的重叠按接触处理，毫秒级及以上的重叠仍会被拒绝。
4. **用 `List.copyOf` 冻结段表**。`ThrustProfile` 会被三个线程并发读取（服务端积分、客户端外推、地形预载），值类型拿着一个可变列表就不再是值类型。

`delaySeconds` 允许为负，沿用"负值表示从求解起点就已点火"的语义。

### 3.4 时间原点与 `remainingSince`

`delaySeconds` 的原点是**发射时刻**，与内容包给出的时间同源。求解器把收到的剖面一律解释为"已经平移到本次求解起点"：`t = 0` 就是入参位置与速度对应的时刻。首次求解时两个原点重合，剖面可以直接传。

中途重解（初速因命中改变、燃尽校核）时两个原点不再重合，调用方必须先平移，否则整条燃烧窗口会整体后移 `elapsed` 秒。`remainingSince(elapsed)` 做这件事：整体减去 `elapsed`，返回不可变的新剖面。

**基础质量守恒让续算不需要任何质量参数**：`baseMass` 由 `config.mass()` 提供、裁剪不碰它，`massAt` 在新原点自动成立——烧掉的药已经体现在"段质量减少"里，不会被扣第二次。三条裁剪规则：

- **已燃尽**（`delaySeconds + durationSeconds ≤ elapsed`）：丢弃。
- **正在燃烧**（`delaySeconds < elapsed < delaySeconds + durationSeconds`）：`delaySeconds` 置 `0`、`durationSeconds` 改为剩余时长、`massKg` 改为 `massKg − burned(elapsed)`。窗口变短、质量变少，`mdot` 保持不变，`forceAt` 与 `massAt` 在新区间上与原剖面逐点对应。
- **尚未点火**（`delaySeconds ≥ elapsed`）：`delaySeconds` 减去 `elapsed`，`durationSeconds` 与 `massKg` 不变。

质量用与 `massAt` 同一个 `burned` 函数折算，因此 `remainingSince(elapsed).massAt(0, m)` 与原剖面 `massAt(elapsed, m)` 逐位相同（T17）。调用方传的 `elapsed` 只是时间差，不必是"累计燃烧秒数"。

## 四、`RealisticTrajectory` 接线

| 位置 | 实现 |
| --- | --- |
| `#forwardSolve` 的推力门禁 | `thrust.isActive() && velocity.length() > 1e-10`；段间空隙由 `forceAt = 0` 自然跳过，不存在按步分派 |
| 步初时刻 | 每个推力积分器每步算 `double stepStart = (i - 1) * (double) dt;`，只算一次、供当步的取力、取质量共用 |
| 当步质量 | `float m = thrust.massAt(stepStart, config.mass());`——阻力系数与推力加速度共用；段质量为 0 时它逐位返回 `config.mass()` |
| 当步推力 | `float forceN = thrust.forceAt(stepStart);`，`forceN > 0f` 才施加；`aT = forceN / m` 保持 float 除法 |
| `#solveThrustNoDragSI` | `speed += aT * dt`；不涉及阻力，因此只在有推力的步取质量 |
| `#solveThrustStraightDragSI` | `halfRhoRef = 0.5f * cd * area / m` 每步重算，`accel = -halfRhoRef·ρ·speed² + (forceN>0 ? aT : 0)` |
| `#solveThrustReducedSI` | 同式；推力项仍带 `vMag > 1e-10` 守卫（去掉后 `aT·dt/vMag` 在近垂直顶点会给出 `Infinity` / `NaN`） |
| `#solveWithLead` 的 `estimateSpeedBoost` | 逐段累加"该段速度增量的一半"：`r_i` 落在 `[0, 1]` 端点的段取 `(0.5f · (forceN/m_i)) · durationSeconds`，`r_i ∈ (0, 1)` 的段取时间平均闭式解 `ve·[1 + r·ln r/(1−r)]`；`m_i` 是该段点火时的质量 |
| 非推力路径的 `config.mass()`（`#solveStraightDecelerationSI`、`#solveFullIntegrationSI`、`#solveParabolicMotionSI`、`#solveLinearMotionSI`） | 常量，不看剖面 |

**`estimateSpeed` 的两式**：`ve · ln(m₀/m_f)` 是整段燃烧的**总 Δv**，不是区间平均速度；无段质量式取的就是"总 Δv 的一半"（单段时即时间平均，与单窗口形态逐位相同）。有段质量时"总 Δv 的一半"会把平均速度高估（`r = 0.5` 时高 13%，`r = 0.25` 时高 29%），首轮预测点仍然偏近，因此改用时间平均的闭式解 `ve · [1 + r·ln r/(1−r)]`；它 `r → 1` 时退化为 `½·ve·ln(m₀/m_f)`，与无段质量式连续。符号：`ve_i = forceN_i · durationSeconds_i / massKg_i`，`m_i` 是该段点火时的质量，`m_f,i = m_i − massKg_i`，`r_i = m_f,i / m_i`；段间不重叠，全部按段序燃尽时 `m_i = baseMass + Σ_{j≥i} massKg_j`。

**判据必须逐段，不能对整表判一次 `Σ massKg_i`。** §一 把质量流失定为"按段可选"，因此"一段有质量 + 一段 `massKg = 0`"是合法剖面；按整表判档会让零质量段走进质量式，得到 `mdot = 0`、`ve = +∞`、`r = 1`、`r·ln r/(1−r) = 0/0 = NaN`。分档的实际判据是 `r ∈ (0, 1)` 而不是 `massKg == 0`：段质量小到 `massKg / m_i` 在 `float` 里舍入成 0 时（小于基础质量的 `2⁻²⁴` 量级），`r` 已经是 1；基础质量为 0 时 `m_i = massKg`，`r` 落到 0。两个端点走质量式都会得到 `0/0`，而它们与零质量式是同一个极限，所以并到一起。`estimateSpeed` 变 NaN 后 `roughTime = roughDist / Math.max(NaN, 1e-6f)` 仍是 NaN，`roughTime > 0` 为假，首轮预测点退回目标当前位置——不会崩，但提前量的首轮粗估失效，迭代从更远的地方起步。

**这组公式只对"已平移到本次求解起点"的剖面成立。** `delaySeconds < 0` 或整段落在 `t = 0` 之前的剖面（§3.2 明确允许，不报错）若按上式求和，会把已经烧掉的段当成还没点火，凭空多出半段 Δv。重解前先 `remainingSince` 这条前提自动满足；首次求解就带负延迟时估算偏大，只影响首轮预测点，迭代会收敛。

无段质量式的写法要注意结合顺序：`estimateSpeed += (0.5f * (forceN / m_i)) * durationSeconds`，左结合即 `(0.5f · aT) · d`。写成 `0.5 * Σ(aT_i · d_i)` 会把 `0.5` 提到求和外，单段时就可能差 1 ulp，而 `estimateSpeed` 经 `roughTime` 改变首轮预测点、进而改变整个迭代轨迹与最终解——这是"逐位相同"唯一会失守的地方。

四条不变式：

- **剖面含有效段且初速非零时，走推力积分器**，包括段间空隙，也包括「所有段都落在求解视界之外」的剖面（此时 `forceAt` 恒为 0）。于是非推力退化路径从不调用 `massAt`、始终用常量 `config.mass()`，改造面停在推力三个积分器上；代价是空隙步也走推力积分器，收益是分派门禁保持静态、不必按步分派。门禁上还挂着既有的 `velocity.length() > 1e-10`：初速为零时推力方向 `v̂` 无定义，落进非推力积分器，它们按 `config.mass()` 算阻力、段质量不参与——这条边界写进 §七。
- **单段剖面与单窗口等价**：`of(...)` 的段质量为 0，`massAt` 逐位返回 `config.mass()`，`forceAt` 在窗口内返回同一个 `float`，因此 `aT`、除质量的算术与单窗口形态逐位一致（T10 以冻结基线守住）。前提是 `forceAt` / `massAt` 的返回类型保持 `float`——若中途经 `double` 再窄化回 `float`，就是一次二次舍入，`aT` 会差 1 ulp，逐位就不成立了。
- **`solveFiringAngle` 的门禁**仍用 `isActive()`，语义是"剖面里有推力"，与空隙无关。
- **等价性分三个层级，断言必须指明层级**：① 同一代码路径 + 同一输入 ⇒ 逐位一致（`NONE` 与不带剖面参数的重载、单段 `of` 与单窗口、乱序段排序后与前序写入、视界外的段）；② 同一离散格式的两份实现 ⇒ 数学等价，浮点差在 T5 实测的 5.5e-7 m 量级（如平面二维推进与三维全积分、空隙内与无推力外推）；③ 不同离散格式 ⇒ 米级（见 `docs/弹道求解器-推力项设计.md` §四「离散语义」的 `½aΔt·t`）。

「窗口全在视界外」与「传 `NONE`」属于层级②，不是层级①：前者走 `#solveThrustReducedSI`（阻力项在 `double` 里算），后者走 `#solveFullIntegrationSI`（`float dragFactor`），差在 T5 实测的 5.5e-7 m 量级。带上段质量后两者连"同一发弹"都不算：`NONE` 的阻力按 `config.mass()`，带剖面的一侧按 `baseMass + Σ massKg`，差异是质量比量级。T11、T12 与本节的分层比较一律把 `massKg` 固定为 0。

| T10 | `singleSegmentProfileReproducesLegacyWindowBits` | 单段 `of(2600, 0.5, 2.5)` 与迁移前 `ThrustProfile(2600, 0.5, 3.0)` 的轨迹逐位相同 |
| T11 | `segmentedBurnCoastsThroughGapThenReignites` | 双段含 0.5 s 空隙：空隙内与无推力外推逐点相差 < 1e-3 m；第二段点火后速率立刻抬升约 `a_T·Δt = 1 m/s` |
| T12 | `segmentBeyondHorizonIsInvisible` | 第二段起点晚于求解视界 ⇒ 与只含第一段的剖面逐位相同 |
| T13 | `profileNormalisationRejectsOverlapAndDropsInvalidSegments` | 重叠段抛 `IllegalArgumentException`；`massKg` 为负的段被丢弃；乱序段排序后与顺序写入逐位相同 |
| T14 | `massLossProducesTsiolkovskyVelocityIncrement` | 燃尽时刻的速度增量相对误差 < 2e-3；燃尽后 `massAt` 等于基础质量 |
| T15 | `singleSegmentProfileEqualsExplicitSegmentList` | `of(f, s, d)` 与一段、质量为 0 的段表相等；段质量为 0 时 `massAt` 逐位返回 `baseMass` |
| T16 | `remainingSinceContinuesTailOfUnclippedTrajectory` | 从 `elapsed` 处续算，与不裁剪、从发射点一路算到同一时刻的尾部逐点相差 < 1e-3 m |
| T17 | `remainingSincePreservesMassBitsAtTheCut` | `remainingSince(elapsed).massAt(0, m)` 与原剖面 `massAt(elapsed, m)` 逐位相同 |

T10 的基线冻结在 `src/test/resources/io/github/sweetzonzi/ballistics_framework/api/trajectory/t10-legacy-baseline.txt`：采样点数、全轨迹 64 位摘要（`floatToIntBits` + 6 个 `doubleToLongBits` 的 FNV-1a），以及首尾各 5 个采样点的位模式。场景 `start (0,64,0)`、`velocity (50,20,0)`、`config (0.3, 26, 0.018, 9.81, 0.01, 2000)`、`CONSTANT_DENSITY`。基线是迁移前采的，因此它锁定的是"单段剖面复现单窗口算术"这件事本身；`docs/弹道求解器-求角免物化与采样存储改造计划.md` 的 B2 阶段会把中间量从 `float` 放宽到 `double`，届时基线需要重取，判据由那份计划的 §七.1 八用例矩阵接管。

T14 与 T16 的容差口径与 T4、T5 一致：只捕获"项写错"这类米级偏差，不锁数值快照。两条各有前提：

- **T14 的容差由离散求和决定**：左端点求和与连续解的相对误差约为 `½·(1−r)²/(r·T)·Δt/ln(1/r)`，取 `r = 0.5`、`T = 2.5 s`、`Δt = 0.01 s` 得 1.4e-3，因此容差取 2e-3。`Δt = 0.05 s`（`BallisticConfig` 的默认值）时该误差升到 7e-3，那组参数不适用本断言。
- **T16 的 1e-3 依赖网格对齐**：`elapsed` 取 `Δt` 的整数倍、初值取原轨迹该时刻的采样点。二者缺一，裁剪后的燃烧边界会落在不同的步上，单步冲量差可达 `a_T·Δt`（`a_T = 100 m/s²`、`Δt = 0.01 s`，约 1 m/s），尾部差出米级。

## 六、接口决策、版本与文档

- **不提供三参构造器**：不做 `ThrustProfile(float, float, float)`。它会让这个类型看起来像"几个字段的 record"，而它的状态是段表。同样的便利由 `of(...)` 承担，命名清楚、不会与规范构造重载混淆。`of` 不是兼容垫片，是常见形状的规范拼写：单段恒质量是绝大多数调用方的全部需求，也是本库最该短的那条路。
- **`NONE` 语义**：空段表与三个不带剖面参数的重载（4/7/10 参）走同一条路径，逐位一致（T1 守住）。
- **版本**：`1.0.0.alpha.15`。本文先于 `docs/弹道求解器-求角免物化与采样存储改造计划.md`（`alpha.16`）落地——后者要在本文的输出上取逐位基线，顺序反了基线会被本文的算术改动污染。
- **破坏性变更（源码级）**：`ThrustProfile` 的构造写法变了，`force()` 被移除。下游从 `alpha.14` 迁移到 `alpha.15` 按下面的对照表改。

| `alpha.14` 的写法 | `alpha.15` 的写法 |
| --- | --- |
| `new ThrustProfile(force, start, end)` | `ThrustProfile.of(force, start, end − start)`（第三参由熄火时刻改为持续时长） |
| `new ThrustProfile(0f, 0f, 0f)` | `ThrustProfile.NONE` |
| `thrust.force()` | 逐点用 `thrust.forceAt(t)`；摘要量按段累加（§四 `estimateSpeed`），`burnDuration()` 是 Σ 段时长、不等于首段起点到末段熄火时刻的跨度 |

`startSeconds()` / `endSeconds()` 保留：单段剖面上语义与单窗口形态相同，多段剖面上分别返回首段起点与末段熄火时刻。

- **文档归属**：推力相关的四篇文档描述的都是分段形态——本文（API、语义、接线、T10–T17）、`docs/弹道求解器-推力项设计.md`（求解器一侧的位置、退化路径、反解与提前量、T1–T9）、`docs/外弹道设计文档.md`（模型层面的推力与质量）、`docs/wiki/5-外弹道工具/` 的 5.2 / 5.3 / 5.4（调用示例）。`AGENTS.md` 的 Important conventions 段与 `BallisticConfig#mass` 的 Javadoc 按"基础质量 + 段质量"的口径陈述。

## 七、明确不做

- **推力曲线 / 任意函数**：固体发动机的实际剖面是"平台 + 尾段爬升"，2~4 个分段点足够；采样曲线没有消费方。
- **分级分离**：真正的多级有级间分离、质量跳变与迎风面积跳变。段表给的是"多次点火"，每个段的质量在段内烧尽，没有"各级干重"这个概念，也不含分离事件。
- **指令点火（飞行中由外部指令触发）**：它把各段的 `delaySeconds` 从发射前就固定的常量变成每发实例的运行时状态，需要消费方自己持有"已解析的剖面"；库侧不引入该概念。
- **质量随时间的一般形式**：只支持"段内匀速消耗"。非匀速（如燃面变化）用更多分段近似表达。
- **初速为零的推力发射**：推力方向 `v̂` 在静止点无定义，`#forwardSolve` 的门禁（§四第一条）把它交给非推力积分器，那里按 `config.mass()` 算阻力、段质量不参与——一次"从静止点火"会被算成"基础质量 + 无推力"，阻力偏大。要表达静置发射，调用方给一个非零初速（哪怕 `1e-3` m/s），或把段质量并入 `config.mass()` 后传 `NONE`。两条都会放弃"质量随燃烧流失"，因此这是模型的边界而不是配置错误。

## 八、与 Machine-Max 的衔接

| 内容包字段 | 折算到 |
| --- | --- |
| `base_mass` (kg，基础质量) | `BallisticConfig#mass` |
| 每段 `mass` (kg，推力段质量) | 该段的 `massKg` |
| `force` (N) | 该段的 `forceN` |
| `start` (s，自发射瞬间) | 该段的 `delaySeconds` |
| `duration` (s) | 该段的 `durationSeconds` |

剖面上没有"段的起止时刻"这两个字段：`startSeconds()` / `endSeconds()` 是 `ThrustProfile` 的只读派生量（首段 `delaySeconds`、末段 `delaySeconds + durationSeconds`），内容包不需要也不应该设置它们。

- 内容包的 `external.thrust` 从对象改为段数组，`ignition_delay` 由 `start` 取代。
- **质量模型**：`m(t) = BallisticConfig#mass + Σ 未燃尽的段质量`。内容是常量，发射前构造一次剖面即可；发射质量由求解器算，调用方不用求和，也不必在每次重解时报"当前质量"。
- **`BallisticConfig#mass` 只有一个含义**：基础质量。推力路径拿它当基线加段质量；无推力路径（含 `NONE` 剖面）直接把它当全重——没有剖面就没有段质量，两个用法在这些输入上重合。唯一的例外是 §七 的零初速边界：剖面带段质量但初速为零时走非推力积分器，段质量被忽略、`config.mass()` 被当成全重，实际用"基础质量"这个数去算一条本该更重的弹道。这条已记在 §七，不是隐藏语义。
- **两条时间原点要分开说**：Machine-Max 自己的积分器（`TrajectoryStep`）按发射时刻的绝对时间推进，段表与它同源，因此不调用 `remainingSince`；而它调用 `forwardSolve` / `solveFiringAngle` 做重解时，`t = 0` 是重解时刻，必须先 `remainingSince(elapsed)`。续算不需要传质量——基础质量与裁剪后的段质量已经把 `m(t)` 决定好了。
- 质量一律由「基础质量 + 剖面段质量」给出，消费方不得再维护一条"求解器不知道"的质量曲线，否则两边会分家。
