# 终点弹道协议（Terminal Ballistics Protocol）技术设计文档

## 一、项目定位与设计目标

本项目为 Minecraft NeoForge/Forge 模组生态定义一套"终点弹道伤害协议层（Terminal Ballistics Damage Protocol Layer）"。其核心定位是一个可供多个枪械、载具、护甲模组共同依赖的 **lib 级兼容协议**，而非一个独立运行的 damage overhaul mod。

协议的终极目标是解决以下问题：在 Minecraft 原生伤害系统中，`DamageSource` 是被设计为不可变的、registry 化的"伤害类型标签"，其职责仅限于描述伤害的种类和来源实体。对于高复杂度场景——枪炮弹道、穿甲深度、命中角度、入射法线、装甲等效厚度、模块化部件伤害等——这些信息是**一次命中过程中临时产生的高维上下文**，它们既不适合塞入 `DamageSource`（那是类型描述而非数据容器），也不适合持久存储在实体 Capability 中（它们只在该次伤害调用链内有意义）。在没有协议的情况下，不同武器模组和装甲模组只能各自发明私有的 ad-hoc 方案，互不兼容。

协议的设计原则如下：

1. **不替代原版，而是包裹原版**：协议绝不绕开 `Entity#hurt`/`LivingEntity#hurt`、绝不直接 `setHealth`、绝不重新实现完整的 combat pipeline。对于未声明协议感知的普通实体，伤害完全走原版流程，协议层透明不参与。
2. **对声明协议感知的目标接管伤害入口**：当一个实体实现了 `BFHurtTarget` 接口，它便声明了"我自行处理穿甲判定和伤害后果"。此时协议层在完成穿甲协商后直接将最终伤害值交给该目标，由目标自行决定是调用 `super.hurt()` 走原版管线，还是完全自定义处理。
3. **上下文通过 ThreadLocal 隐式传递，但 API 完全封装**：由于 vanilla 的 `hurt` 方法签名是固定的，无法显式传递额外参数，协议层使用 ThreadLocal 栈在调用链内传播上下文。但所有 push/pop/try/finally 细节完全内嵌于 `BFDamageApi.hurt()` 内部，协议使用者永远不需要直接接触 ThreadLocal。
4. **双层设计——简易模式与精密模式并重**：协议的默认行为基于离散的 `ArmorLevel` 穿甲/护甲等级体系，简单模组只需实现一个方法即可获得完整的穿甲判定（HD2 风格）。需要精确毫米级判定的模组可覆写全部管线方法深化至精细纯数值模型。穿深的角度效应等归弹头/武器侧计算，协议不默认修正。
5. **协议外伤害有限兼容**：原版生物攻击、TNT 爆炸、岩浆、虚空、指令等"非协议来源"的伤害，如果命中了一个 `BFHurtTarget` 或**穿戴了** **`TBArmorMaterial`** **护甲的实体**，协议层会自动将它转换为一个协议上下文，然后走完整穿甲判定管线。这通过 Mixin 注入 `Entity#hurt` 和 `LivingEntity#hurt` 实现。
6. **护甲装备的协议化接入**：玩家等无法直接实现 `BFHurtTarget` 的原版实体，可通过让护甲物品实现 `TBArmorMaterial` 接口来获得穿甲判定能力。协议层自动识别穿戴此类护甲的实体，通过内部适配器（`TBArmorAdapter`）将其纳入管线——护甲模组无需做事件订阅或手动拦截。原版护甲属性（ARMOR / ARMOR\_TOUGHNESS）的减免可在协议伤害之上叠加，形成两层防护模型。

### 2.2 api/ —— 公共 API 面

这是依赖本 lib 的武器模组或护甲模组唯一需要 import 的包。`api.*` 中的所有类和接口均保证版本兼容性，语义保持稳定。各文件职责：

- **TBArmorMaterial**：护甲物品接口。护甲模组让物品实现此接口后，穿戴该物品的实体——无论是否实现 `BFHurtTarget`——在受到协议伤害或原版伤害时，协议层都会自动将其纳入穿甲判定管线。提供两个 default 方法：`getArmorLevel(EquipmentSlot, BFDamageContext)` 和 `getRHA(EquipmentSlot, BFDamageContext)`，按槽位返回防护数据。
- **ArmorLevel**：13 级离散穿甲/护甲等级枚举（含元等级 UNPENETRABLE）。提供 RHA 值的双向映射（`fromRha`）、等级判定（`canDefeat`）、显示名（`getArmorDisplayName` / `getPenetrationDisplayName`）和边界查询（`upperRha` / `lowerRha` / `medianRha`）。是简易模式的基石——简单护甲模组甚至可以只返回一个枚举值而不关心 RHA 数值。
- **BFDamageApi**：静态方法集合，对外唯一入口。包含 `hurt(Object, BFDamageContext)`（发起协议伤害）、`hasContextFor(Object)`（重入守卫）和 `getContextFor(Object)`（上下文取回）。所有 ThreadLocal 管理逻辑封装在此类的委派调用中。
- **BFDamageContextBuilder**：Builder 模式构造器。位于 api 包但构造器为包可见，外部只能通过 `BFDamageContext.builder()` 获取实例。逐一设置各字段后调用 `build()`。
- **BFDamageContext**：不可变值对象。六个字段通过构造函数一次性赋值。新增 `getPenetrationLevel()` 便捷方法——直接从穿深值映射到 `ArmorLevel`。
- **BFDamageExtensions**：扩展数据的类型安全读写容器。内部持有一个 `Map`，对外提供带有默认值退回的 `get`/`set`。协议自身预定义 `FUSE_DELAY` 扩展 key（引信延迟）。
- **BFDamageExtensionKey**：泛型 key 类。构造器包可见，绑定 `ResourceLocation`、`Class<T>` 和默认值工厂。
- **PenetrationResult**：穿甲判定结果枚举——`PENETRATED`（击穿）、`BLOCKED`（未击穿）、`RICOCHET`（跳弹），三者互斥。由 `BFHurtTarget.resolvePenetration()` 返回，作为 `calculateFinalDamage` 和回调触发的唯一依据。
- **BFDamageHandler**：伤害发起方接口。武器/弹头模组实现，在构造上下文时注入。提供 `onPenetrated`、`onBlocked`、`onRicochet`、`onOvermatch`、`onSpall` 等回调钩子，以及 `dealDamage(target, ctx)` 便捷方法（自动将自身注入上下文再调用 API）。
- **BFHurtTarget**：核心接口。简易模式下实现者只需提供 `getArmorLevel` 和 `hurt`，其余方法均有基于离散等级的默认实现。精密模式下可覆写全部管线方法回到纯数值模型。新增 `resolvePenetration()` 方法返回 `PenetrationResult`，`calculateFinalDamage` 接收该结果作为入参。

### 2.3 internal/ —— 内部实现

此包内所有类为协议内部实现细节，不构成公开 API，不保证跨版本兼容性。

- **TBArmorAdapter**：护甲适配器。将穿戴了 `TBArmorMaterial` 护甲的 `LivingEntity` 包裹为 `BFHurtTarget` 实现，使协议管线能查询装备槽位中的护甲防护数据。同时提供静态方法 `hasTBArmor(LivingEntity)` 供 `BFDamageApi` 和 `BFHurtInterceptor` 共用。hitPoint 按高度占比精确映射到装备槽位（HEAD/CHEST/LEGS/FEET）；无命中点时退回到取所有槽位最高等级的保守策略。
- **TBContextStack**：封装 `ThreadLocal<Deque<StackEntry>>` 的管理。`StackEntry` 是其 `private record`（target + context 对）。对外提供 `push(target, ctx)`、`pop()`、`hasContextFor(target)` 三个操作。
- **TBExtensionKeyRegistry**：全局注册表，持有已注册的 `BFDamageExtensionKey`。在 `register()` 时检查 ID 重名。

### 2.4 mixin/ —— Mixin 注入类

- **EntityHurtMixin**：`@Mixin(Entity.class)`，注入 `Entity#hurt` 的 HEAD 阶段（cancellable=true）。
- **LivingEntityHurtMixin**：`@Mixin(LivingEntity.class)`，注入点同上。必须独立存在——JVM 对 LivingEntity 实例的方法分派直接进入覆写版本。

两者对 LivingEntity 实例不会重复触发：方法分派只命中一个覆写版本。

### 2.5 依赖关系

```
            ┌─────────┐
            │  api 包  │  ← 外部 mod 仅依赖此包
            └────┬────┘
                 │ 委托
            ┌────▼────┐
            │internal包│  ← 内部实现，包可见
            └────┬────┘
                 │
  mixin 包 → 调用 BFDamageApi.hasContextFor() + BFDamageApi.hurt()
  护甲适配 → TBArmorAdapter 实现 BFHurtTarget，内部委托回原版 Entity#hurt
```

api 包中的 `BFDamageApi` 和 `BFDamageExtensions` 依赖 internal 包完成实际工作，但依赖方向始终从 api 向内，使用者的编译路径仅需 api。mixin 包引用 api 和 internal。`TBArmorAdapter` 位于 internal 包，外部模组不可直接引用，只能通过 `TBArmorMaterial` 接口接入。

## 三、BFDamageContext —— 核心数据结构

`BFDamageContext` 是一次命中行为的完整上下文描述对象，由武器模组（协议发起方）在调用 `BFDamageApi.hurt()` 前构造。它是一个不可变的值对象——所有字段在构造时确定，穿甲判定过程中仅读取、不写入。

### 3.1 必备字段

```java
public record BFDamageContext(
    DamageSource source,              // vanilla DamageSource
    float baseDamage,                 // 标称伤害量
    Vec3 hitVelocity,                 // 命中速度矢量（世界坐标）
    Vec3 hitPoint,                    // 命中点世界坐标
    Vec3 hitNormal,                   // 命中面法线（指向面外侧）
    float penetration,                // 理论穿深（垂直RHA等效，mm），由武器侧计算
    BFDamageExtensions extensions,    // 类型安全扩展容器
    @Nullable BFDamageHandler handler // 伤害发起方回调接口，可选（null 表示无回调）
)
```

**source** —— vanilla `DamageSource` 的完整引用。协议层不创建新的 source、不修改 source、也不把额外字段塞入 source。`DamageSource#getEntity()` 返回间接攻击者，`DamageSource#getDirectEntity()` 返回直接攻击者（子弹实体）。

**baseDamage** —— 等同原版 `Entity#hurt(DamageSource, float)` 的 `amount` 参数。在穿甲判定完成后，`BFHurtTarget.calculateFinalDamage` 默认按分级逻辑处理 baseDamage：未击穿 0、同级击穿 65%、越级击穿 100%。

**hitVelocity** —— 命中瞬间弹体的速度矢量（单位 m/s）。其模长是命中速度，其方向是入射方向。需要入射方向时 `hitVelocity.normalize()` 即可。保留完整矢量而非归一化方向是因为部分装甲模型需要的正是速度大小（如动能判定）。

**hitPoint** —— 命中点的世界坐标。由武器模组的弹道追踪产生。护甲模组用它来确定命中部位，然后返回对应部位的装甲属性。

**hitNormal** —— 命中面的法线向量，指向面外侧。可用于计算入射角、播放反弹粒子等。

**penetration** —— 理论穿深。由武器模组填入，是弹体在命中条件下的 RHA 等效穿透能力（mm）。**重要：从 v2 起，角度效应等归弹头/武器侧在构造上下文前自行计算**，协议不再做默认斜穿修正。这意味着武器模组在调用 builder 时填入的 `penetration` 已经是考虑过角度、距离衰减等后的最终穿深值。协议内核只负责比较 `modifyPenetration(ctx)` 与 `getRHA(ctx)`。

**extensions** —— 类型安全扩展容器，见第五章。

**handler** —— 伤害发起方的回调接口，可选（默认 null）。武器模组通过 `builder.handler(myHandler)` 或 `ctx.withHandler(myHandler)` 注入。为 null 时管线不触发任何回调。护甲侧可在 `getRHA` 等方法内通过 `ctx.getHandler()` 查询"谁在打我"做精细判定（如爆反是否对该弹药类型生效）。

record 为不可变类型，通过 `withHandler(handler)` 返回一个新实例（原字段不变，仅替换 handler）：

```java
public BFDamageContext withHandler(BFDamageHandler handler) {
    return new BFDamageContext(source, baseDamage, hitVelocity,
        hitPoint, hitNormal, penetration, extensions, handler);
}
```

**`childContext(newBaseDamage, newPenetration)`** —— 构造子上下文，用于双层串联管线中护甲层向本体层传递修正后的弹头状态。仅替换 baseDamage 和 penetration，其余字段不变：

```java
public BFDamageContext childContext(float newBaseDamage, float newPenetration) {
    return new BFDamageContext(source, newBaseDamage, hitVelocity,
        hitPoint, hitNormal, newPenetration, extensions, handler);
}
```

典型用法：护甲适配器完成 `modifyPenetration`（有效穿深减效）、`resolvePenetration`（跳弹/击穿判定）、`calculateFinalDamage`（残余伤害量）后，构造子上下文，残余穿深传入本体层做二次穿甲判定：

```java
// 护甲层击穿 → 残余穿深传入本体
BFDamageContext childCtx = ctx.childContext(residualDmg, residualPen);
// 护甲层未击穿/跳弹 → 穿深 0 表示仅钝伤
BFDamageContext childCtx = ctx.childContext(residualDmg, 0f);
```

### 3.2 getPenetrationLevel()

`BFDamageContext` 新增便捷方法 `getPenetrationLevel()`，将穿深值映射到离散穿甲等级：

```java
public ArmorLevel getPenetrationLevel() {
    return ArmorLevel.fromRha(this.penetration);
}
```

该方法等价于 `ArmorLevel.fromRha(ctx.penetration())`，被 `BFHurtTarget` 的默认实现内部使用。

## 四、ArmorLevel —— 穿甲/护甲等级枚举

`ArmorLevel` 是一个 13 级枚举（12 级实体等级 + 1 级元等级），将连续 RHA 值映射为离散等级。它是简易模式的核心——参考 Helldivers 2 的离散护甲理念，**同一等级内视为防护效能相等**，不同等级之间是质变而非量变。

### 4.1 等级定义

| 枚举常量            | upperRha | lowerRha | 现实参照                            |
| --------------- | -------- | -------- | ------------------------------- |
| `UNARMORED_1`   | 1mm      | 0mm      | 血肉、无保护裸露表面                      |
| `UNARMORED_2`   | 3mm      | 1mm      | 几丁质甲壳、木板、薄塑料壳                   |
| `LIGHT_1`       | 5mm      | 3mm      | 轻型防弹衣、铁皮、铝合金薄板                  |
| `LIGHT_2`       | 10mm     | 5mm      | 重型防弹衣、装甲车门                      |
| `MEDIUM`        | 20mm     | 10mm     | 一般车辆车架、步战车侧后方                   |
| `HEAVY`         | 40mm     | 20mm     | 步战车正面、坦克侧后/顶部                   |
| `SUPER_HEAVY_1` | 80mm     | 40mm     | 二战早期中型坦克正面（T-34、谢尔曼）            |
| `SUPER_HEAVY_2` | 150mm    | 80mm     | 二战晚期重型坦克正面（虎王、IS-2）             |
| `SUPER_HEAVY_3` | 300mm    | 150mm    | 冷战早期主战坦克（T-55、M48）              |
| `SUPER_HEAVY_4` | 600mm    | 300mm    | 冷战中期+爆反（T-72、M60A3 ERA）         |
| `SUPER_HEAVY_5` | 1200mm   | 600mm    | 冷战晚期现代 MBT（豹2A4、M1A1 HA）        |
| `SUPER_HEAVY_6` | 2000mm   | 1200mm   | 现代 MBT 重爆反+复合间隙（挑战者2 TES、T-90M） |
| `UNPENETRABLE`  | ∞        | 2000mm   | 绝对不可击穿——元等级，仅显式引用获取             |

等级值约 ×2 增长：`1 → 3 → 5 → 10 → 20 → 40 → 80 → 150 → 300 → 600 → 1200 → 2000`。超过 2000mm 的 RHA 值仍映射到 `SUPER_HEAVY_6`——`UNPENETRABLE` 是元等级，不会由 `fromRha` 映射产生。

每个等级有三个 JSON lang key——`armor_level.{ns}.{name}.armor`（护甲显示名）和 `armor_level.{ns}.{name}.penetration`（穿甲显示名），支持中英文分别翻译。`UNPENETRABLE` 的护甲显示名为"绝对防御"（Invulnerable），穿甲显示名为"绝对穿透"（Invulnerable Pen）。

### 4.2 核心方法

```java
// 映射
public static ArmorLevel fromRha(float rha)     // RHA → 等级（向上映射），跳过UNPENETRABLE
public float upperRha()                          // 上限
public float lowerRha()                          // 下限
public float medianRha()                         // 中位值 = (lower+upper)/2

// 离散等级判定
public boolean canDefeat(ArmorLevel armorLevel)  // >= 比较，等于算击穿；对UNPENETRABLE永远返回false

// 本地化显示
public Component getArmorDisplayName()            // 护甲显示名
public Component getPenetrationDisplayName()      // 穿甲显示名
```

### 4.3 使用示例

```java
// 简单护甲模组——我只知道我是"重甲"
ArmorLevel level = ArmorLevel.HEAVY;
float rha = level.medianRha();  // → 30f（中位值），自动填入穿甲判定

// 武器模组查询自己能否打穿某个等级
ArmorLevel penLevel = ctx.getPenetrationLevel();
boolean canPen = penLevel.canDefeat(ArmorLevel.MEDIUM);  // 能打中甲？

// 绝对防御——免疫一切弹道伤害
ArmorLevel godMode = ArmorLevel.UNPENETRABLE;
boolean immune = penLevel.canDefeat(godMode);  // → false，任何武器都打不穿

// HUD 显示
player.displayClientMessage(level.getArmorDisplayName(), true);
// 中文："重甲"  英文："Heavy"
```

`UNPENETRABLE` 不会由 `fromRha` 返回，因此普通武器永远无法自然"达到"这个等级。它只能通过护甲模组在 `getArmorLevel` 中显式返回，用于表示该目标免疫一切弹道伤害。即使精密模式下覆写 `resolvePenetration`，穿深与 `getRHA` 返回的 `Float.MAX_VALUE` 比较也永远为未击穿。

## 五、BFDamageExtensions —— 类型安全扩展机制

```java
public final class BFDamageExtensions {
    private final Map<BFDamageExtensionKey<?>, Object> data;

    BFDamageExtensions() { ... }

    public <T> T get(BFDamageExtensionKey<T> key) {
        // 若未设置，返回注册时的默认值
    }

    public <T> void set(BFDamageExtensionKey<T> key, T value) { ... }
}

public final class BFDamageExtensionKey<T> {
    private final ResourceLocation id;
    private final Class<T> type;
    private final Supplier<T> defaultValueFactory;
}
```

### 5.1 注册

扩展 key 在 mod 初始化阶段通过 `BFDamageExtensions.register()` 注册为全局单例，建议存为 `public static final`。

注册时必须提供：

- **命名空间 ID**（ResourceLocation）：扩展字段的唯一标识符
- **类型**（Class\<T>）
- **默认值工厂**（Supplier\<T>）

```java
// Machine-Max 注册自己的扩展 key
public static final BFDamageExtensionKey<HitBox> HIT_BOX =
    BFDamageExtensions.register(
        ResourceLocation.fromNamespaceAndPath("machine_max", "hit_box"),
        HitBox.class, () -> null);
```

### 5.2 使用

读操作总返回非 null（未设置时退回默认值），消费者无需判空。

### 5.3 协议预定义扩展 key

| 常量           | 类型    | 默认值 | 语义                  |
| ------------ | ----- | --- | ------------------- |
| `FUSE_DELAY` | Float | 0   | 引信延迟（s），0 表示瞬发      |
| `CALIBER`    | Float | 0.1 | 弹体口径（m），默认 100mm 口径 |
| `MASS`       | Float | 10  | 弹体质量（kg），默认 10kg    |

## 六、TBArmorMaterial —— 协议护甲物品接口

`TBArmorMaterial` 是一个供护甲物品实现的接口，位于 `api/` 包。它的核心价值在于：让**无法直接修改实体类**的护甲模组（如给玩家添加防弹胸甲）也能接入协议穿甲管线，无需做任何事件订阅或手动拦截。

### 6.1 设计动机

原版玩家（`ServerPlayer`）、僵尸等原版实体无法实现 `BFHurtTarget`。护甲模组面临的根本问题是：护甲数据在物品上，但穿甲判定的主体是实体。`TBArmorMaterial` 解决了这个矛盾：

- **护甲物品实现此接口**，声明自己在各槽位的防护能力
- **协议层通过适配器自动识别**穿戴了此类护甲的实体，将其纳入管线
- **原版伤害也被接管**：僵尸拍打、TNT 爆炸等命中穿护甲玩家时，Mixin 拦截后通过适配器走穿甲判定

### 6.2 简易模式 vs 精密模式

与 `BFHurtTarget` 对等，`TBArmorMaterial` 也提供双层设计：

| 模式       | 需实现                        | 判定方式                    | 适用场景              |
| -------- | -------------------------- | ----------------------- | ----------------- |
| **简易模式** | `getArmorLevel(slot, ctx)` | 离散等级 → 两级递进伤害（65%/100%） | 基础护甲、快速原型         |
| **精密模式** | 覆写全部管线方法                   | 精确 float × 全自定义逻辑       | 爆反、间隙装甲、角度效应、跳弹判定 |

精密模式下护甲物品可按槽位覆写管线的每一步——与 `BFHurtTarget` 拥有同等的深度定制能力，只是操作粒度下沉到了装备槽位。

### 6.3 接口完整定义

```java
public interface TBArmorMaterial {

    // ========== 简易模式：只需实现此方法 ==========

    /**
     * 返回此护甲物品在指定槽位提供的护甲等级。
     *
     * @param slot 装备槽位（HEAD / CHEST / LEGS / FEET）
     * @param ctx  命中上下文（可用于读取武器元数据做精细判定）
     * @return 护甲等级，默认 UNARMORED_1（无防护）
     */
    default ArmorLevel getArmorLevel(EquipmentSlot slot, BFDamageContext ctx) {
        return ArmorLevel.UNARMORED_1;
    }

    /**
     * 返回此护甲物品在指定槽位的 RHA 等效厚度（mm）。
     * 默认委托给 getArmorLevel 的中位值。精密模组可覆写。
     */
    default float getRHA(EquipmentSlot slot, BFDamageContext ctx) {
        return getArmorLevel(slot, ctx).medianRha();
    }

    // ========== 穿甲判定管线（精密模式覆写） ==========

    /**
     * 修正穿深（此槽位护甲的减效逻辑）。
     * <p>
     * 默认直接返回 ctx.penetration()——不做减效。
     * 高级护甲可覆写以实现：
     * <ul>
     *   <li>爆反拦截（ERA）：仅对化学能弹头生效，减去固定的等效厚度</li>
     *   <li>间隙衰减：穿深随间隙距离递减</li>
     *   <li>跳弹角度：入射角过大时大幅缩减有效穿深</li>
     * </ul>
     *
     * @param slot 装备槽位
     * @param ctx  命中上下文
     * @return 修正后的有效穿深
     */
    default float modifyPenetration(EquipmentSlot slot, BFDamageContext ctx) {
        return ctx.penetration();
    }

    /**
     * 解析此槽位护甲的最终穿甲结果（含跳弹判定）。
     * <p>
     * 默认委托给 isArmorPenetrated，返回 PENETRATED 或 BLOCKED。
     * 需要跳弹判定的护甲应覆写此方法——
     * 在入射角过大时返回 RICOCHET。
     *
     * @param slot 装备槽位
     * @param ctx  命中上下文
     * @return 穿甲结果（PENETRATED / BLOCKED / RICOCHET，三者互斥）
     */
    default PenetrationResult resolvePenetration(EquipmentSlot slot, BFDamageContext ctx) {
        return isArmorPenetrated(slot, ctx)
            ? PenetrationResult.PENETRATED
            : PenetrationResult.BLOCKED;
    }

    /**
     * 根据穿甲结果计算此槽位护甲的最终伤害量。
     * <p>
     * 默认分三级（基于离散等级）：
     * <ul>
     *   <li>PENETRATED + 同级击穿（刚好击穿）：标称伤害 × 65%</li>
     *   <li>PENETRATED + 越级击穿：标称伤害 × 100%</li>
     *   <li>BLOCKED / RICOCHET：0</li>
     * </ul>
     * <p>
     * 需要非零未击穿伤害（如钝伤、破片）、跳弹转贯穿加成的模组应覆写此方法。
     *
     * @param slot   装备槽位
     * @param ctx    命中上下文
     * @param result 由 resolvePenetration 返回的穿甲结果
     * @return 最终伤害量
     */
    default float calculateFinalDamage(EquipmentSlot slot, BFDamageContext ctx,
                                        PenetrationResult result) {
        if (result != PenetrationResult.PENETRATED) return 0f;
        ArmorLevel penLevel = ctx.getPenetrationLevel();
        ArmorLevel armorLevel = getArmorLevel(slot, ctx);
        if (penLevel == armorLevel) return ctx.baseDamage() * 0.65f;
        return ctx.baseDamage();
    }

    /**
     * 判断此槽位护甲是否被击穿（纯击穿判定，不含跳弹）。
     * <p>
     * 默认基于离散等级比较（等于算击穿）。精密模组可覆写为精确 float 比较。
     *
     * @param slot 装备槽位
     * @param ctx  命中上下文
     * @return true 表示穿深足以击穿此槽位护甲
     */
    default boolean isArmorPenetrated(EquipmentSlot slot, BFDamageContext ctx) {
        return ctx.getPenetrationLevel().canDefeat(getArmorLevel(slot, ctx));
    }

    // ========== 命中槽位映射（可选覆写） ==========

    /**
     * 根据命中上下文确定此护甲物品对应的装备槽位。
     * <p>
     * 默认按命中点高度占比划分：头部 >85%，躯干 55%~85%，腿部 35%~55%，脚部 <35%。
     * 命中点无效时返回 null。
     * <p>
     * 需要自定义映射的护甲可覆写——例如：
     * <ul>
     *   <li>全覆盖头盔：将所有头部高度命中也纳入 HEAD 槽位，并忽略入射方向</li>
     *   <li>盾牌物品：将正前方所有命中纳入持有手的盾牌槽位</li>
     *   <li>坐骑装甲：根据骑乘实体的包围盒重定义命中区域</li>
     * </ul>
     *
     * @param wearer 穿戴此护甲的实体
     * @param ctx    命中上下文
     * @return 对应装备槽位；命中点无效或此物品不应处理时返回 null
     */
    @Nullable
    default EquipmentSlot mapHitToSlot(LivingEntity wearer, BFDamageContext ctx) {
        Vec3 hitPoint = ctx.hitPoint();
        if (hitPoint == null || hitPoint.equals(Vec3.ZERO)) return null;
        Vec3 localHit = hitPoint.subtract(wearer.position());
        double heightFrac = localHit.y / wearer.getBbHeight();
        if (heightFrac > 0.85) return EquipmentSlot.HEAD;
        if (heightFrac > 0.55) return EquipmentSlot.CHEST;
        if (heightFrac > 0.35) return EquipmentSlot.LEGS;
        return EquipmentSlot.FEET;
    }
}
```

### 6.4 管线委派链

当适配器调用 `BFHurtTarget` 的某方法时，委派路径为：

```
adapter.resolvePenetration(ctx)
  → adapter.mapHitToSlot(ctx)
      → 遍历 ARMOR_SLOTS，调用每件护甲物品的 mapHitToSlot(wearer, ctx)
      → 第一件返回非 null 的物品胜出
  → 若确定槽位且该槽位有 TBArmorMaterial：
      → mat.resolvePenetration(slot, ctx)   ← 按槽位委托
  → 若未确定槽位（无命中点）：
      → 取所有 TBArmorMaterial 槽位中 getArmorLevel 最高者
      → mat.resolvePenetration(bestSlot, ctx)
  → 若全身无 TBArmorMaterial（不应发生，进入此分支前 hasTBArmor 已检查）：
      → 走 BFHurtTarget 默认实现（UNARMORED_1，等效无防护）

adapter.modifyPenetration(ctx)
  → 同上槽位确定 → mat.modifyPenetration(slot, ctx)
  → 未确定 → 取最高等级槽位 → mat.modifyPenetration(bestSlot, ctx)

adapter.calculateFinalDamage(ctx, result)
  → 同上槽位确定 → mat.calculateFinalDamage(slot, ctx, result)
  → 未确定 → 取最高等级槽位 → mat.calculateFinalDamage(bestSlot, ctx, result)
```

**关键设计**：适配器不依赖 `BFHurtTarget` 的默认实现做穿甲判定——每一步都委托给护甲物品，确保护甲模组拥有与 `BFHurtTarget` 实现者同等的定制权限。

### 6.5 使用示例

**简易模式（约 5 行代码）**——只覆写 `getArmorLevel`：

```java
public class HeavyChestplate extends ChestplateItem implements TBArmorMaterial {

    @Override
    public ArmorLevel getArmorLevel(EquipmentSlot slot, BFDamageContext ctx) {
        if (slot == EquipmentSlot.CHEST) {
            return ArmorLevel.HEAVY;  // 躯干：20~40mm 防护
        }
        return ArmorLevel.UNARMORED_1;  // 其他槽位不由此物品保护
    }
}
```

**精密模式（含爆反拦截 + 跳弹判定）**——覆写全部管线方法：

```java
public class ERAHeavyChestplate extends ChestplateItem implements TBArmorMaterial {

    @Override
    public ArmorLevel getArmorLevel(EquipmentSlot slot, BFDamageContext ctx) {
        return slot == EquipmentSlot.CHEST ? ArmorLevel.SUPER_HEAVY_4 : ArmorLevel.UNARMORED_1;
    }

    @Override
    public float getRHA(EquipmentSlot slot, BFDamageContext ctx) {
        return slot == EquipmentSlot.CHEST ? 350f : 0f;  // 基甲 350mm + 爆反 150mm
    }

    @Override
    public float modifyPenetration(EquipmentSlot slot, BFDamageContext ctx) {
        float pen = ctx.penetration();
        BFDamageHandler handler = ctx.getHandler();
        if (handler instanceof ChemicalEnergyWarhead) {
            pen -= 150f;  // 爆反对化学能弹头削减 150mm 等效穿深
        }
        // 角度效应：射入角 60° 以上认为跳弹（实际减效在此，resolvePenetration 仅判断是否跳过极限）
        float angle = angleBetweenDeg(ctx.hitVelocity(), ctx.hitNormal());
        if (angle > 60f) pen *= (70f - angle) / 10f;  // 60°~70° 间穿深快速衰减
        return Math.max(pen, 0f);
    }

    @Override
    public PenetrationResult resolvePenetration(EquipmentSlot slot, BFDamageContext ctx) {
        float angle = angleBetweenDeg(ctx.hitVelocity(), ctx.hitNormal());
        if (angle > 75f) return PenetrationResult.RICOCHET;  // 75° 以上强制跳弹
        float pen = modifyPenetration(slot, ctx);
        float rha = getRHA(slot, ctx);
        return pen >= rha ? PenetrationResult.PENETRATED : PenetrationResult.BLOCKED;
    }

    @Override
    public float calculateFinalDamage(EquipmentSlot slot, BFDamageContext ctx,
                                       PenetrationResult result) {
        return switch (result) {
            case RICOCHET -> ctx.baseDamage() * 0.05f;   // 跳弹仍有 5% 钝伤
            case BLOCKED -> ctx.baseDamage() * 0.15f;    // 未击穿 15% 钝伤
            case PENETRATED -> ctx.baseDamage();          // 击穿全伤害（已在 modifyPenetration 中扣除爆反）
        };
    }
}
```

### 6.6 createContextFromVanilla：协议外伤害的接管控制

`BFArmorMaterial` 提供 `createContextFromVanilla(DamageSource, float)` 方法，决定哪些原版伤害应被拦截转为协议伤害、哪些放行原版。

默认实现始终返回有效上下文（穿深 = 原版伤害量 / 2），意味着**所有原版伤害都会被拦截并进入穿甲管线**。护甲物品覆写此方法后按需过滤：

```java
@Override
@Nullable
public BFDamageContext createContextFromVanilla(DamageSource source, float amount) {
    // 魔法、虚空、溺水等不应被钢板阻挡，放行原版
    if (source.is(DamageTypes.MAGIC)
        || source.is(DamageTypes.OUT_OF_WORLD)) {
        return null;
    }
    // 物理攻击走穿甲判定
    return BFDamageContext.builder()
        .source(source)
        .baseDamage(amount)
        .penetration(amount / 2f)
        .build();
}
```

适配器在调用 `createContextFromVanilla` 时遍历所有护甲槽位：任一护甲物品返回非 null 时整次伤害被接管；所有护甲物品均返回 null 时才退回原版流程。这意味着如果你同时穿戴了拦截物理伤害的胸甲和放行魔法伤害的头盔，一次魔法攻击会因胸甲的 `createContextFromVanilla` 返回 null 且头盔也返回 null 而走原版。

## 七、TBArmorAdapter —— 护甲适配器

`TBArmorAdapter` 位于 `internal/` 包，不是公开 API。它负责将穿戴了 `TBArmorMaterial` 护甲的 `LivingEntity` 包裹为 `BFHurtTarget` 实现，按管线的每一步逐方法委托给护甲物品。

### 7.1 核心职责

| 职责                  | 说明                                                                                 |
| ------------------- | ---------------------------------------------------------------------------------- |
| **实现 BFHurtTarget** | 逐方法委托给护甲物品的 `TBArmorMaterial` 管线方法                                                 |
| **槽位映射**            | 遍历各槽位护甲物品的 `mapHitToSlot()`，第一个返回非 null 者胜出                                        |
| **兜底策略**            | 无命中点时，RHA 取四槽位加权平均（胸甲35%、头盔30%、护腿25%、靴子10%；无协议护甲的槽位贡献0）。等级由加权RHA映射。其余步骤仍委托最高等级槽位的护甲物品 |
| **原版伤害接管**          | `createContextFromVanilla` 遍历所有槽位，委托给每件护甲物品的同名方法。任一返回非 null 则接管，全部返回 null 则放行原版    |
| **重入安全**            | `hurt()` 直接委托 `entity.hurt()`——栈顶 target 与 entity 为同一引用，`hasContextFor` 返回 true 放行 |
| **回调兼容**            | `getBFEntity()` 返回被包裹的实体，handler 通过 `target.getBFEntity()` 安全访问                    |

### 7.2 BFHurtTarget 管线方法的完整委派

适配器对 `BFHurtTarget` 所有管线方法的实现均委托给护甲物品：

```java
final class TBArmorAdapter implements BFHurtTarget {

    private final LivingEntity entity;
    // slot → ItemStack 缓存（由 mapHitToSlot 填充后供后续方法复用）
    private EquipmentSlot resolvedSlot;
    private TBArmorMaterial resolvedMaterial;

    // ===== 槽位映射（shared） =====

    /**
     * 遍历 ARMOR_SLOTS，逐一调用护甲物品的 mapHitToSlot(wearer, ctx)。
     * 第一件返回非 null 的物品胜出。无命中点时返回 null。
     */
    private boolean resolveTarget(BFDamageContext ctx) {
        for (EquipmentSlot slot : ARMOR_SLOTS) {
            ItemStack armor = entity.getItemBySlot(slot);
            if (armor.getItem() instanceof TBArmorMaterial mat) {
                EquipmentSlot mapped = mat.mapHitToSlot(entity, ctx);
                if (mapped == slot) {
                    this.resolvedSlot = slot;
                    this.resolvedMaterial = mat;
                    return true;
                }
            }
        }
        return false;
    }

    // ===== 兜底：无命中点时加权平均 RHA =====

    private void resolveBestSlot(BFDamageContext ctx) {
        ArmorLevel best = ArmorLevel.UNARMORED_1;
        EquipmentSlot bestSlot = null;
        TBArmorMaterial bestMat = null;

        float weightedRha = 0f;
        float totalWeight = 0f;

        for (int i = 0; i < ARMOR_SLOTS.length; i++) {
            EquipmentSlot slot = ARMOR_SLOTS[i];
            ItemStack armor = entity.getItemBySlot(slot);
            if (armor.getItem() instanceof TBArmorMaterial mat) {
                ArmorLevel level = mat.getArmorLevel(slot, ctx);
                if (level.ordinal() > best.ordinal()) {
                    best = level;
                    bestSlot = slot;
                    bestMat = mat;
                }
                weightedRha += mat.getRHA(slot, ctx) * SLOT_WEIGHTS[i];
                totalWeight += SLOT_WEIGHTS[i];
            }
        }

        this.resolvedSlot = bestSlot;
        this.resolvedMaterial = bestMat;
        this.fallbackRha = totalWeight > 0f ? weightedRha / totalWeight : 0f;
    }

    // ===== 管线方法（逐方法委托给 resolvedMaterial） =====

    /** 确保槽位已解析（惰性初始化，不假设调用顺序） */
    private void ensureResolved(BFDamageContext ctx) {
        if (resolvedMaterial == null && !resolveTarget(ctx)) {
            resolveBestSlot(ctx);
        }
    }

    @Override
    public ArmorLevel getArmorLevel(BFDamageContext ctx) {
        ensureResolved(ctx);
        if (!exactMatch) {
            return ArmorLevel.fromRha(fallbackRha);
        }
        if (resolvedMaterial != null) {
            return resolvedMaterial.getArmorLevel(resolvedSlot, ctx);
        }
        return ArmorLevel.UNARMORED_1;
    }

    @Override
    public float getRHA(BFDamageContext ctx) {
        ensureResolved(ctx);
        if (!exactMatch) {
            return fallbackRha;
        }
        if (resolvedMaterial != null) {
            return resolvedMaterial.getRHA(resolvedSlot, ctx);
        }
        return 0f;
    }

    @Override
    public float modifyPenetration(BFDamageContext ctx) {
        ensureResolved(ctx);
        if (resolvedMaterial != null) {
            return resolvedMaterial.modifyPenetration(resolvedSlot, ctx);
        }
        return ctx.penetration();
    }

    @Override
    public PenetrationResult resolvePenetration(BFDamageContext ctx) {
        ensureResolved(ctx);
        if (resolvedMaterial != null) {
            return resolvedMaterial.resolvePenetration(resolvedSlot, ctx);
        }
        return BFHurtTarget.super.resolvePenetration(ctx);
    }

    @Override
    public float calculateFinalDamage(BFDamageContext ctx, PenetrationResult result) {
        ensureResolved(ctx);
        if (resolvedMaterial != null) {
            return resolvedMaterial.calculateFinalDamage(resolvedSlot, ctx, result);
        }
        return BFHurtTarget.super.calculateFinalDamage(ctx, result);
    }

    @Override
    public boolean hurt(DamageSource source, float amount) {
        return entity.hurt(source, amount);  // 直接委托原版，栈顶引用匹配保证重入安全
    }

    @Override
    @Nullable
    public Entity getBFEntity() {
        return entity;
    }

    @Override
    @Nullable
    public BFDamageContext createContextFromVanilla(DamageSource source, float amount) {
        // 遍历所有护甲槽位，任一护甲物品愿意接管即可
        for (EquipmentSlot slot : ARMOR_SLOTS) {
            if (entity.getItemBySlot(slot).getItem() instanceof BFArmorMaterial mat) {
                BFDamageContext ctx = mat.createContextFromVanilla(source, amount);
                if (ctx != null) return ctx;
            }
        }
        return null;
    }
}
```

### 7.3 委派缓存策略

`ensureResolved(ctx)` 方法实现惰性初始化——当任一管线方法首次被调用时自动解析槽位并缓存。`resolveTarget` 调用各护甲物品的 `mapHitToSlot(wearer, ctx)`（默认按高度占比映射），第一个返回非 null 者胜出——此模式称为**精确匹配**，适配器逐方法委托给命中槽位的护甲物品。无命中点时退回到 `resolveBestSlot`：取四槽位 RHA 的加权平均（胸甲35%、头盔30%、护腿25%、靴子10%），未穿戴协议护甲的槽位贡献0；同时记录最高等级槽位供 `modifyPenetration`、`resolvePenetration`、`calculateFinalDamage` 等其余管线步骤委托。一旦解析完成，整个管线周期内缓存复用——因为 `ctx` 和 `entity.position()` 在同一调用链内不可变。

**材料内部调用不经过适配器**：当 `TBArmorMaterial.resolvePenetration(slot, ctx)` 内部调用 `this.modifyPenetration(slot, ctx)` 或 `this.getRHA(slot, ctx)` 时，调用的是材料自身的 default 方法，不走适配器。适配器的 `getRHA`/`modifyPenetration` 只在 `BFHurtTarget.super.resolvePenetration` 回退路径中才会被调用——此时 `getArmorLevel` 已在前一步完成了缓存填充。

### 7.4 静态工具方法

`TBArmorAdapter.hasTBArmor(LivingEntity)` 遍历四个护甲槽位（HEAD/CHEST/LEGS/FEET），检查是否有任何一件物品实现了 `TBArmorMaterial`。此方法被 `BFDamageApi` 和 `BFHurtInterceptor` 共用。

### 7.5 重入安全保证

适配器不创建新的上下文层级。`BFDamageApi.hurt()` 中 `push(target, ctx)` 的 target 是实体自身（不是适配器）。适配器的 `hurt()` 调用 `entity.hurt()` 时，Mixin 检查 `hasContextFor(entity)`——栈顶 target 与 entity 为同一引用（`==`），返回 true 放行。不会产生无限递归。

**关键**：`BFDamageApi.hurt()` 传入的 target 参数直接作为 `push` 的第一个参数，适配器在此步骤之后才被创建，适配器自身不进入上下文栈。

## 八、BFHurtTarget —— 协议伤害目标接口

`BFHurtTarget` 是协议层的核心抽象：默认实现基于离散的 `ArmorLevel` 体系，简单模组只需实现 `getArmorLevel` 和 `hurt` 两个方法；需要精确数值判定的模组可覆写全部管线方法。

### 8.1 接口完整定义

```java
public interface BFHurtTarget {

    // ========== 简易模式：只需实现此方法 ==========

    /**
     * 返回此命中部位对应的离散护甲等级。
     * 简单模组只需实现此方法，默认的穿甲判定、伤害计算均基于此等级。
     */
    ArmorLevel getArmorLevel(BFDamageContext ctx);

    /**
     * 返回命中部位的 RHA 等效厚度（mm）。
     * 默认实现取 getArmorLevel 的中位值。精密模组应覆写。
     */
    default float getRHA(BFDamageContext ctx) {
        return getArmorLevel(ctx).medianRha();
    }

    // ========== 穿甲判定管线 ==========

    /**
     * 修正穿深。默认直接返回原始值。
     * 穿深的角度效应等应由武器侧在构造 BFDamageContext 前计算。
     * 此 hook 保留给爆反拦截、间隙衰减等护甲侧减效逻辑。
     */
    default float modifyPenetration(BFDamageContext ctx) {
        return ctx.penetration();
    }

    /**
     * 判断是否能够击穿装甲（纯击穿判定，不含跳弹）。
     * 默认基于离散等级比较（等于算击穿）。精密模组应覆写为精确 float 比较。
     */
    default boolean isArmorPenetrated(BFDamageContext ctx) {
        return ctx.getPenetrationLevel().canDefeat(getArmorLevel(ctx));
    }

    /**
     * 解析本次命中的最终穿甲结果。
     * <p>
     * 默认实现直接委托 {@link #isArmorPenetrated}，返回 PENETRATED 或 BLOCKED。
     * 需要跳弹判定的护甲模组应覆写此方法——
     * 在入射角过大时返回 RICOCHET，此时伤害流程可能被护甲侧完全跳过。
     * <p>
     * 此方法由 BFDamageApi 在管线中单次调用，其返回值作为
     * calculateFinalDamage 的入参和回调触发的唯一依据。
     *
     * @param ctx 命中上下文
     * @return 穿甲结果（PENETRATED / BLOCKED / RICOCHET，三者互斥）
     */
    default PenetrationResult resolvePenetration(BFDamageContext ctx) {
        return isArmorPenetrated(ctx) ? PenetrationResult.PENETRATED : PenetrationResult.BLOCKED;
    }

    /**
     * 根据穿甲结果计算最终伤害量。
     * <p>
     * 默认分三级（基于离散等级）：
     * <ul>
     *   <li>PENETRATED + 同级击穿（刚好击穿）：标称伤害 × 65%</li>
     *   <li>PENETRATED + 越级击穿：标称伤害 × 100%</li>
     *   <li>BLOCKED / RICOCHET：0</li>
     * </ul>
     * <p>
     * 需要非零未击穿伤害（如钝伤）、跳弹转贯穿、超匹配(碾压)加成的模组应覆写此方法。
     * 不是"未击穿 / 跳弹就不造成伤害"——护甲侧可在覆写中自由决定。
     *
     * @param ctx    命中上下文
     * @param result 由 resolvePenetration() 返回的穿甲结果
     * @return 最终伤害量
     */
    default float calculateFinalDamage(BFDamageContext ctx, PenetrationResult result) {
        if (result != PenetrationResult.PENETRATED) return 0f;
        if (ctx.getPenetrationLevel() == getArmorLevel(ctx)) return ctx.baseDamage() * 0.65f;
        return ctx.baseDamage();
    }

    // ========== 必须实现 ==========

    boolean hurt(DamageSource source, float amount);

    /**
     * 返回此协议伤害目标对应的实体。
     * <p>
     * 默认实现：若自身是 Entity 子类则返回 this，否则返回 null。
     * 适配器（如 TBArmorAdapter）应覆写此方法返回被包裹的实体。
     * <p>
     * 供 BFDamageHandler 回调中使用——武器模组可在回调中
     * 拿到被命中的实体以播放音效、粒子或触发额外逻辑。
     *
     * @return 目标对应的实体，可能为 null
     */
    @Nullable
    default Entity getBFEntity() {
        return this instanceof Entity e ? e : null;
    }

    @Nullable
    BFDamageContext createContextFromVanilla(DamageSource source, float amount);
}
```

### 8.2 简易模式 vs 精密模式

| 模式       | 需实现                                                   | 判定方式                    | 适用场景                  |
| -------- | ----------------------------------------------------- | ----------------------- | --------------------- |
| **简易模式** | `getArmorLevel` + `hurt` + `createContextFromVanilla` | 离散等级 → 两级递进伤害（65%/100%） | 简单护甲模组、HD2 风格         |
| **精密模式** | 覆写全部管线方法                                              | 精确 float → 毫米级判定        | Machine-Max 载具、WoT 风格 |

简易模式的等价流程：

```
ctx.getPenetrationLevel().canDefeat(target.getArmorLevel(ctx))
  → true且同级 → 65%伤害
  → true且越级 → 100%伤害
  → false     → 0
```

精密模式的覆写示例（Machine-Max SubPart、含跳弹判定）：

```java
@Override public float getRHA(BFDamageContext ctx) { return hitBox.getRHA(this); }
@Override public ArmorLevel getArmorLevel(BFDamageContext ctx) { return ArmorLevel.fromRha(getRHA(ctx)); }
@Override public float modifyPenetration(BFDamageContext ctx) { return hitBox.modifyPiercing(...); }
@Override public boolean isArmorPenetrated(BFDamageContext ctx) { return modifyPenetration(ctx) > getRHA(ctx); }
@Override public PenetrationResult resolvePenetration(BFDamageContext ctx) {
    float angle = angleBetween(ctx.hitVelocity(), ctx.hitNormal());
    if (angle > 70f) return PenetrationResult.RICOCHET;  // 判定为跳弹
    return super.resolvePenetration(ctx);                  // 委托默认逻辑
}
@Override public float calculateFinalDamage(BFDamageContext ctx, PenetrationResult result) {
    return switch (result) {
        case RICOCHET -> 0f;              // 跳弹不造成伤害
        case BLOCKED -> ctx.baseDamage() * 0.1f;  // 未击穿仍有 10% 钝伤
        case PENETRATED -> /* 自定义逻辑 */;
    };
}
```

### 8.3 穿甲判定调用顺序

当 `BFDamageApi.hurt(target, ctx)` 被调用时，协议按优先级匹配处理路径：

```
target 同时是 BFHurtTarget + LivingEntity + 穿戴 TBArmorMaterial?
  → 是：走双层串联管线——护甲层先处理，本体层后处理（见下方"八步复合管线"）
  → 否：target instanceof BFHurtTarget?
    → 是：走标准管线（见下方标准五步）
    → 否：target 是 LivingEntity 且穿戴 TBArmorMaterial 护甲？
      → 是：通过 TBArmorAdapter 走管线（适配器模式）
      → 否：target 是普通 Entity？
        → 是：直接调用 entity.hurt(source, baseDamage)（原版回退）
        → 否：返回 0
```

**复合管线（BFHurtTarget + BFArmorMaterial，八步）：**

```
第一层：护甲拦截
  1. residualPen = adapter.modifyPenetration(ctx)   ← 爆反拦截、间隙衰减
  2. armorResult = adapter.resolvePenetration(ctx)  ← 跳弹判定
  3. residualDmg = adapter.calculateFinalDamage(ctx, armorResult) ← 穿过护甲的残余伤害

  3b. adapter.armorAfterHurt(ctx, armorResult, residualDmg)  ← 护甲后效
  3c. 触发护甲层回调（before* + on*）——告知武器侧护甲层结果

  childCtx = ctx.childContext(residualDmg,
              (armorResult == PENETRATED) ? residualPen : 0f)

第二层：本体判定
  4. entityResult = bfTarget.resolvePenetration(childCtx)    ← 本体判定（穿深可能为 0）
  5. finalDmg = bfTarget.calculateFinalDamage(childCtx, entityResult) ← 含钝伤
  5b. 触发本体层伤害前回调（before*）
  6. bfTarget.hurt(source, finalDmg)                          ← 实际扣血
  6b. bfTarget.afterHurt(childCtx, entityResult, finalDmg)
  7. 触发本体层伤害后回调（on*）
  8. 返回 dealt
```

**关键设计：无论护甲是否击穿，本体始终执行完整管线。** 区别仅在 childCtx 的穿深：

| 护甲结果       | childCtx.penetration | 本体收到      | childCtx.baseDamage |
| ---------- | -------------------- | --------- | ------------------- |
| PENETRATED | residualPen（减效后）     | 残余弹头的穿甲能力 | residualDmg         |
| BLOCKED    | 0                    | 仅钝伤，穿深=0  | residualDmg         |
| RICOCHET   | 0                    | 仅钝伤       | residualDmg         |

标准五步管线（纯 BFHurtTarget，无护甲物品）：

```
1. float rha = target.getRHA(ctx)              ← 简易模式：取 medianRha()
2. float modifiedPen = target.modifyPenetration(ctx) ← 简易模式：= ctx.penetration()
3. PenetrationResult result = target.resolvePenetration(ctx)   ← 简易模式：离散 canDefeat
4. float finalDmg = target.calculateFinalDamage(ctx, result) ← 简易模式：0 / 65% / 100%
4b. 触发伤害前回调（before*）
5. target.hurt(source, finalDmg)
5b. target.afterHurt(ctx, result, finalDmg)
6. 触发伤害后回调（on*）
```

适配器模式（纯 BFArmorMaterial 护甲，无 BFHurtTarget）走相同的五步，但各步骤委托给护甲物品的 `BFArmorMaterial` 方法查询。

### 8.4 对非 BFHurtTarget 实体的处理

- **穿戴 TBArmorMaterial 护甲的 LivingEntity**：通过 `TBArmorAdapter` 走完整穿甲判定。穿深与护甲等级比较决定击穿/未击穿。原版护甲属性（ARMOR / ARMOR\_TOUGHNESS）的减免可在协议伤害之上叠加。
- **普通 LivingEntity（无协议护甲）**：直接调用 `living.hurt(ctx.source(), ctx.baseDamage())`，视作**完全击穿**（无护甲等级，100% 伤害）。穿深字段在此时不起作用。
- **普通 Entity（非 Living、非 BFHurtTarget）**：同上，直接走原版。

## 九、PenetrationResult 与 BFDamageHandler —— 管线结果反馈

### 9.1 PenetrationResult —— 穿甲判定结果枚举

```java
/**
 * 穿甲判定的一次性结果。
 * <p>
 * PENETRATED / BLOCKED / RICOCHET 三者互斥，是命中的主结果。
 * 由 BFHurtTarget.resolvePenetration() 返回，
 * 作为 calculateFinalDamage 的入参和回调触发的唯一依据。
 * <p>
 * 超匹配(碾压)与破片不在此枚举中表达——它们由
 * BFDamageHandler.isOvermatch() / isSpall() 在回调阶段动态判定。
 */
public enum PenetrationResult {
    PENETRATED,   // 击穿（穿深足以穿透装甲）
    BLOCKED,      // 未击穿（含钝伤等，伤害量由护甲侧自由决定）
    RICOCHET      // 跳弹（穿深不足 + 入射角过大）
}
```

由 `BFHurtTarget.resolvePenetration()` 返回，作为 `calculateFinalDamage` 的入参和 `BFDamageHandler` 回调触发的唯一依据。护甲模组覆写此方法可自然地表达跳弹，不再需要手动设置 `extensions.set(RICOCHET, true)`。

`calculateFinalDamage` 接收此枚举后可自由决定伤害——BLOCKED 不一定是 0（钝伤），RICOCHET 也可能产生非零伤害（跳弹转贯穿）。

### 9.2 BFDamageHandler —— 伤害发起方回调接口

```java
/**
 * 协议伤害发起方的处理接口。
 * <p>
 * 由武器/弹头模组实现，在构造 BFDamageContext 时注入。
 * 职责：
 * <ul>
 *   <li>接收管线执行前/后的事件回调（双阶段模型）</li>
 *   <li>通过 isOvermatch / isSpall 的默认实现让协议层自动判定
 *       超匹配(碾压)与破片条件，实现者无需手动设置标记</li>
 *   <li>向护甲侧提供伤害来源的元信息（ctx.getHandler() 查询）</li>
 * </ul>
 */
public interface BFDamageHandler {

    // ========== 伤害前回调（穿甲判定后、hurt() 前） ==========

    default void beforePenetrated(BFHurtTarget target, BFDamageContext ctx) {}
    default void beforeBlocked(BFHurtTarget target, BFDamageContext ctx) {}
    default void beforeRicochet(BFHurtTarget target, BFDamageContext ctx) {}
    default void beforeOvermatch(BFHurtTarget target, BFDamageContext ctx) {}
    default void beforeSpall(BFHurtTarget target, BFDamageContext ctx) {}
    /** 普通实体命中前回调 */
    default void beforeNormalEntityHit(Entity entity, BFDamageContext ctx,
                                       float baseDamage) {}

    // ========== 伤害后回调（hurt() 后） ==========

    default void onPenetrated(BFHurtTarget target, BFDamageContext ctx) {}
    default void onBlocked(BFHurtTarget target, BFDamageContext ctx) {}
    default void onRicochet(BFHurtTarget target, BFDamageContext ctx) {}
    default void onOvermatch(BFHurtTarget target, BFDamageContext ctx) {}
    default void onSpall(BFHurtTarget target, BFDamageContext ctx) {}
    /** 普通实体命中后回调 */
    default void onNormalEntityHit(Entity entity, BFDamageContext ctx,
                                   float baseDamage, boolean success) {}

    // ========== 判定方法（默认实现，可覆写） ==========

    /** 判断是否为超匹配(碾压)（穿深远超装甲厚度）。默认：击穿且穿深 > RHA × 1.5 */
    default boolean isOvermatch(BFHurtTarget target, BFDamageContext ctx,
                                 PenetrationResult result) { ... }

    /** 判断是否产生破片。默认：未击穿，或击穿但非超匹配 */
    default boolean isSpall(BFHurtTarget target, BFDamageContext ctx,
                             PenetrationResult result) { ... }

    // ========== 便捷方法 ==========

    /** 发起协议伤害，并将自身注入上下文以便接收回调 */
    default float dealDamage(Object target, BFDamageContext ctx) {
        return BFDamageApi.hurt(target, ctx.withHandler(this));
    }
}
```

### 9.3 回调双阶段触发时序

自 v1.0.0.alpha.9 起，回调分为伤害前（`before*`）和伤害后（`on*`）两个阶段，在 `hurt()` 调用前后分别触发：

```
resolvePenetration(ctx) → result
    ↓
calculateFinalDamage(ctx, result) → finalDmg
    ↓
triggerBeforeCallbacks(handler, target, ctx, result):   // ★ 伤害前阶段
    ↓
target.hurt(source, finalDmg)
    ↓
triggerCallbacks(handler, target, ctx, result):         // ★ 伤害后阶段
```

每阶段内部按 `PenetrationResult` 分发主回调，再根据 `isOvermatch` / `isSpall` 追加派生回调：

```
PENETRATED:
  beforePenetrated() / onPenetrated()
  → isOvermatch()==true  → beforeOvermatch() + onOvermatch()
  → isSpall()==true      → beforeSpall() + onSpall()

BLOCKED:
  beforeBlocked() / onBlocked()
  → isSpall()==true      → beforeSpall() + onSpall()

RICOCHET:
  beforeRicochet() / onRicochet()
```

对于分支0（复合目标），护甲层和本体层各触发两轮（伤害前+伤害后），共计四轮回调。第一轮使用 `adapter` 和原始 `ctx`，第二轮使用 `bfTarget` 和 `childCtx`。

### 9.4 两种使用路径

**路径一：简单伤害（无回调）**——直接使用 `BFDamageApi`：

```java
BFDamageContext ctx = BFDamageContext.builder()
    .source(src).baseDamage(35f).penetration(120f).build();
float dealt = BFDamageApi.hurt(target, ctx);
```

**路径二：带回调**——实现 `BFDamageHandler`，通过 `dealDamage` 自动注入：

```java
public class MyWeapon implements BFDamageHandler {
    @Override public void onRicochet(BFHurtTarget t, BFDamageContext c) {
        playRicochetSound(c.hitPoint());
    }
    @Override public void onPenetrated(BFHurtTarget t, BFDamageContext c) {
        spawnPenetrationEffects(c.hitPoint());
    }

    void fire(Entity target) {
        BFDamageContext ctx = BFDamageContext.builder()
            .source(src).baseDamage(35f).penetration(120f).build();
        float dealt = this.dealDamage(target, ctx);  // 自身注入 ctx
    }
}
```

**护甲侧利用 handler 做精细判定：**

```java
@Override
public float getRHA(BFDamageContext ctx) {
    BFDamageHandler handler = ctx.getHandler();
    if (handler instanceof ChemicalEnergyWarhead) {
        return this.eraEffectiveRha;  // 爆反对化学能弹头有效
    }
    return this.baseRha;
}
```

## 十、BFDamageApi —— 核心调度器与上下文栈

### 10.1 上下文栈的结构

上下文栈由 `internal.TBContextStack` 类管理，它是一个包可见的单例，封装了 `ThreadLocal<Deque<StackEntry>>`。`StackEntry` 是其内部的 `private record`，绑定 target 与 context：

```java
// TBContextStack 内部
private record StackEntry(Object target, BFDamageContext ctx) {}
```

上下文栈的元素是 **`(target, context)`** **对**，解决了重入判定的精准性问题。

### 10.2 为什么需要 target-context 对

单纯检查"栈是否为空"不足以处理嵌套伤害中的跨目标场景。典型反例：**荆棘附魔**。

```
子弹命中穿甲玩家 → BFDamageApi.hurt(player, ctx1)
  push(player, ctx1)
  
  player.hurt() 
    → 原版管线 → 荆棘触发
    → attacker.hurt(thornsSource, thornDamage)  ← 对另一个实体的伤害!
    
如果 hasContext() 只检查栈是否为空:
  → stack 非空 → "有上下文" → 不拦截 → 荆棘绕过协议 ✗

使用 hasContextFor(attacker):
  → stack.peek().target == player ≠ attacker → 拦截 ✓
```

**栈 target 的选取规则**：`BFDamageApi.hurt()` 在 `push` 之前会检查 target 是否为 `BFHurtTarget` 且 `getBFEntity() != null`。若是，则以 `getBFEntity()` 的返回值而非 target 本身作为栈 target。这一规则确保：

- 实体直接实现 `BFHurtTarget` → `getBFEntity()` 返回 `this` → 栈 target = 实体 ✅
- 非实体包装器实现 `BFHurtTarget` → `getBFEntity()` 返回被包裹实体 → 栈 target = 实体 ✅
- 非实体包装器，`getBFEntity()` 返回 null → 栈 target = 包装器自身 ✅

这样，任何委托到 `entity.hurt()` 的 `BFHurtTarget` 实现都能让 mixin 的 `hasContextFor(entity)` 正确匹配，不会重新进入协议管线。

### 10.3 BFDamageApi 的内部实现

```java
public static float hurt(Object target, BFDamageContext ctx) {
    BFDamageHandler handler = ctx.getHandler();
    // 如果目标是 BFHurtTarget 且持有实体引用，用该实体做栈 target
    // 以确保委托到 entity.hurt() 时 hasContextFor 能正确放行
    Object stackTarget = target;
    if (target instanceof BFHurtTarget tb && tb.getBFEntity() != null) {
        stackTarget = tb.getBFEntity();
    }
    TBContextStack.INSTANCE.push(stackTarget, ctx);
    try {
        // ================================================================
        // 分支0：复合目标 — BFHurtTarget + TBArmorMaterial 护甲 (type 4)
        //   护甲层先拦截 → childCtx → 本体层始终执行完整管线
        // ================================================================
        if (target instanceof LivingEntity living
                && target instanceof BFHurtTarget tb
                && TBArmorAdapter.hasTBArmor(living)) {

            // 第一层：护甲管线
            TBArmorAdapter adapter = new TBArmorAdapter(living);
            float residualPen = adapter.modifyPenetration(ctx);
            PenetrationResult armorResult = adapter.resolvePenetration(ctx);
            float residualDmg = adapter.calculateFinalDamage(ctx, armorResult);

            // 构造子上下文——未击穿/跳弹时穿深传 0 表示仅钝伤
            float childPen = armorResult == PenetrationResult.PENETRATED
                    ? residualPen : 0f;
            BFDamageContext childCtx = ctx.childContext(residualDmg, childPen);

            // 护甲层回调
            if (handler != null) {
                triggerBeforeCallbacks(handler, adapter, ctx, armorResult);
                triggerCallbacks(handler, adapter, ctx, armorResult);
            }

            // 第二层：本体始终执行完整管线
            PenetrationResult entityResult = tb.resolvePenetration(childCtx);
            float finalDmg = tb.calculateFinalDamage(childCtx, entityResult);
            // 本体伤害前回调
            if (handler != null) {
                triggerBeforeCallbacks(handler, tb, childCtx, entityResult);
            }
            boolean success = tb.hurt(ctx.source(), finalDmg);
            float dealt = success ? finalDmg : 0f;
            tb.afterHurt(childCtx, entityResult, finalDmg);

            // 本体伤害后回调
            if (handler != null) {
                triggerCallbacks(handler, tb, childCtx, entityResult);
            }
            return dealt;
        }

        // 分支1：BFHurtTarget（实体或独立对象直接声明协议感知）
        if (target instanceof BFHurtTarget tb) {
            PenetrationResult result = tb.resolvePenetration(ctx);
            float finalDmg = tb.calculateFinalDamage(ctx, result);
            if (handler != null) {
                triggerBeforeCallbacks(handler, tb, ctx, result);
            }
            boolean success = tb.hurt(ctx.source(), finalDmg);
            float dealt = success ? finalDmg : 0f;
            tb.afterHurt(ctx, result, finalDmg);

            if (handler != null) {
                triggerCallbacks(handler, tb, ctx, result);
            }
            return dealt;
        }
        // 分支2：LivingEntity 穿戴了 BFArmorMaterial 护甲 → 适配器模式
        if (target instanceof LivingEntity living && BFArmorAdapter.hasBFArmor(living)) {
            BFArmorAdapter adapter = new BFArmorAdapter(living);
            PenetrationResult result = adapter.resolvePenetration(ctx);
            float finalDmg = adapter.calculateFinalDamage(ctx, result);
            adapter.armorAfterHurt(ctx, result, finalDmg);
            if (handler != null) {
                triggerBeforeCallbacks(handler, adapter, ctx, result);
            }
            boolean success = adapter.hurt(ctx.source(), finalDmg);
            float dealt = success ? finalDmg : 0f;

            if (handler != null) {
                triggerCallbacks(handler, adapter, ctx, result);
            }
            return dealt;
        }
        // 分支3：普通 Entity → 原版回退
        if (target instanceof Entity entity) {
            if (handler != null) {
                handler.beforeNormalEntityHit(entity, ctx, ctx.baseDamage());
            }
            boolean success = entity.hurt(ctx.source(), ctx.baseDamage());
            if (handler != null) {
                handler.onNormalEntityHit(entity, ctx, ctx.baseDamage(), success);
            }
            return success ? ctx.baseDamage() : 0f;
        }
        return 0f;
    } finally {
        BFContextStack.INSTANCE.pop();
    }
}

private static void triggerBeforeCallbacks(BFDamageHandler handler, BFHurtTarget target,
                                            BFDamageContext ctx, PenetrationResult result) {
    switch (result) {
        case PENETRATED -> {
            handler.beforePenetrated(target, ctx);
            if (handler.isOvermatch(target, ctx, result)) {
                handler.beforeOvermatch(target, ctx);
            } else if (handler.isSpall(target, ctx, result)) {
                handler.beforeSpall(target, ctx);
            }
        }
        case BLOCKED -> {
            handler.beforeBlocked(target, ctx);
            if (handler.isSpall(target, ctx, result)) {
                handler.beforeSpall(target, ctx);
            }
        }
        case RICOCHET -> handler.beforeRicochet(target, ctx);
    }
}

private static void triggerCallbacks(BFDamageHandler handler, BFHurtTarget target,
                                      BFDamageContext ctx, PenetrationResult result) {
    switch (result) {
        case PENETRATED -> {
            handler.onPenetrated(target, ctx);
            if (handler.isOvermatch(target, ctx, result)) {
                handler.onOvermatch(target, ctx);
            } else if (handler.isSpall(target, ctx, result)) {
                handler.onSpall(target, ctx);
            }
        }
        case BLOCKED -> {
            handler.onBlocked(target, ctx);
            if (handler.isSpall(target, ctx, result)) {
                handler.onSpall(target, ctx);
            }
        }
        case RICOCHET -> handler.onRicochet(target, ctx);
    }
}
```

push/pop 包裹在 `try/finally` 中，确保异常也不会泄漏上下文栈。

## 十一、Mixin 注入策略

### 11.1 双注入方案

必须同时注入 `Entity#hurt` 和 `LivingEntity#hurt`。仅注入其一会有遗漏：

- 只注入 `LivingEntity#hurt`：非 LivingEntity 的 BFHurtTarget 被外部伤害时不触发拦截。
- 只注入 `Entity#hurt`：`LivingEntity#hurt` 是 `Entity#hurt` 的覆写，JVM 调用 `LivingEntity` 实例的 `hurt` 时实际执行的是 `LivingEntity#hurt` 方法体，不会经过 `Entity#hurt` 的注入点。

两个 Mixin 包含相同逻辑，不会重复触发——对于引用类型为 `LivingEntity` 的实例，调用 `hurt` 只会命中 `LivingEntity#hurt` 的注入点。

### 11.2 Mixin 拦截逻辑

```java
public static void intercept(Entity self, DamageSource source, float amount,
                             CallbackInfoReturnable<Boolean> cir) {
    // 情况1：已在此目标的协议管线内 → 放行
    if (BFDamageApi.hasContextFor(self)) return;

    // 情况2：实体自身是 BFHurtTarget → 接管
    if (self instanceof BFHurtTarget tb) {
        BFDamageContext ctx = tb.createContextFromVanilla(source, amount);
        if (ctx == null) return;

        float dealt = BFDamageApi.hurt(self, ctx);
        cir.setReturnValue(dealt > 0f);   // 只要 ctx != null 就是协议接管，
        return;                           // 必须 cancel 原版；返回值表示是否实际造成伤害
    }

    // 情况3：实体穿戴了 TBArmorMaterial 护甲 → 通过适配器接管
    if (self instanceof LivingEntity living && TBArmorAdapter.hasTBArmor(living)) {
        TBArmorAdapter adapter = new TBArmorAdapter(living);
        BFDamageContext ctx = adapter.createContextFromVanilla(source, amount);
        if (ctx == null) return;

        float dealt = BFDamageApi.hurt(self, ctx);
        cir.setReturnValue(dealt > 0f);
        return;  // 同情况2：ctx ≠ null 即接管，必须 cancel 原版
    }

    // 情况4：其他 → 放行原版流程
}
```

### 11.3 八种伤害路径总览

| # | 场景                                    | 行为                                                              | 递归风险 | 关键设计                                       |
| - | ------------------------------------- | --------------------------------------------------------------- | :--: | ------------------------------------------ |
| 1 | **协议内伤害命中** **`BFHurtTarget`**        | `push(target)` → 目标管线 → `target.hurt`                           |   无  | `hasContextFor(target)` 放行内部原版 hurt        |
| 2 | **协议内伤害命中穿装备实体**                      | `push(entity)` → adapter 管线 → `adapter.hurt → entity.hurt`      |   无  | 栈 target 必须是 entity，不能是 adapter            |
| 3 | **协议内伤害命中普通实体**                       | `push(entity)` → 原版 `entity.hurt(baseDamage)`                   |   无  | Mixin 看到同一 entity 的上下文放行                   |
| 4 | **协议内伤害命中复合目标（BFHurtTarget + 护甲）**    | `push(entity)` → 护甲层（adapter）→ childCtx → 本体层（bfTarget）→ `hurt` |   无  | 本体始终执行完整管线；childCtx 穿深=0 表示仅钝伤             |
| 5 | **协议外伤害命中** **`BFHurtTarget`，返回 ctx** | 转协议管线 → `cir.setReturnValue(dealt > 0f)` → 取消原版                 |   无  | ctx ≠ null 即接管，无论 dealt 为多少                |
| 6 | **协议外伤害命中复合目标，返回 ctx**                | `BFDamageApi.hurt` → 复合分支(路径4)                                  |   无  | 同路径 4，拦截逻辑走 BFHurtTarget 分支进入 Api          |
| 7 | **协议外伤害命中穿装备实体，返回 ctx**               | 走 adapter 管线 → `cir.setReturnValue(dealt > 0f)` → 取消原版          |   无  | 适配器以伤害量/2 作为默认穿深                           |
| 8 | **协议外伤害命中实体，返回 null**                 | 不接管 → 原版流程继续                                                    |   无  | 实现者自己在 `createContextFromVanilla` 中返回 null |

**核心不变量**：`BFDamageApi.hurt()` 中 `push` 的 target 优先取 `target.getBFEntity()`（若非空），否则取 target 自身。这保证了栈顶始终与内部 `entity.hurt()` 的调用者引用一致——无论 target 是实体直接实现 `BFHurtTarget` 还是非实体包装器。`TBArmorAdapter` 分支的 target 本来就是实体，不受此规则影响。

## 十二、武器侧角度效应处理

由于协议不再默认修正穿深，武器模组在构造 `BFDamageContext` 时必须自行完成角度效应计算。

典型公式（Machine-Max 实现）：

```java
穿透 = amount × cosθ

其中 θ 为命中速度方向与面法线的夹角。60° 入射时穿深降至 50%；掠射钳制到 1%。
```

这意味着武器模组在 builder 中填入的 penetration 已经是角度修正后的最终穿深值。协议层的 `modifyPenetration` 默认原样返回，仅作为护甲侧减效（爆反拦截、间隙衰减）的 hook。

## 十三、完整调用链示意

### 13.1 协议内伤害（武器模组 → BFHurtTarget、无回调）

```
武器模组:
  pen = amount × cosθ  （角度效应归弹头计算）
  ctx = BFDamageContext.builder()
    .source(myDamageSource).baseDamage(35f)
    .hitVelocity(vel).hitPoint(pos).hitNormal(normal)
    .penetration(pen)    // 已修正的最终穿深
    .build();
  
  BFDamageApi.hurt(tankEntity, ctx);
  
    → push(tankEntity, ctx)
    → tankEntity.resolvePenetration(ctx)
        → tankEntity.isArmorPenetrated(ctx)          // 默认委托
            → ctx.getPenetrationLevel().canDefeat(tankEntity.getArmorLevel(ctx))
            → true（同级或越级）→ PENETRATED
    → tankEntity.calculateFinalDamage(ctx, PENETRATED)
        → 同级 → baseDmg × 0.65  或  越级 → baseDmg
    → tankEntity.hurt(source, finalDmg)
        → 实现者可调用 super.hurt() 走原版，或完全自定义
    → ctx.getHandler() == null → 无回调
    → pop()
```

### 13.1b 协议内伤害（武器模组 → BFHurtTarget、带回调）

```
武器模组 (实现 BFDamageHandler):
  ctx = BFDamageContext.builder()
    .source(src).baseDamage(35f).penetration(120f).build();
  
  myHandler.dealDamage(tankEntity, ctx);
    → ctx = ctx.withHandler(myHandler)               // 自动注入
    → BFDamageApi.hurt(tankEntity, ctx)
        → push(tankEntity, ctx)
        → resolvePenetration(ctx) → PENETRATED
        → calculateFinalDamage(ctx, PENETRATED) → finalDmg
        → tankEntity.hurt(source, finalDmg)
        → triggerCallbacks: isOvermatch? → 穿深120 vs 装甲30×1.5=45 → true
        → myHandler.onPenetrated(tankEntity, ctx)     // 击穿回调

        → pop()
```

### 13.2 协议外伤害（原版攻击 → BFHurtTarget）

```
原版 or 未知模组:

    → Mixin(HEAD): hasContextFor(tankEntity)? → false (栈为空)
    → tankEntity instanceof BFHurtTarget → true
    → ctx = tankEntity.createContextFromVanilla(vanillaSource, 5.0f)
        → 低信息量上下文（仅 source + baseDamage，弹道字段零值）

        → tankEntity.calculateFinalDamage(ctx, BLOCKED) → 0

```

### 13.3 穿戴 TB 护甲的实体（协议伤害 → 穿护甲玩家）

```
武器模组:
  BFDamageApi.hurt(player, ctx)              // ctx: hitPoint=胸口, penetration=100
    → push(player, ctx)                      // ★ 栈顶 target = player 自身
    → NOT BFHurtTarget → LivingEntity → hasTBArmor? → true
    → adapter = new TBArmorAdapter(player)
    → adapter.resolvePenetration(ctx)         // 管线入口
        → adapter.ensureResolved(ctx)         // 惰性解析槽位
            → resolveTarget: 遍历各槽位
                → HEAD: 头盔.mapHitToSlot(player, ctx) → null
                → CHEST: 胸甲.mapHitToSlot(player, ctx) → CHEST ✓
            → resolvedMaterial = 胸甲, resolvedSlot = CHEST
        → 胸甲.resolvePenetration(CHEST, ctx)
            → 胸甲内部调用 this.getRHA(CHEST, ctx) → 350f
            → 胸甲内部调用 this.modifyPenetration(CHEST, ctx)
                → handler instanceof ChemicalEnergyWarhead? 否
                → 入射角 45° → 无削减 → 100f
            → 入射角 45° < 75° → 不跳弹
            → 100 < 350 → BLOCKED
    → adapter.calculateFinalDamage(ctx, BLOCKED)
        → 复用缓存 → 胸甲.calculateFinalDamage(CHEST, ctx, BLOCKED)
            → 默认：BLOCKED → 0（精密模式可能覆写为 15% 钝伤）
    → 不执行 hurt（finalDmg = 0）
    → triggerCallbacks(handler, adapter, ctx, BLOCKED)
        → handler.onBlocked(adapter, ctx)
        → handler 可通过 adapter.getBFEntity() 拿到 Player 实例
    → pop()
```

### 13.4 原版伤害命中穿戴 TB 护甲的实体

僵尸攻击 → player.hurt(source, 5)
  → Mixin intercept(player, source, 5)
    → hasContextFor(player)? → false（栈空）
    → player instanceof BFHurtTarget? → false
    → hasTBArmor(player)? → true           // ★ 第三条分支
    → adapter.createContextFromVanilla(source, 5)
        → ctx（source + baseDamage=5，弹道字段零值）

            → resolveBestSlot → 加权平均 RHA（假设仅胸甲=350mm×0.35归一到1.0=350mm）
            → adapter2.resolvePenetration 委托最高等级槽位胸甲

### 13.6 复合目标（BFHurtTarget + TB 护甲）

```
武器模组:
  BFDamageApi.hurt(载具驾驶员, ctx)     // 实体既是 BFHurtTarget(LivingEntity的实现者)，又穿着TBArmor胸甲
    → push(driver, ctx)                 // 栈 target = getBFEntity() = driver
    → 复合分支识别:
        driver instanceof LivingEntity?  → true
        driver instanceof BFHurtTarget? → true
        hasTBArmor(driver)?             → true
    → 第一层：护甲拦截
    → adapter = new TBArmorAdapter(driver)
    → adapter.modifyPenetration(ctx)    → 爆反拦截 → residualPen = 60
    → adapter.resolvePenetration(ctx)   → 击穿 (60 >= 50) → PENETRATED
    → adapter.calculateFinalDamage(ctx, PENETRATED)
        → 胸甲.calculateFinalDamage(CHEST, ctx, PENETRATED)
        → 同级击穿 → baseDmg × 0.65 = 35 × 0.65 = 22.75 → residualDmg = 22.75
    → 构造子上下文:
        armorResult == PENETRATED → childPen = residualPen = 60
        childCtx = ctx.childContext(22.75, 60)
    
    → 第二层：本体判定
    → driver.resolvePenetration(childCtx)
        → childPen=60, driver本体自身等效厚度=10
        → 60 >= 10 → PENETRATED
    → driver.calculateFinalDamage(childCtx, PENETRATED)
        → 越级击穿 → baseDmg × 100% = 22.75
    → driver.hurt(source, 22.75)
        → driver.hurt → Mixin hasContextFor(driver)=true → 放行 ✓
        → 22.75 再经原版护甲二次减免（ARMOR/TOUGHNESS/保护附魔）
    → triggerCallbacks(handler, driver, childCtx, PENETRATED)
        → handler.onPenetrated(driver, childCtx)
    → pop()
```

未击穿场景（BLOCKED）时的差异：

```
    → adapter.resolvePenetration(ctx)   → BLOCKED (60 < 100)
    → residualDmg = adapter.calculateFinalDamage(ctx, BLOCKED)
        → 胸甲覆写返回 15% 钝伤 = 35 × 0.15 = 5.25
    → armorResult != PENETRATED → childPen = 0f
    → childCtx = ctx.childContext(5.25, 0f)     // 穿深=0表示仅钝伤

    → 第二层：本体判定
    → driver.resolvePenetration(childCtx)
        → childPen=0 → 等效装甲等级 UNARMORED_1
        → driver 本体等效 10mm → UNARMORED_1.canDefeat(UNARMORED_1) → true
        → PENETRATED (0穿深也能"穿透"自身血肉)
    → driver.calculateFinalDamage(childCtx, PENETRATED)
        → childPen=0, getPenetrationLevel=UNARMORED_1, getArmorLevel=UNARMORED_1
        → 同级击穿 → baseDmg × 65% = 5.25 × 0.65 = 3.41
    → 最终扣血 3.41（本体的钝伤）
```

**关键观察**：穿深 0 时 `ArmorLevel.fromRha(0)` 返回 `UNARMORED_1`，与本体等级比较为同级 → 65% 基础伤害。这意味着本体"始终能被自身的血肉等级击穿，但只产生钝伤比例的伤害"——符合物理直觉。

## 十四、边界场景说明

### 14.1 荆棘反伤

`hasContextFor(target)` 精确区分"对同一目标的嵌套调用"和"副作用产生的新伤害"。荆棘对另一实体的伤害会被正确拦截并通过 `createContextFromVanilla` 重新进入协议管线。

### 14.2 嵌套伤害（子弹→爆炸→破片→多实体）

```
BFDamageApi.hurt(tank, bulletCtx)
  push(tank, bulletCtx)
  tank 判定为击穿 → 爆炸!
    tank 内部触发了对周围3个实体的爆炸伤害:
      for each nearby entity e:
        e.hurt(explosionSource, explosionDamage)
          → Mixin: hasContextFor(e)? → peek=(tank,bulletCtx) → false
          → 每个实体独立进入协议管线 ✓
    tank.hurt(source, finalDmg) → Mixin: hasContextFor(tank)=true → 不拦截 ✓
  pop(tank, bulletCtx)
```

### 14.3 虚空/指令/创造模式杀死

这些伤害类型与穿甲语义格格不入。与适配器对称——适配器的 `createContextFromVanilla` 始终返回有效上下文，不负责过滤。如果某个 `BFHurtTarget` 实现者希望虚空/指令等伤害退回原版，应在自己的 `createContextFromVanilla` 中返回 `null`。

### 14.4 实体作为 BFHurtTarget 目标

实体的 `Entity` 子类具有完整的原版伤害管线。当实体是 `BFHurtTarget` 时，`hurt` 可选择调用 `super.hurt()` 保留原版护甲值、保护附魔、药水等，或在调用前后添加自定义逻辑。

### 14.5 穿戴 TB 护甲的实体与回调交互

当 handler 回调收到 `BFHurtTarget target` 参数时，target 可能是 `TBArmorAdapter` 实例（非 Entity）。handler 可通过 `target.getBFEntity()` 安全地获取被包裹的实体：

```java
@Override
public void onPenetrated(BFHurtTarget target, BFDamageContext ctx) {
    if (target.getBFEntity() instanceof Player player) {
        player.playSound(myPenetrationSound, 1.0f, 1.0f);
        spawnParticlesAt(player, ctx.hitPoint());
    }
}
```

对于直接实现 `BFHurtTarget` 的实体，`getBFEntity()` 的默认实现返回 `this`——handler 无需区分目标类型。

## 十五、实现约束与长期目标

### 15.1 实现必须遵守

- 不修改 `DamageSource` 或其子类，不通过 Mixin 向 source 注入字段
- 不依赖弱引用（WeakReference）或静态 Map 作为 side-channel
- 不绕开 vanilla hurt pipeline 直接 `setHealth`
- 不破坏 Forge/NeoForge 的事件模型和事件总线
- ThreadLocal 上下文栈在 `try/finally` 中管理，确保不会泄漏
- 不对任何 vanilla 类做字段注入（@Shadow field additions）
- `TBArmorAdapter` 作为 internal 类不暴露给外部 mod，外部仅通过 `TBArmorMaterial` 接口接入
- `BFHurtTarget.getBFEntity()` 必须优先返回实体引用（非 null）以配合栈 target 选取规则——若实现者委托 `entity.hurt()` 却返回 null，会导致 mixin 重入守卫失效

### 15.2 长期愿景

项目最终目标是建立一套**面向复杂弹道与物理伤害的标准化交互层**，使得：

- 简单模组可以通过几行代码获得合理的穿甲判定（HD2 风格直达）
- 精密模组可以通过覆写全部管线获得毫米级精确判定（WoT 风格直达）
- 两种风格可以在同一个服务器共存互操作
- 穿甲模型（爆反、间隙装甲等）由装甲提供方在 hook 中实现，武器方无需了解装甲内部结构
- **护甲物品**通过 `TBArmorMaterial` 接口零代码接入协议，武器模组的回调中统一拿到 `BFHurtTarget` 抽象
- 模组间共享的命中结果元数据通过 `BFDamageExtensions` 的标准 key 传递，生态可在不修改协议库的情况下演化
- AI/自动化系统可以统一读取上下文做出决策
- 回放与网络同步基于统一的上下文字段实现

本项目本质上应被视为：**构建于 vanilla damage pipeline 之上的高维伤害语义层**，同时为简易场景和精密场景提供两个不同抽象级别的最短路径。

## 十六、多类型伤害处理策略

一次命中可能包含多种不同类型的伤害（如 24 火焰 + 100 穿刺）。协议不会在上下文中保存 Source-amount 列表，也不会要求调用方分多次调用 `BFDamageApi.hurt()`。

### 16.1 设计原则

| 层级                    | 职责                               | 示例                     |
| --------------------- | -------------------------------- | ---------------------- |
| **主伤害（context）**      | 走完整穿甲判定管线，决定穿透与否                 | 穿刺 100，penetration=100 |
| **附加伤害（handler 回调）**  | 穿甲结果确定后，在回调中用正确的 DamageSource 施加 | 穿透→内部燃烧 24 火焰          |
| **附加元数据（extensions）** | 护甲侧需要感知的额外伤害信息                   | 破片伤害量、燃烧持续时间           |

### 16.2 为什么不在上下文存 Source-amount 列表

1. **穿甲判定是单一事件**：弹体要么穿透要么没穿透。火焰不"穿透"装甲——它是穿透的后果，不是独立的穿甲判定。
2. **Minecraft DamageSource 的硬限制**：火焰保护附魔、火焰免疫等机制依赖正确的 `DamageSource` 触发。合并为一个 source 会导致这些机制失效。
3. **99% 场景的复杂度**：绝大多数命中只有一种伤害类型。为这 1% 让 context 变成列表，会污染所有护甲模组的实现。

### 16.3 推荐实现：handler 回调施加附加伤害

```java
// 武器模组侧
BFDamageContext ctx = BFDamageContext.builder()
    .source(PIERCING_SOURCE)       // 主伤害：穿刺
    .baseDamage(100f)
    .penetration(100f)
    .hitVelocity(vel)
    .hitPoint(point)
    .hitNormal(normal)
    .handler(new BFDamageHandler() {

        @Override
        public void onPenetrated(BFHurtTarget target, BFDamageContext ctx) {
            // 穿透后：在载具/实体内部施加火焰伤害
            Entity entity = target.getBFEntity();
            if (entity != null) {
                entity.hurt(DamageSource.IN_FIRE, 24f);
            }
        }

        @Override
        public void onBlocked(BFHurtTarget target, BFDamageContext ctx) {
            // 未穿透：火焰在装甲外部燃烧，伤害减半
            Entity entity = target.getBFEntity();
            if (entity != null) {
                entity.hurt(DamageSource.IN_FIRE, 12f);
            }
        }
    })
    .build();

BFDamageApi.hurt(target, ctx);
```

### 16.4 护甲侧配合（可选）

如果护甲模组需要在 `calculateFinalDamage` 中统一计算包含附加伤害的最终值，武器侧可将附加伤害量写入扩展：

```java
// 武器侧
exts.set(FIRE_DAMAGE, 24f);  // 注册一个 FIRE_DAMAGE 扩展 key

// 护甲侧覆写
@Override
public float calculateFinalDamage(BFDamageContext ctx, PenetrationResult result) {
    float kinetic = super.calculateFinalDamage(ctx, result);
    float fire = ctx.extensions().get(FIRE_DAMAGE);
    if (hasSpallLiner()) fire *= 0.5f;  // 防爆衬层减半燃烧伤害
    return kinetic + fire;
}
```

不过此方式将多个伤害合并在一个 `DamageSource` 下调用 `hurt()`，火焰保护附魔不会正确触发。**推荐使用 handler 回调方案**——它使用正确的 DamageSource 分别调用 `hurt()`。

## 十七、BFHitResolver —— 命中前目标解析接口

### 17.1 设计动机

在复杂的模组生态中，`Entity.hurt()` 被调用的目标实体可能只是**代理实体**——真正应该承受伤害的物理对象隐藏在代理后面。

典型场景：Machine-Max 的 `MMPartEntity`。载具的每个零部件在 Minecraft 实体层有一个对应的 `MMPartEntity` 代理实体，用于挂载乘客、显示 UI、接收事件等。但真正的伤害处理发生在物理层的 `SubPart`（实现 `BFHurtTarget`）上。原版碰撞检测（AABB 相交）命中 `MMPartEntity` 后，攻击方如何知道应该把伤害路由到哪个 `SubPart`？

另外，攻击方在调用 `BFDamageApi.hurt()` **之前**需要知道：
- 是否真的命中了（而不是 AABB 膨胀导致的假阳性）
- 命中的精确位置和法线是什么
- 真正的伤害目标是什么

这些都是 `BFDamageApi.hurt()` 的管线内无法回答的问题——因为进入管线时，伤害已经被判定为"已发生"了。

### 17.2 核心思路：管线外查询 + 管线内执行

`BFHitResolver` 是一个独立于 `BFHurtTarget` 的接口，在伤害管线**之前**被调用。它负责：

1. 接收原始命中信息（命中点、命中方向、查询距离）
2. 执行精确的命中验证（可能包含物理引擎射线检测）
3. 返回真正的伤害目标 + 修正后的命中几何数据

返回 `null` 表示实际未命中，攻击方应让投射物继续飞行。

**与 `BFHurtTarget` 的职责分离：**
- `BFHitResolver` 回答"打中了谁"的问题——在管线外
- `BFHurtTarget` 回答"打中了之后穿深多少、伤害多少"的问题——在管线内

### 17.3 接口定义

```java
/**
 * 命中前目标解析接口。
 * <p>
 * 由代理实体实现。在伤害管线之外（ {@link BFDamageApi#hurt} 调用之前）执行，
 * 将原始的实体命中重定向到实际的物理伤害目标。
 */
public interface BFHitResolver {

    /**
     * 解析命中的实际伤害目标。
     *
     * @param hitPoint 原版报告的命中点（世界坐标）
     * @param delta    搜索矢量，其模为搜索距离上限（m），方向为命中方向。
     *                 典型值：投射物的 deltaMovement 或其倍数。
     * @return 解析结果；{@code null} 表示实际未命中，投射物应继续飞行
     */
    @Nullable
    BFHitResolveResult resolveHit(Vec3 hitPoint, Vec3 delta);
}

/**
 * 命中解析结果——真正的目标 + 修正后的命中几何 + 扩展数据。
 *
 * @param actualTarget       真正的协议伤害目标（{@link BFHurtTarget} 实例）
 * @param correctedHitPoint  修正后的命中点世界坐标
 * @param correctedHitNormal 修正后的命中面法线
 * @param extensions         解析器提供的扩展数据，可直接用于构造 {@link BFDamageContext}。
 *                           调用方应先 {@link BFDamageExtensions#copy() copy} 后再追加自己的 key。
 *                           无扩展数据时为空容器。
 */
public record BFHitResolveResult(
    BFHurtTarget actualTarget,
    Vec3 correctedHitPoint,
    Vec3 correctedHitNormal,
    BFDamageExtensions extensions
) {
    /** 无扩展数据的便利构造器 */
    public BFHitResolveResult(BFHurtTarget actualTarget, Vec3 correctedHitPoint, Vec3 correctedHitNormal) {
        this(actualTarget, correctedHitPoint, correctedHitNormal, new BFDamageExtensions());
    }
}
```

### 17.4 BFDamageApi 便利方法

```java
/**
 * 解析命中目标。
 * <p>
 * 若 hitEntity 实现了 {@link BFHitResolver}，执行精确验证并返回修正后的目标与几何。
 * 否则，若 hitEntity 自身是 {@link BFHurtTarget}，直接包装返回。
 * 返回 null 表示未命中（投射物应继续飞行）。
 * <p>
 * 典型调用模式（武器模组侧）：
 * <pre>{@code
 * var resolved = BFDamageApi.resolveHitTarget(hitEntity, hitPoint, hitDir, maxDistance);
 * if (resolved == null) {
 *     event.setCanceled(true); // 假阳性，投射物继续飞行
 *     return;
 * }
 * var ctx = BFDamageContext.builder()
 *     .hitPoint(resolved.correctedHitPoint())
 *     .hitNormal(resolved.correctedHitNormal())
 *     .extensions(resolved.extensions().copy())  // 解析器产生的扩展数据
 *     // ...
 *     .build();
 * BFDamageApi.hurt(resolved.actualTarget(), ctx);
 * }</pre>
 *
 * @param hitEntity    原版碰撞检测命中的实体
 * @param hitPoint     原版报告的命中点
 * @param hitDirection 命中方向（已归一化）
 * @param maxDistance  搜索距离上限
 * @return 解析结果；{@code null} 表示未命中
 */
public static @Nullable BFHitResolveResult resolveHitTarget(
    Entity hitEntity, Vec3 hitPoint, Vec3 hitDirection, double maxDistance
) {
    if (hitEntity instanceof BFHitResolver resolver) {
        return resolver.resolveHit(hitPoint, hitDirection, maxDistance);
    }
    if (hitEntity instanceof BFHurtTarget bf) {
        return new BFHitResolveResult(bf, hitPoint, Vec3.ZERO);
    }
    return null;
}
```

### 17.5 两层防御体系

```
┌──────────────────────────────────────────┐
│    框架内攻击者（武器模组）                    │
│  ① resolveHitTarget() → 查询真目标           │
│  ② 用修正几何构造 BFDamageContext              │
│  ③ BFDamageApi.hurt(actualTarget, ctx)      │
│                                              │
│  → 命中精确几何 → 伤害精准路由                   │
│  → 返回 null → 假阳性，投射物继续飞行             │
└──────────────────┬───────────────────────┘
                   │
┌──────────────────▼───────────────────────┐
│          BFHitResolver (协议层)              │
│  MMPartEntity 实现 → 物理射线 → SubPart       │
│  普通 Entity 不实现 → 跳过                    │
└──────────────────────────────────────────┘
                   │
┌──────────────────▼───────────────────────┐
│     防御侧自愈（BFHurtTarget.hurt() 内部）     │
│  攻击方未调用 resolveHitTarget 时，              │
│  防御方在 hurt() 内部自行做精确检测                │
│  → 安全网，确保任何攻击路径都路由正确               │
└──────────────────────────────────────────┘
```

**关键设计决策**：BFHitResolver 不能也不应该替代防御侧自愈。框架内攻击者通过 `resolveHitTarget()` 获得更好的体验（精确几何、假阳性判断），框架外攻击者的伤害由防御侧在 `hurt()` 内部自愈——两者互补。

### 17.6 为什么不放在 BFHurtTarget 中

`BFHurtTarget` 的所有方法（`getRHA`、`modifyPenetration`、`resolvePenetration`、`calculateFinalDamage`、`hurt`）都在**伤害管线内部**被调用。此时上下文中已有完整的 `BFDamageContext`，攻击已被视为"已发生"。

命中选择——包括判断是否实际命中、获取精确几何——是**管线外**的操作。它应该在攻击方调用 `BFDamageApi.hurt()` 之前完成。将两者合并到同一接口中会造成语义混淆：
- 哪些方法在管线内被调用？哪些在管线外被调用？
- 调用顺序如何保证？
- `BFDamageApi.hurt()` 内部是否要额外触发命中选择？

分离接口使职责边界清晰，也允许防御方独立演化两个维度的行为。

### 17.7 示例：Machine-Max 代理实体实现

```java
// MMPartEntity 实现 BFHitResolver
@Override
public BFHitResolveResult resolveHit(Vec3 hitPoint, Vec3 hitDirection, double maxDistance) {
    var start = PhysicsHelperKt.toBVector3f(hitPoint);
    var end = PhysicsHelperKt.toBVector3f(hitPoint.add(hitDirection.scale(maxDistance)));
    var results = getPhysicsLevel().getWorld().getWorldSnapshot().rayTest(start, end);
    for (var result : results) {
        if (PhysicsBodyExtensionKt.getOwner(result.getCollisionObject()) instanceof SubPart sp) {
            if (sp.isWheelSurface(result.triangleIndex())) continue;
            var hb = sp.getHitBox(result.triangleIndex());
            if (!hb.isActive()) continue;

            BFDamageExtensions ext = new BFDamageExtensions();
            ext.set(MMDamageExtensions.HIT_BOX, hb);

            return new BFHitResolveResult(
                sp,
                SparkMathKt.toVec3(
                    start.add(end.subtract(start).mult(result.getHitFraction()))),
                SparkMathKt.toVec3(result.getHitNormalLocal(null)),
                ext
            );
        }
    }
    return null; // 射线穿过——实际未命中
}
```

### 17.8 便利方法重载：从 HitResult 解析

为降低调用门槛，提供两层重载：

**接口上的 default 方法**（`BFHitResolver` 内部）：

```java
/**
 * 便利重载：从原版 HitResult 提取命中点后委托给三参数方法。
 *
 * @param hitResult    原版命中结果（取其 getLocation() 作为命中点）
 * @param hitDirection 命中方向（已归一化）
 * @param maxDistance  搜索距离上限
 * @return 解析结果；null 表示未命中
 */
@Nullable
default BFHitResolveResult resolveHit(HitResult hitResult, Vec3 hitDirection, double maxDistance) {
    return resolveHit(hitResult.getLocation(), hitDirection, maxDistance);
}
```

**BFDamageApi 上的对应便利方法**：

```java
/**
 * 从原版 HitResult 解析命中目标。
 * <p>
 * 相比 {@link #resolveHitTarget(Entity, Vec3, Vec3, double)}，
 * 本重载自动从 EntityHitResult 中提取命中实体和命中点。
 * 非 EntityHitResult（如方块命中）返回 null。
 *
 * @param hitResult    原版命中结果
 * @param hitDirection 命中方向（已归一化）
 * @param maxDistance  搜索距离上限
 * @return 解析结果；null 表示未命中或无效命中类型
 */
@Nullable
public static BFHitResolveResult resolveHitTarget(
        HitResult hitResult, Vec3 hitDirection, double maxDistance) {
    if (hitResult instanceof EntityHitResult ehr) {
        return resolveHitTarget(ehr.getEntity(), hitResult.getLocation(), hitDirection, maxDistance);
    }
    return null;
}
```

两个重载的分工：

| 重载 | 签名 | 用途 |
|------|------|------|
| 实体版本 | `resolveHitTarget(Entity, Vec3, Vec3, double)` | 调用方已分别持有命中实体和命中点 |
| HitResult 版本 | `resolveHitTarget(HitResult, Vec3, double)` | 调用方持有原版 HitResult，自动解包 |

### 17.9 ProjectileHitResolverMixin —— 命中流程自动化接管

#### 17.9.1 设计动机

17.5 节描述的两层防御体系中，"攻击侧查询"需要武器模组主动调用 `resolveHitTarget()`。但对于框架外的武器模组，它们不会调用这个方法——此时若发生 AABB 假阳性命中，投射物仍会被错误销毁。

理想方案是让验证**自动发生**——在投射物的 `onHit()` 被调用时，协议层自动拦截，先做精确命中验证，再决定是否放行。

#### 17.9.2 注入点选择

注入 `Projectile.onHit(HitResult)` 的 HEAD 阶段。这个点满足所有条件：

- 在命中声音、伤害处理、discard 之前
- `@Inject(cancellable = true)` 可直接阻止原版流程
- cancel 后投射物保留在 world 中，继续下一 tick 的飞行
- 注入到 Projectile 基类，所有子类（箭、火球、自定义弹头等）均受益

#### 17.9.3 Mixin 实现

```java
package io.github.sweetzonzi.ballistics_framework.mixin;

import io.github.sweetzonzi.ballistics_framework.api.BFDamageApi;
import io.github.sweetzonzi.ballistics_framework.api.BFHitResolver;
import net.minecraft.world.entity.projectile.Projectile;
import net.minecraft.world.phys.EntityHitResult;
import net.minecraft.world.phys.HitResult;
import net.minecraft.world.phys.Vec3;
import org.spongepowered.asm.mixin.Mixin;
import org.spongepowered.asm.mixin.injection.At;
import org.spongepowered.asm.mixin.injection.Inject;
import org.spongepowered.asm.mixin.injection.callback.CallbackInfo;

/**
 * 注入 {@link Projectile#onHit(HitResult)} 的 HEAD 阶段。
 * <p>
 * 若命中的实体实现了 {@link BFHitResolver}，在执行原版命中处理之前
 * 先做精确验证：调用 {@link BFDamageApi#resolveHitTarget(HitResult, Vec3, double)}
 * 检查是否实际命中。返回 null 时取消原版流程，投射物继续飞行（AABB 假阳性不销毁）。
 * <p>
 * 与 {@code EntityHurtMixin} / {@code LivingEntityHurtMixin} 的互补关系：
 * <ul>
 *   <li>本 Mixin 在管线之外——在 onHit 执行前拦截，解决投射物生命周期问题</li>
 *   <li>EntityHurtMixin 在管线入口——在 hurt 执行前拦截，解决协议外伤害接管问题</li>
 * </ul>
 */
@Mixin(Projectile.class)
public class ProjectileHitResolverMixin {

    @Inject(method = "onHit", at = @At("HEAD"), cancellable = true)
    private void bf$resolveHitBeforeProcess(HitResult result, CallbackInfo ci) {
        if (!(result instanceof EntityHitResult ehr)) return;
        if (!(ehr.getEntity() instanceof BFHitResolver)) return;

        Projectile self = (Projectile) (Object) this;
        Vec3 velocity = self.getDeltaMovement();
        double speed = velocity.length();
        if (speed < 0.001) return;

        // 搜索距离基于投射物速度动态计算：
        // 取两 tick 飞行距离作为安全余量，钳制在 [1.0, 8.0] 米
        double maxDistance = Math.clamp(speed * 2.0, 1.0, 8.0);

        var resolved = BFDamageApi.resolveHitTarget(
                result, velocity.scale(1.0 / speed), maxDistance);
        if (resolved == null) {
            ci.cancel();
        }
    }
}
```

#### 17.9.4 与 Machine-Max 现有流程的交互

| 场景 | 触发链 | Mixin 行为 |
|------|--------|------------|
| 第三方投射物 → MMPartEntity AABB 假阳性 | PartHitHandler 先 cancel 了 ProjectileImpactEvent | `onHit()` 不会被调用，Mixin 不触发 ✅ |
| 第三方投射物 → MMPartEntity AABB 真命中 | PartHitHandler 设置 IProjectileMixin 数据 → `onHit()` | Mixin 触发 → `resolveHitTarget` 找到 SubPart → 非 null → 放行 ✅ |
| MM 投射物 → `manualProjectileHit` | `onProjectileTick` → 射线检测 → `onHit(HitResult)` | Mixin 触发 → `resolveHitTarget` 找到 SubPart → 非 null → 放行 ✅ |
| 普通 Entity（非 BFHitResolver） | 原版 → `onHit()` | `instanceof BFHitResolver` = false → 直接 return，零开销 ✅ |

#### 17.9.5 为什么放在 BF 而不是 Machine-Max

`BFHitResolver` 是 BF 定义的接口。利用此接口做前置拦截是**协议层行为**：任何实现了此接口的实体被任何投射物命中时，都自动获得精确验证。将其放在 BF 内：

- 所有 `BFHitResolver` 实现者统一受益，不限于 Machine-Max
- 与已有的 `EntityHurtMixin` / `LivingEntityHurtMixin` 在性质和粒度上完全一致
- 没有 BFHitResolver 实体存在时，不过是一次 `instanceof` + return，性能影响可忽略

#### 17.9.6 完整自动化调用链

```
投射物飞行 → 原版碰撞检测 → onHit(HitResult)

    ↓ Mixin 注入 (HEAD, cancellable)

    ① HitResult 是 EntityHitResult？
       ↓ 否 → return（方块命中，正常处理）

    ② hitEntity 是 BFHitResolver？
       ↓ 否 → return（普通实体，正常处理）

    ③ resolved = BFDamageApi.resolveHitTarget(result, velocity.normalize(), maxDistance)
       ↓ 内部自动解包 EntityHitResult → 路由到 resolveHitTarget(Entity, Vec3, Vec3, double)
       ↓ 内部调用 BFHitResolver.resolveHit(HitResult, dir, dist)
       ↓ 内部调用 BFHitResolver.resolveHit(hitPoint, dir, dist)

    ④ resolved == null？
       ↓ 是 → ci.cancel()  ★ 投射物不销毁，继续飞行
       ↓ 否 → 放行，原版 onHit 正常执行
```

#### 17.9.7 两层互补体系（更新版）

```
上层（攻击侧自动化）: ProjectileHitResolverMixin
  拦截 Projectile.onHit → resolveHitTarget → null → cancel
  → 解决"投射物不该被销毁"的问题（防御侧做不到）

下层（防御侧自愈）:  MMPartEntity.hurt() 中的 rayTestSelf()
  已在管线内的伤害 → 自行精确检测 → 路由到正确 SubPart
  → 解决"伤害路由正确性"的问题

两者解决的是不同层次的问题：
  Mixin     → 投射物生命周期管理（打空了就该继续飞）
  hurt 自愈 → 伤害精准路由（打中了就该找对目标）
```
