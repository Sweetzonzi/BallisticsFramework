# 弹道求解器 — 求角免物化与采样存储改造计划

> **状态**：计划中（未实施）。
>
> **定位**：本文拥有「求角路径不构造轨迹」与「采样存储改为列式」两阶段改造的目标契约：分派结构、每一处接线的写法、验收断言与版本策略。`TrajectoryResult` / `TrajectorySample` 的公共形态目前由 `api/trajectory/TrajectoryResult.java` 与 `api/trajectory/TrajectorySample.java` 自身拥有，本文落地后接管其存储形态与访问方式。
>
> **本文自包含**：分派点、等价条件、体积账与验收断言都在文内给出，不要求先读其他文档。文中源码引用一律用 `path#symbol`，不绑定行号。

## 一、问题与证据

### 1.1 观测量

在 Machine-Max 的 K17 连发场景采集 `/spark profiler start --thread * --interval 1 --timeout 20`，得到 `Machine-Max/run/config/spark/profile-2026-11-02_11.21.43.sparkprofile`。该报告 `Render thread` 窗口 12.18 s，其中：

| 栈帧 | self / 归属 | 占该线程 |
| --- | --- | --- |
| `java.util.ImmutableCollections#listFromArray` | 5.11 s self | 42.19% |
| `RealisticTrajectory#solveFiringAngle` 整条链 | 5.58 s total | 45.85% |
| `RealisticTrajectory#solveFullIntegrationSI` | 9 ms self | 0.07% |

最后一行的读数需要打折看：`solveFullIntegrationSI` 被 C2 内联进 `binarySearchAngleSI`（该帧 self 384 ms，同为内联折叠），因此"积分贵还是拷贝贵"无法从采样直接切分。可以确定的是 **`List.copyOf` 是一次独立于积分之外的全量遍历**，它不产生任何被保留的结果。

调用方是 `Machine-Max` + `client/render/gui/hud/molang/HudBallisticTable.java#resolve`：它沿距离取 128 个点，每点调一次 `RealisticTrajectory#solveFiringAngle`，后者在 `#solveFullFiringAngleSI` 内做平射与高抛各一次二分搜索。以 30mm 弹（`max_lifetime = 5.0`、`timeStep = 1/60`）计，`maxSteps = 300`，一次表求解的积分次数上限为 `128 × 2 × 50 = 12800` 次。

### 1.2 两层浪费

1. **求角不需要轨迹**。`#binarySearchAngleSI` 拿到 `TrajectoryResult` 后只做两件事：找离目标最近的采样点、求目标水平距离处的弹道高度（`#heightAtHorizontalDistanceSI`）。两条扫描都是逐点、只看当前点的量，没有任何一步需要保留历史。而 `#forwardSolve` 每次都把整条轨迹物化成 `maxSteps + 1` 个采样点。
2. **采样点的存储形态偏重**。每个采样点是一个 record 加两个 `Vec3`：

| 组成 | 字节（压缩指针，8 字节对齐） |
| --- | --- |
| `TrajectorySample`：对象头 12 + `time` 4 + 两个引用 8 | 24 |
| 两个 `Vec3`：各自 12 + 3×8，对齐到 40 | 80 |
| `ArrayList` 槽位 | 4 |
| **合计** | **108**，有效载荷仅 56（7 个 double） |

外加 `List.copyOf` 在 `TrajectoryResult` 紧凑构造函数里再分配一个等长 `Object[]` 并整体复制一次。

### 1.3 这不是"库太慢"

单次 `forwardSolve` 的开销本身在可接受范围；问题被调用方的乘法放大了——一次表求解等于上万次完整积分的分配量。改造的目标是让"只需要一个数"的调用方不必为"整条轨迹"付费，这同时是一条 API 造型问题。

## 二、范围

| 能力 | 本计划 |
| --- | --- |
| **阶段 B**：求角路径融合积分与扫描，不构造 `TrajectoryResult` | 做 |
| 积分核改用基本类型局部变量（B 的零分配前提，见 §3.3） | 做 |
| **阶段 C**：`TrajectoryResult` 改列式 `double[]` 存储，采样点不再是独立对象 | 做 |
| 去掉内部路径的 `List.copyOf` | 随 C 自然消失（C 之后内部路径不再有 `List`） |
| `float` 存储采样值以再省一半 | 不做，见 §七 |
| 改积分公式、换数值方案 | 不做 |
| SIMD / 多线程积分 | 不做 |

顺序是 **B → C**，不可颠倒：若先做 C，求角路径仍然要算 12800 条轨迹，只是每条从 32.5 KB 降到 16.9 KB；B 直接把 12800 条降到 0 条。C 的受益方是真正需要整条轨迹的飞行推进路径。

## 三、阶段 B — 求角免物化

### 3.1 分派结构

`#solveFiringAngle` 的门禁不变，仍按 `thrust.isActive()` 与 `isNoDrag` / `gravity` 分出四条路径。其中三条退化路径（`#solveLinearFiringSI`、`#solveParabolicFiringSI`、`#solveDecelerationFiringSI`）是解析解，不经过积分循环，本阶段不触碰。只有完整路径 `#solveFullFiringAngleSI` 内的 `#binarySearchAngleSI` 需要改造。

### 3.2 采样汇聚器：全基本类型签名

七个积分器（`#solveLinearMotionSI`、`#solveStraightDecelerationSI`、`#solveParabolicMotionSI`、`#solveFullIntegrationSI`，以及推力侧的 `#solveThrustNoDragSI`、`#solveThrustStraightDragSI`、`#solveThrustReducedSI`）目前都以 `samples.add(new TrajectorySample(...))` 结尾。把这一句换成对 `SampleSink` 的调用，签名一律用基本类型：

```java
/** 积分循环的采样出口；实现自行累积，不向外返回状态。 */
private interface SampleSink {
    void accept(float time, double x, double y, double z, double vx, double vy, double vz);
}
```

为什么不用 `Vec3`：`Vec3` 不可变，积分循环每步 `pos = pos.add(...)` 都会新建两个实例（80 B/步）。汇聚器若收 `Vec3`，探针路径就被迫跟着建这两个对象，"免物化"只免掉了采样点本身，正解路径的分配量也一分未减。收七个 `double` 之后，探针路径一次分配都不发生。

两个实现，都由 `RealisticTrajectory` 私有持有：

- `AppendSink`：内部 `new Vec3(...)` 与 `new TrajectorySample(...)` 后追加到 `ArrayList`，产出的对象与现有构造点逐字等价，供 `#forwardSolve` 继续返回完整轨迹。
- `ProbeSink`：零分配，只更新四个字段——`minDist`、`bestTime`、`bestVelocity`、`heightAtTarget`。

选择汇聚器而不是给每个积分方案再写一份"探针版"，是为了避免七份复制体各自漂移；`ProbeSink` 需要的能力（距离、水平投影、高度插值）都由同一个出口表达。

**内联风险与兜底**：每个积分循环的调用点是双态（`AppendSink` / `ProbeSink`），C2 依类型剖面做守卫内联，正常情况下每次采样多不出一次真实调用。验收里设一条基准（§六.3）；若基准显示未内联，兜底方案是只给 `#solveFullIntegrationSI` 与其推力变体写探针专用副本，退化路径不参与求角，无需覆盖。

### 3.3 积分核基本类型化

要让 §3.2 的零分配真正成立，求角路径会走到的四个积分器必须把推进变量从 `Vec3` 换成 `double` 局部量：`#solveFullIntegrationSI` 与推力侧的 `#solveThrustNoDragSI`、`#solveThrustStraightDragSI`、`#solveThrustReducedSI`。其中 `#solveThrustReducedSI` 已经是这个形态——用 `u` / `w` / `along` / `height` 推进，只在出口构造 `Vec3`——可直接作为其余三个的写法基准。

另三个退化积分器（`#solveLinearMotionSI`、`#solveParabolicMotionSI`、`#solveStraightDecelerationSI`）只被 `#forwardSolve` 使用，不在求角路径上，保留 `Vec3` 推进，只在出口把分量拆给汇聚器。这样改动面停在四个方法上。

改写只换承载变量，不动运算顺序：`pos.add(vel.scale(k))` 与 `px += vx * k` 在 `double` 上逐位等价，因为 `Vec3#add` 与 `Vec3#scale` 都是分量级乘加。把两次乘加合并成一次、或调整结合顺序这类"顺手优化"会破坏 §六.1 的逐位一致，明确禁止。

### 3.4 语义等价条件

改造后 `#binarySearchAngleSI` 的返回值必须与现在逐字段一致，包括 `FiringSolution#iterations`。为此四条约束写死：

1. **采样点集合不变**：仍是 `0 .. maxSteps` 共 `maxSteps + 1` 个点，`time = i · timeStep`，`i = 0` 处为入参位置与速度。
2. **最近点判据不变**：`(float) position.distanceTo(target)`，严格 `<` 比较，先到先得（等价关系保留，不改成 `<=`）。
3. **高度插值规则不变**：把 `#heightAtHorizontalDistanceSI` 的遍历逻辑原样搬进 `ProbeSink`——以发射点为原点，沿水平方向做点积，第一个 `dot >= targetDot` 的点用 `span < 1e-9` 守卫后按线性插值取高度；全程未越过则记 `NaN`。
4. **越界语义不变**：`NaN` 仍在 `#binarySearchAngleSI` 里按"未越过 / 过冲"处理，即 `overshoot = !reached || heightAtTarget > target.y`。

`ProbeSink` 在 `#binarySearchAngleSI` 入口创建一次，跨最多 50 次迭代复用；`heightAtTarget` 每次迭代开头重置。

### 3.5 公开面不变

`#forwardSolve` 仍返回完整 `TrajectoryResult`，`MinecraftTrajectory` 的五个便捷入口（`#arrowTrajectory`、`#snowballTrajectory`、`#fireballTrajectory`、`#potionTrajectory`、`#bottleTrajectory`）不受影响。本阶段对公共 API 是零改动。

## 四、阶段 C — 采样存储列式化

### 4.1 目标形态

`TrajectoryResult` 从 record 改为 `final class`，内部一个行优先数组：

```java
public final class TrajectoryResult {
    private static final int STRIDE = 7;          // t, x, y, z, vx, vy, vz
    private final double[] data;                  // 长度 = 采样点数 × STRIDE
    private final int count;

    public int size();
    public TrajectoryCursor cursor();             // 可复用、零分配遍历
    public List<TrajectorySample> toSampleList(); // 显式物化

    // 既有的便捷查询保持不变：first / last / totalTime / terminalPoint /
    // terminalVelocity / approximateHitNormal
}
```

```java
public final class TrajectoryCursor {
    public boolean advance();                     // 前进一格，越界返回 false
    public int index();
    public double time();
    public double x(); public double y(); public double z();
    public double vx(); public double vy(); public double vz();
    public Vec3 position();                       // 需要时才建
    public Vec3 velocity();
    public double distanceTo(Vec3 point);         // 基本类型运算，不建 Vec3
}
```

`equals` / `hashCode` 按 `count` 与 `data` 内容实现，与 record 形态下的值语义对齐——改存储不该顺带改变相等性。

### 4.2 为什么行优先单数组

- **56 B/点，恰好落在一个 64 B 缓存行内**，一格的 7 个值一次读入。
- 现有消费方全部是"逐点读全状态"：`#binarySearchAngleSI` 读位置算距离，飞行推进读位置与速度判命中。没有"只读某一列"的热点，平行数组只会把一次顺序访问拆成两三次。
- 一条轨迹一次分配（`count · 7` 个 double），而不是每点三次分配。

### 4.3 为什么舍弃 `samples()`

record 的 `samples()` 是个陷阱：调用方写 `for (var s : result.samples())` 时，要么返回物化后的 `List`（成本回到旧形态），要么返回视图（`equals`/`hashCode` 与遍历耗时都依赖访问顺序）。两者都让"这次调用很便宜"的错觉得以成立。

替代是 `toSampleList()`——名字本身声明了分配。库内 10 处 `result.samples()` 调用点改为 `cursor()` 遍历；`TrajectorySample` 保留为对外 DTO，只由 `toSampleList()` 与 `first()` / `last()` 生产。

### 4.4 体积账

| 路径 | 现状 | 阶段 B 后 | 阶段 B + C 后 |
| --- | --- | --- | --- |
| 求角（每次二分迭代一次的积分） | 32.5 KB / 904 次分配 | **0 / 0** | 0 / 0 |
| 正解（一次 301 点 `forwardSolve`） | 32.5 KB / 904 次分配 | 32.5 KB / 904 次 | **16.9 KB / 1 次** |

两阶段互补而非重叠：B 消掉的是求角路径的**次数**（一次表求解上万次积分，全部不分配），C 降低的是正解路径的**单次成本**（904 次分配压到 1 次）。正解路径在 B 之后看不出变化，因为 `AppendSink` 仍要物化采样点——这也是 B 排在 C 前面的理由：先消掉不需要结果的那些调用，再优化需要结果的形态。

## 五、C 暂缓时的止血做法

若只做 B、C 排期靠后，`TrajectoryResult` 的紧凑构造函数仍是飞行推进路径上的固定成本。此时给 `TrajectoryResult` 加一个包内工厂：

```java
static TrajectoryResult owned(List<TrajectorySample> samples);  // 跳过 List.copyOf
```

公开构造器保留 `List.copyOf`，内部 12 处 `new TrajectoryResult(samples)` 改为 `owned(...)`。依据是这 12 处的实参都是方法内新建、返回后即无外部引用的局部 `ArrayList`，且元素不可变，因此不存在被外部改写的路径。

这条只止血不治病：它省掉一次等长数组分配与一次全量遍历，采样点对象的开销原样保留。C 落地后 `List` 构造路径消失，本节的工厂随之删除。

## 六、验收

1. **正解逐位一致**：同一组 `BallisticConfig`、`DensityFunction`、`ThrustProfile` 下，`#forwardSolve` 在阶段 B（积分核基本类型化）与阶段 C（存储列式化）前后的输出逐点用 `Double.doubleToLongBits` 比较相等；时间列需与 `i · timeStep` 的 `float` 值一致。
2. **求角逐字段一致**：B 前后，`#solveFiringAngle` 对退化路径与完整路径各取一组样例，返回的 `FiringSolution` 在 `direction`、`flightTime`、`velocity`、`isHighArc`、`iterations` 上完全相等。
3. **分配量**：两条基准，都用 `-Xlog:gc` 或 spark `--alloc` 取证，不接受估算：
   - 求角路径：B 后 `HudBallisticTable#resolve` 单次调用期间采样分配为 0；改造前是同一条路径上上万次积分各 32.5 KB。
   - 正解路径：C 后 `#forwardSolve` 单次 301 点的分配从 904 次降到 1 次，字节从 32.5 KB 降到 16.9 KB。
4. **内联兜底触发条件**：基准显示每次积分的 CPU 时间相对现状上升超过 5% 时，按 §3.2 的兜底方案收窄 `ProbeSink` 的覆盖面。
5. **回归**：`RealisticTrajectoryInvariantTest` 全绿；`./gradlew runGameTestServer` 24 项全绿。

## 七、明确不做

- **`float` 存储**：`double[]` 降到 `float[]` 能再省一半（28 B/点），但位置与速度目前以 `double` 参与运算，落盘成 `float` 会改动数值结果，与 §六.1 的逐位一致冲突。要省这一半，得先接受"输出精度变更"，那是另一个决定。
- **`samples()` 兼容层**：保留它等于保留"读整条轨迹很便宜"的错觉。迁移成本已查清——`samples()` 的 10 处消费全在 `api/trajectory/RealisticTrajectory.java` 与 `api/trajectory/MinecraftTrajectory.java` 内部，Machine-Max 未直接使用该访问器。
- **改积分公式或数值方案**：本文只动数据形状与调用结构。
- **并行化**：单条轨迹最多几百步，线程调度开销大于收益。
