# 弹道求解器 — 求角免物化与采样存储改造计划

> **状态**：计划中（未实施）。
>
> **定位**：本文拥有三处改造的目标契约：求角路径不构造轨迹（B1）、积分器中间量统一为 `double`（B2）、采样存储改为行优先单数组（C），以及随 C 同批落地的输出类型表面修正（§5.7）。分派结构、每一处接线的写法、验收断言与版本策略都在文内。`TrajectoryResult` / `TrajectorySample` / `FiringSolution` 的公共形态目前由 `api/trajectory/` 下各自的源文件拥有，本文落地后接管其存储形态、访问方式与字段契约。
>
> **本文自包含**：分派点、等价条件、体积账与验收断言都在文内给出，不要求先读其他文档。文中源码引用写成 `api/trajectory/<类>.java#符号`，同节后续用 `<类>#符号`；两个解算器同名的 `#forwardSolve` 每次都带类名。
>
> **落地顺序**：B1 → B2 → C，三个阶段各自独立提交、独立验收。B1 是纯结构改造（输出逐位不变），B2 是一次有意的数值变更，C 改存储形态。B2 若与 B1 合并，「结构改错」与「精度变了」这两种差异就再也分不开，逐位一致这道免费的回归判据随之失效。

---

## 一、问题与证据

### 1.1 观测量

在 Machine-Max 的 K17 连发场景采集 `/spark profiler start --thread * --interval 1 --timeout 20`，得到 `Machine-Max/run/config/spark/profile-2026-11-02_11.21.43.sparkprofile`。该报告 `Render thread` 窗口 12.18 s，其中：

| 栈帧 | self / 归属 | 占该线程 |
| --- | --- | --- |
| `java.util.ImmutableCollections#listFromArray` | 5.11 s self | 42.19% |
| `RealisticTrajectory#solveFiringAngle` 整条链 | 5.58 s total | 45.85% |
| `RealisticTrajectory#solveFullIntegrationSI` | 9 ms self | 0.07% |

最后一行的读数需要打折看：`solveFullIntegrationSI` 被 C2 内联进 `binarySearchAngleSI`（该帧 self 384 ms，同为内联折叠），因此"积分贵还是拷贝贵"无法从采样直接切分。可以确定的是 **`List.copyOf` 是一次独立于积分之外的全量遍历**，它不产生任何被保留的结果。

调用方是 `Machine-Max` + `client/render/gui/hud/molang/HudBallisticTable.java#resolve`：它沿距离取 128 个点，每点调一次 `RealisticTrajectory#solveFiringAngle`，后者在 `#solveFullFiringAngleSI` 内做平射与高抛各一次二分搜索。以 30mm 弹（`max_lifetime = 5.0`、`timeStep = 1/60`）计，`maxSteps = 300`，一次表求解的积分次数上限为 `128 × 2 × 50 = 12800` 次。

### 1.2 两层浪费

1. **求角不需要轨迹**。`#binarySearchAngleSI` 拿到 `TrajectoryResult` 后只读三样东西：最近采样点的时间与速度、目标水平距离处的弹道高度（`#heightAtHorizontalDistanceSI`）。两条扫描都是逐点、只看当前点的量，没有任何一步需要保留历史。而 `#forwardSolve` 每次都把整条轨迹物化成 `maxSteps + 1` 个采样点。
2. **采样点的存储形态偏重**。每个采样点是一个 record 加两个 `Vec3`：

| 组成 | 字节（压缩指针，8 字节对齐） |
| --- | --- |
| `TrajectorySample`：对象头 12 + `time` 4 + 两个引用 8 | 24 |
| 两个 `Vec3`：各自 12 + 3×8，对齐到 40 | 80 |
| `ArrayList` 槽位 | 4 |
| **合计** | **108**，有效载荷仅 52（6 个 `double` + 1 个 `float`）；C 阶段的每行 56（7 个 `double`），见 §5.2 |

外加 `List.copyOf` 在 `TrajectoryResult` 紧凑构造函数里再分配一个等长 `Object[]` 并整体复制一次。

折算到 §1.1 的调用方：一条 301 点的轨迹是 301 × 108 B ≈ **32.5 KB**；单次 `HudBallisticTable#resolve` 上限 12800 次积分，即约 **416 MB 临时对象**，且全部在几十毫秒内变成垃圾。`ImmutableCollections#listFromArray` 占到该线程 42%，来源就在这里——那 5.11 s 不是计算，是分配加复制。这两个数也是 §5.6 体积账的基准。

### 1.3 这不是"库太慢"

单次 `forwardSolve` 的开销本身在可接受范围；问题被调用方的乘法放大了——一次表求解等于上万次完整积分的分配量。改造的目标是让"只需要一个数"的调用方不必为"整条轨迹"付费，这同时是一条 API 造型问题。

## 二、范围与顺序

| 能力 | 本计划 |
| --- | --- |
| **阶段 B1**：求角路径融合积分与扫描，不构造 `TrajectoryResult`；中间量的声明类型保持现状；`DensityFunction` 改为基本类型 SAM | 做 |
| **阶段 B2**：求角路径四个积分器的中间量由 `float` 统一为 `double` | 做 |
| **阶段 C**：`TrajectoryResult` 改行优先单数组 `double[]` 存储，采样点不再是独立对象 | 做 |
| **随 C 同批**：`TrajectoryResult` 去掉以模拟终止点为前提的 `totalTime` / `terminalPoint` / `terminalVelocity` / `approximateHitNormal`，改 `closestTo(Vec3)`；`FiringSolution` 与 `#solveWithLead` 的契约修正；`BallisticConfig#simple` 补 `maxSteps` 重载（§5.7） | 做 |
| 去掉内部路径的 `List.copyOf` | 随 C 自然消失（C 之后内部路径不再有 `List`） |
| `float` 存储采样值以再省一半 | 不做，见 §八 |
| 改积分公式、换数值方案 | 不做 |
| SIMD / 多线程积分 | 不做 |

顺序是 **B1 → B2 → C**，三条理由：

1. 若先做 C，求角路径仍然要算 12800 条轨迹，只是每条从 32.5 KB 降到 16.9 KB；B1 直接把 12800 条降到 0 条。C 的受益方是真正需要整条轨迹的飞行推进路径。
2. B1 与 B2 都能让求角路径零分配，但只有 B1 能用"逐位一致"验收——它是纯调用结构改造。B2 必然改变末位，需要另一条判据（§七.2）。
3. C 改的是存储与访问方式，与求解器内部无关；放在 B1/B2 之后，验收只需比对"同一结果集的两种访问形态"。

## 三、阶段 B1 — 求角免物化（输出逐位不变）

### 3.1 需要改造的两处物化点

- **`#binarySearchAngleSI`**：每轮二分调用一次 `#forwardSolve`，然后扫一遍采样点求最近点、再扫一遍求目标水平距离处的高度。最多 50 轮。
- **`#solveFullFiringAngleSI` 的垂直分支**（`horizDist < 1e-6`）：同样调一次 `#forwardSolve` 再扫最近点。只改前者，垂直射击仍会物化，"求角路径零分配"就不成立。

不在 B1 范围内的是三个退化入口：`#solveLinearFiringSI`、`#solveParabolicFiringSI`、`#solveDecelerationFiringSI`。前两个是解析解，不经过积分循环。**`#solveDecelerationFiringSI` 不是解析解**——它调用一次 `#forwardSolve` 再扫最近点，每次反解固定物化 1 条轨迹，只是不在每轮二分里。它若要一并改造，形状与 `#binarySearchAngleSI` 的单次扫描相同（§3.4 第 2、3 条），但优先级低于上面两处：它的物化次数是 O(1)，不是 O(二分轮数)。

### 3.2 采样汇聚器：全基本类型签名

七个积分器（`#solveLinearMotionSI`、`#solveStraightDecelerationSI`、`#solveParabolicMotionSI`、`#solveFullIntegrationSI`，以及推力侧的 `#solveThrustNoDragSI`、`#solveThrustStraightDragSI`、`#solveThrustReducedSI`）目前都以 `samples.add(new TrajectorySample(...))` 形成采样点。把这一句换成对 `SampleSink` 的调用，签名一律用基本类型：

```java
/** 积分循环的采样出口；实现自行累积，不向外返回状态。 */
private interface SampleSink {
    void accept(float time, double x, double y, double z, double vx, double vy, double vz);
}
```

`t = 0` 的入参采样点同样走这个出口——每个积分器在循环前先 `accept(0f, …)` 一次，与循环内形成一个完整序列。

为什么不用 `Vec3`：`Vec3` 不可变，积分循环每步 `pos = pos.add(...)` 都会新建两个实例（80 B/步）。汇聚器若收 `Vec3`，探针路径就被迫跟着建这两个对象，"免物化"只免掉了采样点本身，正解路径的分配量也一分未减。收成"一个 `float`（`time`）+ 六个 `double`"之后，坐标与速度列不会被窄化（这也是 C 阶段 `double[]` 存储的前提，见 §4.3）。

两个实现，都由 `RealisticTrajectory` 私有持有：

- `AppendSink`：用 `new ArrayList<>(config.maxSteps() + 1)`（与现有七个构造点的初始容量一致，否则 301 点路径上要多做近十次扩容），内部 `new Vec3(...)` 与 `new TrajectorySample(...)` 后追加，产出的对象与现有构造点逐字等价，供 `#forwardSolve` 继续返回完整轨迹。
- `ProbeSink`：构造时接收 `target`、发射点 `origin`、`horizDir` 与 `targetDot`。`origin` 必须传：`dot` 是相对它算的（`p.subtract(origin).dot(dir2d)`），改写成 `p·dir2d − target·dir2d + targetDot` 虽然代数等价，舍入不同，§3.4 第 3 条的"原样搬进"就不成立。状态分三块。
  - 每轮复位（每次 `solveInto` 之前清）：`minDist`、`roundTime`、`roundVelocity` 的三个分量（共五个 `double`）、`heightAtTarget`（初值 `NaN`），以及水平距离插值的游标 `prevY`、`prevDot`。后两者是跨采样点的量：`#heightAtHorizontalDistanceSI` 以发射点为原点沿 `horizDir` 做点积，第一个 `dot >= targetDot` 的点要用前一点的 y 与 dot 做线性插值（`span < 1e-9` 时直接取当前 y），所以"只看当前点的七个值"不够，`accept` 必须能读到上一点。
  - 跨轮保留：`bestTheta`、`bestTime`、`bestVelocity` 的三个分量（共五个 `double`）、`bestIterations`、`improved`。
  - 外层持有：`bestDist` 仍在 `#binarySearchAngleSI` 的局部量里，与现在一致。

  提交协议：每轮扫描结束，外层比较 `sink.minDist() < bestDist`；命中时把 `bestDist`、当轮的 `theta` 连同 sink 里的 `roundTime` / `roundVelocity` / 当前计数器一起提交（写进 `best*`，置 `improved = true`）。一轮都没改进时 `improved` 保持 `false`，`#binarySearchAngleSI` 返回 `null`——现在的代码正是靠这个 `null` 让 `#solveFullFiringAngleSI` 判定"这条弧无解"，改成无条件构造就会凭空多出 `bestTime = 0` 的解。`FiringSolution` 在循环结束后用提交进来的四个值构造一次。

  `#binarySearchAngleSI` 现在是在"本轮 `minDist` 打破 `bestDist`"的那一轮现场构造 `FiringSolution`，而历史最优可能来自更早的轮次。把最优样本也每轮清掉，循环结束时只剩最后一轮的值，`flightTime` / `terminalVelocity` / `iterations` 全都变——§3.5 第 3 条要守的正是这一点。

选择汇聚器而不是给每个积分方案再写一份"探针版"，是为了避免七份复制体各自漂移；`ProbeSink` 需要的能力（距离、水平投影、高度插值）都由同一个出口表达。

**探针入口**：`#forwardSolve` 收 `Vec3` 返回 `TrajectoryResult`，探针路径不能复用它的签名。改造后把分派下移到私有方法 `solveInto(double sx, double sy, double sz, double vx, double vy, double vz, BallisticConfig config, DensityFunction density, ThrustProfile thrust, SampleSink sink)`：起点与初速按分量传，因为二分核每轮算出来的 `dir.scale(speed).add(shooterVelocity)` 本来就不需要装箱。它原样保留 `#forwardSolve` 的五条分支与判定顺序，七个积分器改为 `void` 返回、在出口调 `sink.accept(...)`；`#forwardSolve` 自己变成 `solveInto(..., new AppendSink(...))` 之后再包成 `TrajectoryResult`，二分核与垂直分支直接调 `solveInto(..., probeSink)`。仍以 `Vec3` 推进的三个退化积分器在**入口**把分量装一次（每次调用一次，不是每步）。分派只写一遍，"逐位一致"的判据因此收缩成一条：分支顺序不变。若复制一份分派而不是共用，条件顺序稍有出入就会挑到另一个积分器，而这种错误在结果上只表现为末位差异。

**内联风险与兜底**：每个积分循环的调用点是双态（`AppendSink` / `ProbeSink`），C2 依类型剖面做守卫内联，正常情况下每次采样多不出一次真实调用。验收里设一条基准（§七.5）；若基准显示未内联，兜底方案是只给 `#solveFullIntegrationSI` 与其推力变体写探针专用副本——这两条是完整二分里唯一的积分路径，其余入口不参与每轮求值。

### 3.3 积分核基本类型化

要让 §3.2 的零分配真正成立，求角路径会走到的四个积分器必须把推进变量从 `Vec3` 换成 `double` 局部量：`#solveFullIntegrationSI` 与推力侧的 `#solveThrustNoDragSI`、`#solveThrustStraightDragSI`、`#solveThrustReducedSI`。其中 `#solveThrustReducedSI` 的推进状态已经是四个 `double`（`u` / `w` / `along` / `height`），可作写法基准——但只借"状态标量化"这一半。它并非"只在出口构造 `Vec3`"：循环内每步还建一个 `pos` 专供 `#getDensity`（§3.5 第 4 条由三元重载消掉），出口再建两个。

更要紧的是不能借它的位置重建方式。它每步用 `new Vec3(start.x + horizDir.x * along, height, start.z + horizDir.z * along)` 从原点重建位置，而 `#solveFullIntegrationSI` 是 `pos = pos.add(vel.scale(dt))` 逐点累加；两种写法的舍入不同，重建值又是 `#getDensity` 的入参，差异会经密度放大到整条轨迹。四个方法改造后仍按各自的原有累加顺序推进，`#getDensity` 必须收到同一个值。

另三个退化积分器（`#solveLinearMotionSI`、`#solveParabolicMotionSI`、`#solveStraightDecelerationSI`）保留 `Vec3` 推进，只在出口把分量拆给汇聚器，B1 不改造它们。`#solveStraightDecelerationSI` 确实会经 `#solveDecelerationFiringSI` 被间接走到，但那条入口的物化次数是 O(1)（§3.1），且它不参与每轮二分，改与不改都不影响 B1 的验收结论。这样改动面停在四个方法上。

**B1 的唯一硬约束：中间量的声明类型原样保留。** 推进状态从 `Vec3` 的 `double` 分量读进 `double` 局部量是精确的（不改变任何一位），但 `#solveFullIntegrationSI` 里的 `float vMag = (float) vel.length();`、`float dragFactor = halfRhoRef * rho * vMag;`，以及 `#solveThrustStraightDragSI` 里 `-halfRhoRef * density.getDensity(pos)` 这一步 **float 乘法**必须保留（该方法的 `speed` 与 `accel` 本身已是 `double`，别去找一个不存在的 float 变量）。把 `vMag` 直接写成 `double` 会改变末位，§七.1 的逐位一致立刻失败——这正是 B2 单独成阶段的原因。

同一张清单还包括 `#buildDirectionSI` 里的 `float cosT = (float) Math.cos(theta);` 与 `float sinT = (float) Math.sin(theta);`。§3.5 第 1 条要求把每轮方向内联掉 `Vec3`，但内联不等于换精度：`cosT` / `sinT` 仍是 `float` 局部量，只有由它们算出的三个分量存进 `double`（`dirx = horizDir.x * cosT`、`diry = sinT`、`dirz = horizDir.z * cosT`），再作为 `solveInto` 的实参。写成 `double cosT = Math.cos(theta)` 会让四个 `aim-*` 用例的每轮初速在末位全变，逐位门禁直接失败。

**乘加的结合顺序也要保留。** `pos.add(vel.scale(k))` 对应的是先把步长乘积算成一个局部量 `k`，再逐分量 `px += vx * k`；写成 `px += vx * speed * dt` 会被求值为 `(vx * speed) * dt`，结合顺序不同即不逐位。`Vec3#scale` 与 `Vec3#add` 本身是分量级乘加，与逐分量写法逐位等价，这是唯一被允许的改写。

### 3.4 语义等价条件

改造后 `#binarySearchAngleSI` 的返回值必须与现在逐字段一致，包括 `FiringSolution#iterations`。为此四条约束写死：

1. **采样点集合不变**：仍是 `0 .. maxSteps` 共 `maxSteps + 1` 个点，`time = i · timeStep`，`i = 0` 处为入参位置与速度。
2. **最近点判据不变**：`(float) position.distanceTo(target)`，严格 `<` 比较，先到先得（等价关系保留，不改成 `<=`）。
3. **高度插值规则不变**：把 `#heightAtHorizontalDistanceSI` 的遍历逻辑原样搬进 `ProbeSink`——以发射点为原点，沿水平方向做点积，第一个 `dot >= targetDot` 的点用 `span < 1e-9` 守卫后按线性插值取高度；全程未越过则记 `NaN`。
4. **越界语义不变**：`NaN` 仍在 `#binarySearchAngleSI` 里按"未越过 / 过冲"处理，即 `overshoot = !reached || heightAtTarget > target.y`。

`ProbeSink` 在 `#binarySearchAngleSI` 入口创建一次，跨最多 50 次迭代复用。

### 3.5 零分配的实际边界

`SampleSink` 只消掉采样点本身。探针路径上另有六处分配点，必须一并处理，否则 §七.4 的"采样分配为 0"不成立：

1. `#binarySearchAngleSI` 每轮都要算 `dir = #buildDirectionSI(horizDir, theta)` 来求初速，但不需要那个 `Vec3`：`cosT` / `sinT` 仍按原样取 `float`（§3.3 的硬约束），由它们算出的三个分量存进 `double`，直接作为 `solveInto` 的实参；收敛后用 `bestTheta` 调一次 `#buildDirectionSI` 交给 `FiringSolution`。循环内因此零 `Vec3`——若保留每轮一个 `dir`，最坏 50 个，§七.4 的常数额度就不成立。
2. `dir.scale(speed).add(shooterVelocity)` 每轮建一个 `worldVel`——分量在 `double` 里算好，直接作为 `solveInto` 的六个实参传下去。
3. 每次 `minDist` 改进都 `new FiringSolution(...)`——改为按 §3.2 的提交协议把四个值写进 sink，迭代结束建一次。`bestIterations` 不能省：现有代码在该轮就把当时的计数器当第五个实参传进去，推迟构造后只拿循环末值会改结果。
4. `#solveThrustReducedSI` 每步 `new Vec3(...)` 只为传给 `#getDensity`——由 §3.6 的基本类型重载消掉。
5. `#solveFullFiringAngleSI` 的垂直分支同理，但只适用第 2、3 条：那里 `dir` 是常量 `(0, ±1, 0)`，没有 `theta`、也不调 `#buildDirectionSI`，`FiringSolution#direction` 由外层直接给，`ProbeSink` 不参与方向重建；它不读 `heightAtTarget`，`horizDir` / `targetDot` 传零即可，`improved == false` 时返回 `List.of()`（对应现在的 `if (bestSample == null) return List.of();`）。
6. 推力路径上还有每**调用**一次的 `Vec3`：`#solveThrustNoDragSI` 与 `#solveThrustStraightDragSI` 的 `Vec3 dir = velocity.normalize()`、`#solveThrustReducedSI` 的 `Vec3 horizDir = horizSpeed > 1e-12 ? new Vec3(...) : new Vec3(1, 0, 0)`。`solveInto` 每轮调一次，推力激活时这就是每轮 1 个、最坏 50 个/弧，与"常数"直接冲突。改法与第 1 条同：方向的三个分量存 `double`，除法保持 `coordinate / len` 的逐分量形式（不要改写成乘倒数，末位不同）。两个 `velocity.normalize()` 站点还要连带保留 `Vec3#normalize` 的短路——长度 `< 1.0E-4` 时返回零向量，而 `#forwardSolve` 的推力门禁只要求 `length() > 1e-10`，两者之间的输入会走进这个分支。`#solveThrustReducedSI` 的分母不是速度：`horizSpeed = Math.hypot(velocity.x, velocity.z)` 与 `horizSpeed > 1e-12` 的判断、`new Vec3(1, 0, 0)` 的 else 分支都原样保留（`Math.hypot` 与 `Math.sqrt(x*x+z*z)` 不逐位相同），只有 `horizDir` 这个对象变成三个 `double`；位置重建 `start.x + horizDir.x * along` 不变。

**每轮迭代清零**之后，单次 `#binarySearchAngleSI` 的分配是常数：1 个 `FiringSolution` + 其 2 个 `Vec3`。再往上，每次 `#solveFiringAngle` 还有一组常数对象（`diff`、`horizDir` 及其 `normalize()`、两元素结果列表与它的内部数组），加上两个 `ProbeSink`（平射、高抛各一）与每条产出解 3 个，单次反解的对象数与迭代次数无关，在 10~13 之间（只出平射解 10，两条弧都出解 13）——§七.4 按这个口径验收，不写"除……外无分配"。

收敛后的 `FiringSolution#direction` 与现有代码的 `buildDirectionSI(horizDir, theta)` 必须逐位相同——只是推迟构造，不改变输入。

### 3.6 密度查询：`DensityFunction` 改基本类型 SAM

`#solveThrustReducedSI` 每步都要用当前位置查密度，而 `DensityFunction#getDensity` 只收 `Vec3`；它每步为此新建一个 `Vec3`。这条不解决，"探针路径零分配"就只在非推力路径成立。

改法是把基本类型形态定为接口的抽象方法，`Vec3` 形态降为便利重载：

```java
@FunctionalInterface
public interface DensityFunction {
    float getDensity(double x, double y, double z);

    /** 便利重载：持有 Vec3 的调用方直接传。 */
    default float getDensity(Vec3 position) {
        return getDensity(position.x, position.y, position.z);
    }
    // constant / standardBarometric / MC_OVERWORLD / SEA_LEVEL / VACUUM 一并改成三元 lambda
}
```

这样用户仍只写一个 lambda（`(x, y, z) -> ...`），求解器内部零分配，也不需要对每个自定义实现再要求一个可选覆写。改调三元重载的是实际查密度的四个调用点：`#solveStraightDecelerationSI`、`#solveFullIntegrationSI`、`#solveThrustStraightDragSI`、`#solveThrustReducedSI`。`#solveThrustNoDragSI` 的签名里没有 `DensityFunction`，不涉及；它有 `Vec3` 状态，改造时顺手把分量拆开即可。

代价是一次源码级不兼容：现有的 `pos -> ...` lambda 要改成 `(x, y, z) -> ...`。这是 B1 阶段唯一的公共 API 形态变更（§五 的 `TrajectoryResult` 另计），写进 §九。**接口文件自己的类注释也要改**：`DensityFunction` 的示例是 `DensityFunction mcAtmo = pos -> DensityFunction.standardBarometric(pos.y, level.getSeaLevel(), 8500);`——既用了单参 lambda，又给只有两个形参的 `standardBarometric(float seaLevel, float scaleHeight)` 传了三个实参。改成 `(x, y, z) -> DensityFunction.standardBarometric(level.getSeaLevel(), 8500)`；顺带把 `pos.y` 这个"以高度代密度"的错误示例修掉。

### 3.7 公开面

`#forwardSolve` 仍返回完整 `TrajectoryResult`，`MinecraftTrajectory` 的五个便捷入口（`#arrowTrajectory`、`#snowballTrajectory`、`#fireballTrajectory`、`#potionTrajectory`、`#bottleTrajectory`）不受影响。除 §3.6 的 `DensityFunction` 之外，本阶段的公共 API 形态不变。

`MinecraftTrajectory` 的反解路径（`#binarySearchAngle`）同样逐轮物化，但形状不同：每轮 `#forwardSolve` 之后用 `#estimateHorizontalProgress`（目标高度处的水平进度比，含相邻两点插值）与 `#checkHorizontalOvershoot`（水平投影点积）两条判据调整区间，没有 `RealisticTrajectory` 那套"目标水平距离处的高度插值"。`SampleSink` 的"一 `float` + 六 `double`"签名与参数模型无关，可以复用，但 `ProbeSink` 的字段不够用：MC 需要"目标高度处进度比"（跨采样点，要前一点的 y 与进度）与"是否越过目标水平投影"（只要发射点算出的 `targetDot` 与当前点）两项。本阶段不纳入它，理由是证据而不是难度：§1.1 的性能采样来自 `RealisticTrajectory` 的调用方，MC 路径的实际调用频次低一个数量级，收进来只会把 B1 的积分器改造面从四个翻到七个，而 B1 的全部价值在于"小改动 + 逐位一致"。若将来 MC 路径也出现在性能采样里，按 §3.2 与 §3.5 的形状补做即可，不必重开设计。

## 四、阶段 B2 — 中间量统一为 `double`

### 4.1 改什么

只改 §3.3 列出的四个积分器内部：把 `vMag`、`dragFactor`、`aT`、`halfRhoRef` 从 `float` 声明改为 `double`，与推进状态的宽度一致。**只改声明不会改算术宽度**，这是本节最容易做错的地方：

- `#solveFullIntegrationSI` 的 `float vMag = (float) vel.length();` 要连 `(float)` 强转一起删，否则 `vMag` 仍然只有 float 精度；
- `#solveThrustNoDragSI` 与 `#solveThrustReducedSI` 循环里的 `float aT = forceN / mass;` 右值两个操作数都是 `float`，除法先在 float 里完成，必须显式转 `double` 再除（`forceN` 来自 `thrust.forceAt(stepStart)`、`mass` 来自 `thrust.massAt(stepStart, config.mass())`，两者都返回 `float`，不要顺手改它们的返回类型——§3.3 的"中间量声明类型原样保留"对它们同样适用）；
- `float halfRhoRef = 0.5f * dragCoefficient * area / mass;` 同理——`0.5f` 要写成 `0.5`，三个操作数至少一个先转 `double`。

`rho` 不在可改之列：它的类型由 `DensityFunction#getDensity` 的返回类型定死（仍为 `float`），把局部量声明成 `double` 只是加宽一个 float 值。§4.3 把它列进"被窄化为 `float` 的量"是对的。要动它得先改接口返回类型，那是另一条公共 API 变更，不在 B2 内。

`#solveThrustStraightDragSI` 里 `-halfRhoRef * density.getDensity(...)` 这个乘积在升级后仍要按原顺序求值（`halfRhoRef` 与密度先乘，再乘速度分量），只是宽度变了。采样出口的坐标与速度列已经是 `double`，`time` 仍是 `float`；公共类型（`TrajectorySample#time`、`FiringSolution#flightTime`、`BallisticConfig` 的字段）**保持 `float` 不动**——它们是时长与参数，不是世界坐标，改动属于另一条公共 API 线。采样时刻继续按 `i · dt` 的 `float` 乘法算，不要顺手升成 `double`：那会改变 `TrajectorySample#time` 的末位，§七.1 的逐位比对立刻失败。

B2 之后四个积分器的中间量除 `rho` 外全部是 `double`；`#solveThrustReducedSI` 的推进状态 `u` / `w` / `along` / `height` 本来就是该形态，它的 `aT`、`halfRhoRef` 与其余三个方法的 `vMag`、`dragFactor` 一并升级。`rho` 的宽度由 `DensityFunction#getDensity` 的返回类型定死，保持 `float`。

### 4.2 数值影响与验收

B2 会改变输出末位，因此不能用逐位一致验收。量级预估：一次 `float` 舍入是相对 1e-7，系统性偏差在 10 s 量级的弹道上累计到亚毫米级；最终容差以实测为准（§七.2），要求给出最大偏差而不是估计值。

这是一次**预期的数值变更**，需要在提交说明与版本说明里写明；消费方代码无需改动，但若有人缓存过逐位结果（无此类调用方），需要重算。

### 4.3 远原点精度的真实边界

**远原点精度由"世界坐标的承载宽度"决定，不由积分器中间量决定。** 现状盘点：位置与速度状态是 `Vec3`（`double` 分量），`TrajectorySample` 存 `Vec3`；求角路径上被窄化为 `float` 的量只有 `vMag`、`dragFactor`、`rho`、`aT`、`halfRhoRef` 这类**每单位量**，以及 `#binarySearchAngleSI` 里相对目标测得的 `minDist`。它们都不携带世界坐标，误差只与量本身有关，与出发点离原点多远无关。

远原点真正的两条硬约束因此落在别处，写在本计划里：

1. **坐标列必须是 `double`**：`SampleSink` 的 `x` / `y` / `z`、`TrajectoryCursor` 的坐标访问器、`TrajectoryResult` 的存储数组（§五）。`float` 在 `|x| = 3e7`（世界边界量级）处的 ulp 约 2 m，在 `1e5` 处约 8 mm。
2. **水平分量不得窄化。** `x` / `z` 的量级可达世界边界（`3e7`），`float` 在那里的 ulp 约 2 m；`y` 受世界高度限制（约 ±320），`float` 的 ulp 约 3e-5 m。因此 `MinecraftTrajectory#estimateHorizontalProgress` 的分界是：相对发射点的 `x` / `z`、以及进度比值全部在 `double` 里算，`targetY` / `prevY` / `currY` 这几个高度阈值保留 `float`。判断标准是**量的量级**，不是"是不是坐标"。

所以 B2 的收益是另外两条：消除四个积分器之间的宽度不一致；让内部算术与状态宽度一致，避免"同一物理量在不同分支宽度不同"的认知负担。把它当成远原点修复会漏掉真正该改的地方。

### 4.4 与消费方的一致性

`docs/弹道求解器-推力项设计.md` §三 要求预测与调用方积分器同式。该约束目前只覆盖离散格式；B2 之后求解器的中间量宽度与调用方（Machine-Max 的 `ProjectileManager#updateProjectiles`）是否一致需要单独确认：若调用方以 `float` 计算阻力项，两边会在 1e-7 相对量级分家（亚毫米级，可接受，但应登记为已知偏差），或让调用方一起升 `double`。

## 五、阶段 C — 采样存储行优先单数组

### 5.1 目标形态

`TrajectoryResult` 从 record 改为 `final class`，内部一个行优先数组（每个采样点占连续的 7 个 `double`）：

```java
public final class TrajectoryResult {
    private static final int STRIDE = 7;          // t, x, y, z, vx, vy, vz
    private final double[] data;                  // 长度 ≥ count × STRIDE
    private final int count;

    public int size();
    public TrajectoryCursor cursor();             // 每次新建一个游标；遍历本身零分配
    public List<TrajectorySample> toSampleList(); // 显式物化

    public TrajectorySample first();              // 发射时刻
    public TrajectorySample last();               // 数组里最后一个采样点
    public TrajectorySample closestTo(Vec3 point);// 全程离 point 最近的采样点
}
```

```java
public final class TrajectoryCursor {
    public boolean advance();                     // 前进一格，越界返回 false
    public int index();
    public double time();
    public double x(); public double y(); public double z();
    public double vx(); public double vy(); public double vz();
    public Vec3 position();                       // 需要时才建
    public Vec3 velocity();
    public double distanceTo(Vec3 point);         // 基本类型运算，不建 Vec3
}
```

`equals` / `hashCode` 按 `count` 与 `data` 的前 `count × STRIDE` 项实现，与 record 形态下的值语义对齐——改存储不该顺带改变相等性。数组尾部的多余容量不参与相等性判断（§5.4）。

### 5.2 为什么行优先单数组

- **56 B/点，7 个值连续**：整条轨迹占 `count × 56 B` 的连续内存，顺序扫描时每个缓存行只走一遍（行首按 8 字节对齐、不按 64 字节对齐，单个采样点可能跨两条行，但顺序读不产生额外流量）。
- 现有消费方全部是"逐点读全状态"：`#binarySearchAngleSI` 读位置算距离，飞行推进读位置与速度判命中。没有"只读某一列"的热点，平行的列数组只会把一次顺序访问拆成两三次。
- 一条轨迹一次分配（`count · 7` 个 double），而不是每点三次分配。
- **为什么不是 SoA**：SoA 只在"每次只读其中几列"或"跨点向量化"时才有账可算。这里消费方逐点读全状态；求角路径中只读位置的那条扫描在 B1 之后不再物化轨迹，热点随之消失。改成 7 个平行数组等于把一条顺序流拆成 7 条，还把"一条轨迹一次分配"变成 7 次。
- **为什么不做 8 列补齐**：补齐到 `STRIDE = 8`（64 B）能让每个采样点独占一个缓存行，代价是 14% 的内存与一个恒为 0 的补齐列；顺序扫描由硬件预取合并，收益接近零，不值得让 `equals` 与体积账多一条例外。

### 5.3 为什么舍弃 `samples()`

record 的 `samples()` 是个陷阱：调用方写 `for (var s : result.samples())` 时，要么返回物化后的 `List`（成本回到旧形态），要么返回视图（`equals` / `hashCode` 与遍历耗时都依赖访问顺序）。两者都让"这次调用很便宜"的错觉得以成立。

替代是 `toSampleList()`——名字本身声明了分配。`TrajectorySample` 保留为对外 DTO，只由 `toSampleList()`、`first()` / `last()` 与 `closestTo()` 生产。

迁移面：

- `src/main`：B1 之前 10 处 `result.samples()`（`RealisticTrajectory` 4 处、`MinecraftTrajectory` 6 处）；B1 会换掉其中 3 处（二分扫描、垂直分支、`#heightAtHorizontalDistanceSI`），C 动工时剩 7 处。顺序遍历改用 `cursor()`；其中"扫到最近点"这一类（`#solveDecelerationFiringSI`，B1 未覆盖该入口，见 §3.1）直接用 `closestTo`，不物化列表。`MinecraftTrajectory#estimateHorizontalProgress` 已经是 `first()` 初始化 `prev`、循环内 `get(i)` 的形状，只把取值换成游标，`prev` 局部量保留。**另有构造点不在读取之列**：B1 之前共 12 处 `new TrajectoryResult(samples)`——`RealisticTrajectory` 8 处（B1 把它们收成 `#forwardSolve` 一处，再由 §5.4 ¶1 换成写数组）、`MinecraftTrajectory` 4 处（§5.4 ¶2 的包内缓冲）。C 动工时剩 5 处：`RealisticTrajectory#forwardSolve` 1 处 + MC 4 处。落地时重新 `grep`，不沿用这里的数字。
- `src/test`：`RealisticTrajectoryInvariantTest` 在 alpha.14 上约 31 处 `result.samples()`（含 `#interpolatedHeight(List<TrajectorySample>, …)` 与 `#sampleAt` 的按下标取值）；alpha.15 的推力分段计划会新增 T10–T17 用例，计数还会涨。迁移方式不变：改 `toSampleList()`，辅助方法继续接收 `List`。同类迁移还有该类的 `CONSTANT_DENSITY = pos -> 1.2f`：抽象方法改成三元后它不再能编译，要改成 `(x, y, z) -> 1.2f`，且 §七.1 的基线用例必须沿用同一个常量。落地时重新 `grep` 计数，不沿用本节的数字。

### 5.4 构造面与提前终止

**构造面**：`TrajectoryResult` 不再提供 `List<TrajectorySample>` 的公开构造器——采样点不再是存储单元，外部构造一个空壳没有意义。求解器经包内构造器直接写 `double[]`；`toSampleList()` 是唯一的"List 形态"出口。若下游确实需要自建结果（当前无此需求），另开一个包内工厂，不暴露公开构造器。

**正解路径怎么写到数组里**：C 阶段把 §3.2 的 `AppendSink` 换成持有 `double[]` 与 `count` 的实现——构造时按 `(config.maxSteps() + 1) · STRIDE` 预分配，每次 `accept` 写一行并自增 `count`，`#forwardSolve` 用包内构造器 `new TrajectoryResult(sink.data(), sink.count())` 收尾。提前返回的路径（直线减速）因此自然得到 `count < maxSteps + 1`，尾部空闲容量不进入任何对外语义。这一段不写，§5.6 的"1 次分配 / 16.9 KB"就只是口号：按 §3.2 原样保留 `ArrayList` 版本，B1 之后正解路径一点也不会变。

**`MinecraftTrajectory` 是同一处陷阱的另一半。** 它有三个积分器、四处 `new TrajectoryResult(samples)`：`#solveLinearMotion` 一处、`#solveStraightDeceleration` 两处（含速率归零的提前返回）、`#solveFullIntegration` 一处。而 §3.2 的两个 sink 是 `RealisticTrajectory` 私有的，§3.7 又明确不把 MC 纳入 `SampleSink`。删掉 `List` 构造器之后这四处直接编译不过。C 阶段的最小处理：把写数组的能力提到包内（例如包内类 `TrajectoryBuffer`，按 `maxTicks + 1` 预分配、`append` 自增 `count`），MC 的三个积分器改调它并用包内构造器收尾——只要求它写同一份行优先数组，不要求它走 `solveInto` 的探针路径。

**提前终止与容量**：`#solveStraightDecelerationSI` 在速率归零时提前返回，实际点数少于 `maxSteps + 1`。取"预分配 `(maxSteps + 1) · STRIDE`、`size()` 只看 `count`"这一条：单次分配，代价是数组尾部有未使用的容量，而它不进入任何对外语义（`size()`、`equals`、`toSampleList()`、游标都只认 `count`）。备选方案是 growable 缓冲再 `Arrays.copyOf` 到 `count · STRIDE`，两次分配、无空洞——不用，因为它把 §七.4 的"1 次分配"变成 2 次，而省下的容量是短生命周期对象的一部分。

**便捷查询**：`first()` / `last()` / `closestTo()` 保留 DTO 语义，是明确的分配点（每次 1 个 `TrajectorySample` + 2 个 `Vec3`）。其中 `closestTo` 由游标遍历实现，只在返回时建对象；距离判据与 §3.4 第 2 条同一口径（`(float) position.distanceTo(point)`、严格 `<`、先到先得），这样它和探针路径扫出的是同一个样本——§5.3 把 `#solveDecelerationFiringSI` 的最近点扫描交给它，两条路必须选出同一点，否则同一发弹在不同分支里会给出不同的"最近接近点"。三个访问器只在构造 DTO 时把 `t` 从数组里的 `double` 窄回 `float`（§4.1 要求 `TrajectorySample#time` 保持 `float`）；`totalTime()` 被去掉与窄化无关，理由是 §5.7 一的终止点语义。

### 5.5 游标的遍历约定

`#cursor()` 每次调用分配一个游标对象，约定新游标停在 `-1`，`#advance()` 先自增再判界，因此 `while (cursor.advance()) { … }` 恰好遍历 `0 .. count-1`。游标绑定创建它的结果，不提供随机访问——需要按下标取点的调用方用 `toSampleList()`。

### 5.6 体积账

| 路径 | 现状 | B1 + B2 后 | C 后 |
| --- | --- | --- | --- |
| 求角（每次二分迭代一次的积分） | 32.5 KB / 每点 3 个对象 + 容器 | **0 采样分配**（每次搜索另有 1 个 `FiringSolution`） | 0 采样分配 |
| 正解（一次 301 点 `forwardSolve`） | 32.5 KB / 同上 | 32.5 KB / 同上 | **16.9 KB / 1 次** |

B1 与 C 互补而非重叠：B1 消掉的是求角路径的**次数**（一次表求解上万次积分，全部不分配），C 降低的是正解路径的**单次成本**（每点 3 个对象压到 1 个数组）。正解路径在 B1 之后看不出变化，因为 `AppendSink` 仍要物化采样点——这也是 B1 排在 C 前面的理由。

### 5.7 输出类型的表面修正（与 C 同批）

C 要整体重写 `TrajectoryResult`，同一批把它和 `FiringSolution` 的公共表面定下来。七处修正都来自调用方预演：照现有表面写代码，要么必然取到无意义的数，要么踩空指针。

**一、去掉以「终止点」为前提的四个访问器。**

`#totalTime`、`#terminalPoint`、`#terminalVelocity`、`#approximateHitNormal` 全部读 `last()`，而 `last()` 是**模拟终止点**：两个解算器只以 `maxSteps` / `maxTicks` 为终止条件（直线减速路径另在速率归零时提前返回），都不判落地、不判命中（`api/trajectory/TrajectoryResult.java` 的类注释已明说）。后果是具体的：

- `totalTime()` 就是 `last().time()`。跑满步数时它等于 `maxSteps × timeStep`，由入参算出、不含弹道信息；直线减速路径提前返回时它是"减速到停"的时刻，同样不是落点；
- `terminalPoint()` 是"步数用尽的那一点"。弹丸若在步数用完前已经落地或已经命中，它是地面之下的位置；
- 把它喂给 `BFDamageContext#hitPoint` / `#hitVelocity`，得到的是穿地之后（或命中之后继续飞行）的状态。

替代是 `closestTo(Vec3 point)`——全程离 `point` 最近的采样点，从发射点扫到尾，距离相同先到先得。它回答"弹道最接近这一点时，弹丸在哪、飞了多久、速度多少"，而这正是调用方真正有的问题：命中点通常来自调用方自己的射线检测或碰撞盒解析，不来自求解器。返回 `TrajectorySample`，与 `first()` / `last()` 同为显式物化点。

`first()` 与 `last()` 保留。前者是发射时刻；后者是数组里最后一个采样点。它不表示"跑满了步数"——直线减速路径在速率归零时提前返回，而 `TrajectoryResult` 不保存 `maxSteps`，调用方无法从结果本身分辨是否被截断；需要这个判据，自己拿 `config.maxSteps()` 与 `size()` 比。

**二、法线近似挪到它真正的归属。**

`approximateHitNormal()` 是**逐点**的量（该点速度反方向归一化）。挂在结果类型上等于隐含"整条弹道只有一个法线"，而结果类型并不知道哪一个点是命中点。改为 `TrajectorySample#approximateHitNormal()`，调用方拿到 `closestTo(point)` 的样本后自行调用。`TrajectorySample` 因此在 C 之后仍是对外 DTO，并新增这一个派生方法。

**三、`FiringSolution` 的两个 `Vec3` 都是世界坐标，但组合规则要写进 Javadoc。**

`direction` 是世界坐标轴下的炮口指向单位向量（含方位角与仰角），`terminalVelocity` 是世界坐标系下的速度矢量；二者都不是"发射者坐标系"里的量。反解内部按 `worldVel = direction × speed + shooterVelocity` 求值，因此**世界初速不等同于 `direction × speed`**：发射者自身有速度时漏掉加项，弹丸静默偏后，不报错、不越界，只是打不准。

这条规则目前分散在 `docs/wiki/5-外弹道工具/5.3-瞄准反解.md`、`docs/wiki/4-协议内幕/4.4-弹道计算原理.md`、`docs/wiki/5-外弹道工具/5.4-动目标提前量.md` 与 `docs/外弹道设计文档.md` 四处，以 5.3 为所有者，其余改为指向它。record 的字段注释却读起来像"直接乘标量即可"。改法：`@param direction` 写明"世界坐标轴下的炮口指向单位向量，不含发射者速度；世界初速 = direction × speed + shooterVelocity"。

`@param terminalVelocity` 同样要去掉"命中目标时"，但替换措辞不能写成"取自最近接近目标的采样点"——三条退化入口没有最近点可言：`#solveLinearFiringSI` 直接把发射世界速度 `worldVel` 当作末速返回，`#solveParabolicFiringSI` 按 `worldVel.y − g·flightTime` 闭式推一步，只有 `#solveDecelerationFiringSI`、垂直分支与 `#binarySearchAngleSI` 才真的取采样点的速度。写成"最近接近目标那一时刻的世界速度；解析分支用闭式解给出同一量"才两种来源都覆盖。

**四、`FiringSolution#iterations` 在两个入口含义不同，必须写明。**

完整路径上它是**最优轮次的零基索引**：值在 `iterations++` 之前读出，首轮就收敛记 `0`；另外三类出口传的是字面量 `0`——三条退化入口（`#solveLinearFiringSI`、`#solveParabolicFiringSI`、`#solveDecelerationFiringSI`）与完整路径的垂直分支（`horizDist < 1e-6`，`#solveFullFiringAngleSI` 里那条 `new FiringSolution(dir, bestSample.time(), bestSample.velocity(), false, 0)`）。`#solveWithLead` 里它换成提前量外层迭代的轮次，内层二分的轮数被丢掉。同一个字段承担两种计数，改字段名会动到 §七.1 的基线编码与全部解记录，收益不抵成本；在 Javadoc 里写清即可，且要与 §3.5 第 3 条用同一句话。

**五、`#solveWithLead` 可能返回 `null`。**

三个重载都是这个形状：`api/trajectory/RealisticTrajectory.java#solveWithLead` 的两个（十参、带推力的十一参）与 `api/trajectory/MinecraftTrajectory.java#solveWithLead` 的一个。首轮 `#solveFiringAngle` 就返回空列表时 `bestSolution` 尚未赋值，方法直接 `return bestSolution`。而 `@return` 读起来像必然非空——十参版写"即使未收敛也返回最优猜测"，带推力的十一参版更进一步写着"距离不足最小射程时返回最近接近解"，与代码正相反。调用方照文档写 `lead.direction()` 必空指针。

修正只做在契约上，并且要把这条"最近接近解"的承诺删掉：`@return` 明写"首轮即无解时返回 `null`，后续轮无解时返回上一轮的解"，要求调用方判空。给成因列准：`#solveFiringAngle` 的空列表只来自几处退化守卫——目标与炮口重合（`horizDist < 1e-6` 且 `diff.y == 0`）、抛物线判别式 `< 0`、垂直分支 `flightTime <= 0`；完整二分的两条弧不会返回空。所以"最小射程"不是成因，别写进契约。返回值不改——把 `null` 一律换成"最近接近解"需要先定义"打不出去的一发给什么方向"，那是另一种语义，而且会把"这一发根本打不出去"这个事实从返回值里抹掉。

**六、`BallisticConfig#simple` 补一个 `maxSteps` 重载。**

`simple` 固定 `maxSteps = 200`（= 10 s）。助推弹的飞行时间显著长于同射程的无动力弹，远程射击会先撞到步数上限：`#heightAtHorizontalDistanceSI` 拿不到目标水平距离就返回 `NaN`，二分的"射程不足 / 过冲"判据随之失真（§3.4 第 4 条）。补 `simple(cd, caliber, mass, gravity, maxSteps)`，四参版委托到它并传 200，既有调用点不变。

**七、`MinecraftTrajectory` 的"入 m/tick、出 m/s"要写明不能回喂。**

`#forwardSolve` 的 `velocity` 参数是 m/tick（与 `Entity#getDeltaMovement` 一致），而返回的 `TrajectorySample#velocity` 已乘 20 换成 m/s，`position` 始终是世界米。于是把 `last().velocity()` 直接回喂给 `#forwardSolve` 会静默放大 20 倍——不报错，只算出一条长得多的弹道。两处的 Javadoc 各自说明了单位，但没有一句把它们放在一起说明不能互喂；补这一句即可，不改任何签名。`RealisticTrajectory` 全 SI，不存在这个不对称。

同一处还有第二个单位裂缝，比速度那条更严重：`FiringSolution#flightTime` 在 `MinecraftTrajectory` 里并不总是秒。二分与减速分支取 `bestSample.time()`（秒），另外三处产出 tick 量级：

| 生产者 | 现状 | 改法 |
| --- | --- | --- |
| `#computeParabolicFlightTime` | `horizDist / \|worldVel.y\|`——横向距离除以**竖直**速度，量纲上就不是飞行时间；两个分支的 `if` 还完全相同 | 按水平速度算 `horizDist / \|worldVel.xz\|`，再 `/ 20` 换成秒 |
| `#solveLinearFiring` 的两条内联分支 | 已是"距离 / 速度"（`\|diff.y\|/\|worldVel.y\|` 或 `horizontalDistance()/\|worldVel.xz\|`），只缺 tick→秒 | 两式各补 `/ 20` |
| `#computeParabolicVerticalFlightTime` | 同样以 tick 为单位 | 补 `/ 20`，或抽一个 `flightTimeSeconds(...)` 让三条退化入口共用 |

`FiringSolution` 的字段注释却写着"预计飞行时间（s）"。而且已经有消费方按错的口径在用它：`MinecraftTrajectory#solveWithLead` 取 `sol.flightTime()` 之后直接做 `targetVelocity.scale(flightTime)`，而 `targetVelocity` 的 `@param` 明写 m/tick——秒被当成 tick，提前量少算 20 倍。完整路径今天就带着这个错误，把解析分支统一成秒之后它会在三条分支上一律错。所以这一条要连消费者一起修：`#solveWithLead` 内层改用 `flightTime * 20` 当 tick（或把 `targetVelocity` 换成 m/s 再乘秒），并新增一条 MC 提前量闭环断言——解出的 `direction` 回代后与目标预测点的距离小于容差，只比较量级抓不到 20 倍偏差。

这一条改变 `MinecraftTrajectory` 的输出，属于独立缺陷修复，不并入 B1/C，单独提交。

前六条不改变任何数值：删四个访问器、加一个访问器、挪一个访问器、改四处注释、新增一个重载，与 C 同批释放——C 本来就在重写 `TrajectoryResult`，分批只会让 breaking change 出现两次。第七条含一处数值变更（`flightTime` 的单位），单独提交、单独回归，不并入 B1/B2/C，也不进 §七.3 的逐位判据。

## 六、为什么不能在 C 之前止血

`TrajectoryResult` 是 record，`List.copyOf` 写在紧凑构造函数里，而紧凑构造函数就是规范构造函数——JLS 要求任何其它构造函数都委托到它，静态工厂同样只能调它。所以"加一个跳过拷贝的包内工厂"做不到，`List.copyOf` 与采样点对象只能随 C 一起消失。这一节保留为结论，避免实施时在 B2 之后又绕回同一个想法。

代价是：B1/B2 之后，飞行推进路径（`#forwardSolve` 单次 301 点）仍然是每点 3 个对象 + 容器 + 一次等长数组拷贝，直到 C 落地。求角路径不受影响——它已经不物化了。

## 七、验收

1. **B1 逐位一致**：输入矩阵是一张逐用例的表，不是"四组 config + 一个推力样例"——反解用例还需要 `start` / `target` / `speed` / `shooterVelocity` / `angleEpsilon`，而 `iterations` 的取值依赖 `angleEpsilon`，不写死它这个字段就没法断言。整套用 `CONSTANT_DENSITY`（改为三元 lambda）与 `KORNET` = **`ThrustProfile.of(2600f, 0f, 2.5f)`**（窗口 `[0, 2.5)`）：基线必须取在 alpha.15 之后，那是三参构造器已经不存在的时点，写法就得按新 API。

   | 用例 | 输入 | 覆盖 |
   | --- | --- | --- |
   | `fwd-full` | `start (0,64,0)`、`velocity (100,20,0)`、config `(0.3, 26, 0.018, 9.81, 0.01, 300)` | 完整积分 |
   | `fwd-linear` | `start (0,64,0)`、`velocity (10,-3,5)`、config `(0, 1, 0, 0, 0.02, 50)` | 匀速直线 |
   | `fwd-thrust` | `fwd-full` 的起点与初速 + `KORNET` | 推力完整路径 |
   | `aim-full` | `target (800,60,0)`、`speed 400`、`shooterVelocity Vec3.ZERO`、`angleEpsilon 0.01`、`fwd-full` 的 config | 两条弧的二分 |
   | `aim-vertical` | `target (0,120,0)`（`horizDist < 1e-6`）、`speed 200`、同 config | §3.1 的第二处物化点 |
   | `aim-parabolic` | `target (800,60,0)`、`speed 120`、config `(0, 1, 0, 9.81, 0.01, 300)` | `#solveParabolicFiringSI` |
   | `aim-decel` | `target (300,64,0)`、`speed 200`、config `(0.3, 26, 0.018, 0, 0.01, 300)` | `#solveDecelerationFiringSI` |
   | `aim-empty` | `target (2000,60,0)`、`speed 50`、config `(0, 1, 0, 9.81, 0.01, 300)` | 0 解出口 |

   `aim-empty` 必须挂在退化分支上：完整二分路径**不会**返回空列表——`t = 0` 必有一个采样点，`minDist` 必然是有限值，首轮就会改进并留下解。上面这行用"无阻力 + 距离远超初速"让 `#solveParabolicFiringSI` 的 `discriminant < 0`，才真的产出 0 个解。

   `aim-*` 用例只有 `q` 行、没有 `s` 行（反解不产出采样），头行写 `samples=0`。所有用例的 `start` 默认取 `(0,64,0)`，`shooterVelocity` 默认 `Vec3.ZERO`，`angleEpsilon` 默认 `0.01`，行里不写就按这三条默认——`aim-vertical` 的 `target (0,120,0)` 正是在这个默认起点下才满足 `horizDist < 1e-6`。若要顺带记录 `aim-*` 的正解，就在 `q` 行之后按 `solutions.get(0).direction().scale(speed)` 再跑一次 `#forwardSolve` 追加 `s` 行——可选，不进入断言。

   基线在 B1 之前导出成文本资源 `src/test/resources/trajectory/golden-b1.txt`，临时提交进仓库供 B1/B2/C 三步比对，C 落地后删除。导出方式是测试类里一个 `@Disabled` 的写文件用例（B2 复用同一段代码产出 `golden-b2.txt`），不手抄。每个用例三行起头：

   ```text
   case <id> samples=<期望点数> solutions=<0|1|2>
   s <floatToIntBits(time)> <l(x)> <l(y)> <l(z)> <l(vx)> <l(vy)> <l(vz)>
   q <l(dir.x)> <l(dir.y)> <l(dir.z)> <l(term.x)> <l(term.y)> <l(term.z)> <floatToIntBits(flightTime)> <int iterations> <0|1 isHighArc>
   ```

   其中 `l(...)` = `doubleToLongBits`。时间列是 `float`（§4.1 要求 `TrajectorySample#time` 保持 `float`），写成 `doubleToLongBits` 会因加宽与否出现两种编码；`flightTime` 同理是 `float`，写成 int 只能截断。`samples=` 与 `solutions=` 必须显式写进头行：只比对"文件里出现的行"时，采样点少一段、2 个解退化成 1 个解都会静默通过。

   断言：`#forwardSolve` 的每个采样点与对应行完全相等；`#solveFiringAngle` 的 `direction`、`flightTime`、`terminalVelocity`、`isHighArc`、`iterations` 与对应行完全相等，且解个数等于头行声明的值。
2. **B2 数值变更可量化**：与同一份 `golden-b1.txt` 逐点比较，给出最大位置偏差与最大速度偏差；容差取实测值向上取一个数量级并写进本文，不接受估算。
3. **C 不引入新的数值差异**：B2 落地后把同一组输入再导出成 `golden-b2.txt`（编码同 §七.1），C 落地后与之逐位比对——两张基线的差异只应体现 B2 的数值变更，C 自身为零。另外 `toSampleList()` 与 `cursor()` 遍历同一结果逐点相等；`closestTo(point)` 与"对 `toSampleList()` 手写一遍最近点扫描"对每个输入点取到同一个样本（含同距先到先得）；两份等价构造的 `equals` 为真、尾部空闲容量不影响相等性。
4. **分配量**：用 `com.sun.management.ThreadMXBean#getThreadAllocatedBytes` 在同一线程取前后差。它不需要额外 JVM 参数、不依赖 spark（那是游戏侧 profiler，JUnit 进程里没有），也能把分配归因到单次调用——`-Xlog:gc` 只给 GC 事件与堆占用，做不到这件事，不作为判据。三条写法要求：
   - 先断言 `bean.isThreadAllocatedMemoryEnabled()`，关着就 `setThreadAllocatedMemoryEnabled(true)`。未启用时该方法返回 `-1`，差值恒为 0，断言会假通过。
   - 先预热（如 1e4 次）。首次调用的类加载与 lambda 实例化都记进差值，KB 级开销足以让断言在冷 JVM 上确定性失败，结果还会依赖 JUnit 用例顺序。
   - 测量改成循环 N 次（如 1000）取 `(after − before) / N` 作为每次调用的均值，上界定在实测均值两倍以内，实测值一并记录。§3.5 的"10~13 个对象"只是量级参考，上界必须来自实测。
   - 完整二分路径（`g ≠ 0` **且** `!isNoDrag(config)`，或推力激活的 config）：B1 后单次 `RealisticTrajectory#solveFiringAngle` 的采样分配为 0（断言对象是本仓库的 `#solveFiringAngle`，不是 Machine-Max 的 `HudBallisticTable#resolve`——后者不在本仓库 classpath 上，只能作为"×128 次调用"的说明提及），只剩每次反解那 10~13 个常数对象（§3.5）；B2 不改变分配量。只写 `g ≠ 0` 会把 §七.1 的 `aim-parabolic` 也算进来，而它走的是解析解、根本不积分。
   - `g = 0` 且有阻力的 config 走 `#solveDecelerationFiringSI`，每次反解固定物化 1 条轨迹（§3.1）。这条入口不在 B1 内，验收时单列，不与上一条混算。
   - 正解路径：C 后 `#forwardSolve` 单次 301 点从"每点 3 个对象 + 容器"降到 1 个 `double[]`（§5.4）。
5. **内联兜底触发条件**：在同一个测试类里放一个 `@Disabled` 的基准用例（输入取 §七.1 `fwd-thrust` 的 config 与起点，预热 1e4 次后跑 1e4 次取均值），与 B1 之前那次提交上的同一用例对比。单次 `#forwardSolve` 的 CPU 时间均值上升超过 5% 时（用 `com.sun.management.ThreadMXBean#getCurrentThreadCpuTime` 计时，不用 `System.nanoTime`——wall clock 会被调度与 GC 拖走，波动大于阈值），按 §3.2 的兜底方案给 `#solveFullIntegrationSI` 与其推力变体写探针专用副本。仓库里没有现成基准，"现状"就是基线提交上的这条用例；取不到基线时按"不触发兜底"处理，并在提交说明里记录实测值。
6. **回归**：`RealisticTrajectoryInvariantTest` 全绿——该文件约 31 处 `result.samples()` 需按 §5.3 迁移后再验收；`./gradlew runGameTestServer` 24 项全绿。

## 八、明确不做

- **`float` 存储**：`double[]` 降到 `float[]` 能再省一半（28 B/点），但两条理由都指向不做。其一，位置与速度目前以 `double` 参与运算，落盘成 `float` 会改动数值结果，与 §七.3 的"C 不引入新的数值差异"冲突；其二，也是更硬的一条——`float` 在 `|x| = 3e7` 处的 ulp 约 2 m，远原点弹道会直接失真，这与"再省一半"完全不成比例。要省这一半，得先接受"输出精度变更 + 远原点不可用"，那是另一个决定。
- **`samples()` 兼容层**：保留它等于保留"读整条轨迹很便宜"的错觉。迁移面已查清（§5.3）：`src/main` 10 处（B1 之后剩 7 处）+ 测试约 31 处，Machine-Max 未直接使用该访问器。
- **命中与落地判定**：`#closestTo` 只回答"弹道最接近某一点时弹丸在哪"，不回答"打中了没有"，也不提供"落地点"。求解器不知道地形与碰撞盒，`maxSteps` / `maxTicks` 之外没有第二个终止条件；加判定等于让求解器猜地形，而调用方手上已有真实的碰撞结果。同理不提供"第一次穿越某平面"的查询——那需要调用方给出平面，逻辑与地形判定一样不属于求解器。
- **改积分公式或数值方案**：本文只动数据形状、调用结构与中间量宽度。唯一例外是 §5.7 七 的单列缺陷修复（`MinecraftTrajectory` 的解析飞行时间算法），它单独提交、不并入 B1/B2/C，也不影响本文的逐位判据。
- **并行化**：单条轨迹最多几百步，线程调度开销大于收益。
