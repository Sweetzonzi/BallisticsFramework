# 2.6 代理实体与命中解析

## 为什么要关心代理实体

在 Minecraft 的实体系统中，一个逻辑上的"目标"可能由多个实体分层构成。典型的例子是模块化载具：载具的每个部件（车体、炮塔、履带）在物理和伤害层面是独立的对象，但在 Minecraft 实体层只有一个**代理实体**（Proxy Entity）作为载体。原版的碰撞检测基于 AABB（轴对齐包围盒），它只能命中这个代理实体的外部包围盒，无法区分命中的是哪个子部件。

更具体地说，有以下两种典型场景：

**场景一：部件化实体的碰撞箱膨胀。** 代理实体的 AABB 覆盖了所有子部件的范围，但子部件之间有间隙。原版碰撞检测报告"命中了代理实体"，但实际上弹丸可能从一个缝隙中穿过，并未真正碰到任何有效部件。这就是**假阳性命中**——投射物被错误地销毁，但实际未造成伤害。

**场景二：命中几何不精确。** 即使弹丸确实命中了某个子部件，原版报告的法线和命中点也是针对代理实体整体 AABB 的，不是针对具体子部件表面的精确值。如果不做修正，护甲侧的跳弹判定、斜穿修正、部位区分都将使用错误的几何数据。

```text
原版碰撞检测：
  投射物 → AABB 相交 → 命中代理实体
  → hitPoint = 代理实体 AABB 上的点（粗略）
  → hitNormal = 粗略推算的方向

精确命中验证后：
  投射物 → 物理射线检测 → 命中子部件
  → hitPoint = 子部件表面的精确坐标
  → hitNormal = 子部件表面的精确法线
  → actualTarget = 子部件的 BFHurtTarget
```

`BFHitResolver` 接口和 `BFDamageApi.resolveHitTarget()` 方法正是为解决这些问题而设计的。它们在伤害管线**之前**执行，允许攻击方在调用 `BFDamageApi.hurt()` 之前先做一次精确命中验证，获得修正后的目标和几何数据。

## resolveHitTarget：两步走的调用模式

### 使用 Entity 版本

当你已经从原版碰撞检测或自定义 raycast 中获取了命中的实体和命中点时，使用三参数版本：

```java
// 假设你已经从某种渠道获取了以下信息
Entity hitEntity = ...;    // 原版碰撞检测命中的实体
Vec3 hitPoint = ...;       // 命中点世界坐标
Vec3 delta = velocity.scale(4.0);  // 搜索矢量：方向为弹丸飞行方向，模为搜索距离（米）

var resolved = BFDamageApi.resolveHitTarget(hitEntity, hitPoint, delta);
if (resolved == null) {
    // 假阳性：实际未命中任何有效部件
    // 投射物应继续飞行，不销毁
    return;
}

// 用修正后的几何数据构造上下文
BFDamageContext ctx = BFDamageContext.builder()
    .source(damageSource)
    .baseDamage(35f)
    .hitVelocity(bulletVelocity)
    .hitPoint(resolved.correctedHitPoint())       // 使用修正后的命中点
    .hitNormal(resolved.correctedHitNormal())     // 使用修正后的法线
    .penetration(bulletPenetration)
    .extensions(resolved.extensions().copy())     // 拷贝解析器提供的扩展数据
    .build();

// 对真正的目标发起协议伤害
BFDamageApi.hurt(resolved.actualTarget(), ctx);
```

**关于 delta 参数**：`delta` 是一个方向与模长合一的矢量。方向为弹丸在命中瞬间的飞行方向（即 `hitVelocity.normalize()`），模长为从命中点继续向前搜索的距离上限（单位：米）。协议不规定这个值应该是多少——它由实现 `BFHitResolver` 的代理实体在精确验证时使用。典型值取弹丸两 tick 的飞行距离（对于高速弹丸约 4~8 米），在搜索精度和性能之间取得平衡。

### 使用 HitResult 版本

如果你的代码已经持有原版的 `HitResult`（如在 `ProjectileImpactEvent` 或自定义 raycast 回调中），可以使用更简洁的二参数版本——它自动解包 `EntityHitResult`：

```java
HitResult hitResult = ...;  // 原版碰撞检测结果
Vec3 delta = ...;           // 搜索矢量

var resolved = BFDamageApi.resolveHitTarget(hitResult, delta);
if (resolved == null) {
    // 可能是方块命中、非实体命中、或假阳性
    return;
}

// 构造上下文并发起协议伤害
BFDamageContext ctx = BFDamageContext.builder()
    .source(damageSource)
    .baseDamage(35f)
    .hitVelocity(bulletVelocity)
    .hitPoint(resolved.correctedHitPoint())
    .hitNormal(resolved.correctedHitNormal())
    .penetration(bulletPenetration)
    .extensions(resolved.extensions().copy())
    .build();

BFDamageApi.hurt(resolved.actualTarget(), ctx);
```

如果 `hitResult` 不是 `EntityHitResult`（例如是 `BlockHitResult`），本重载直接返回 null——方块命中不需要实体层面的命中解析。

### 两个重载的取舍

| 重载 | 签名 | 适用场景 |
|------|------|---------|
| 实体版本 | `resolveHitTarget(Entity, Vec3, Vec3)` | 你已分别持有命中实体和命中点。最常用，灵活性最高 |
| HitResult 版本 | `resolveHitTarget(HitResult, Vec3)` | 你持有原版 HitResult，不想手动解包。代码更简洁 |

两者内部逻辑完全一致——HitResult 版本只是实体版本的便利包装，自动调用 `EntityHitResult.getEntity()` 和 `getLocation()` 后委托给实体版本。

## 解析结果的结构

`BFDamageApi.resolveHitTarget()` 的返回值是 `BFHitResolveResult` record，包含四个组件：

| 组件 | 类型 | 说明 |
|------|------|------|
| `actualTarget` | `BFHurtTarget` | 真正的协议伤害目标。传递给 `BFDamageApi.hurt()` 的第一个参数 |
| `correctedHitPoint` | `Vec3` | 修正后的命中点世界坐标。优先于原版报告的命中点 |
| `correctedHitNormal` | `Vec3` | 修正后的命中面法线。优先于原版粗略推算的法线 |
| `extensions` | `BFDamageExtensions` | 解析器提供的扩展数据。调用方应先 `copy()` 再追加自己的 key |

**注意**：`extensions` 是一个直接引用。如果你需要在此基础上添加自己的扩展数据，务必先调用 `.copy()` 创建一个浅拷贝，避免修改解析器内部的状态：

```java
BFDamageExtensions exts = resolved.extensions().copy();
exts.set(MyMod.FUSE_DELAY, 0.05f);
```

有一个方便的构造器在不需要扩展数据时使用：

```java
new BFHitResolveResult(target, hitPoint, hitNormal)
// 等价于 new BFHitResolveResult(target, hitPoint, hitNormal, new BFDamageExtensions())
```

## 返回 null 的含义

`resolveHitTarget` 在以下三种情况下返回 null：

1. **代理实体执行了精确验证，但实际未命中**（射线从部件间隙穿过）——应让投射物继续飞行
2. **命中的实体既未实现 `BFHitResolver`，也未实现 `BFHurtTarget`**——意味着该实体不是协议目标，武器侧可按原版方式处理
3. **输入不是 EntityHitResult**（方块命中）——不需要实体命中解析

对于情况 1，处理方式很明确：**投射物不应被销毁，应继续飞行**。不要在返回 null 时自行调用 `BFDamageApi.hurt()`，因为 null 意味着"没有合法的伤害目标"。

对于情况 2，协议的降级行为是：如果实体仅实现了 `BFHurtTarget` 但未实现 `BFHitResolver`，`resolveHitTarget` 会直接将其包装为结果返回（`correctedHitPoint` = 原版命中点，`correctedHitNormal` = `Vec3.ZERO`，`extensions` = 空容器）。这意味着在不使用精确命中解析的情况下，协议至少能保证伤害正确路由到 `BFHurtTarget` 目标。

## 完整调用示例（含回调）

以下展示完整的武器侧调用模式，包含命中前解析和伤害执行后的回调处理：

```java
// === 在投射物命中回调或碰撞事件中 ===

EntityHitResult hitResult = ...;       // 原版碰撞检测结果
Vec3 bulletVelocity = ...;             // 弹丸速度（m/s）
DamageSource damageSource = ...;       // 原版伤害来源
float baseDamage = 35f;               // 标称伤害
float penetration = 120f;             // 理论穿深（mm RHA）

// 计算搜索矢量：沿弹丸飞行方向搜索 4 米
Vec3 delta = bulletVelocity.normalize().scale(4.0);

// 第一步：命中前解析
var resolved = BFDamageApi.resolveHitTarget(hitResult, delta);
if (resolved == null) {
    // 假阳性或非实体命中——投射物不要销毁
    return;
}

// 第二步：构造上下文（使用修正后的几何）
BFDamageExtensions exts = resolved.extensions().copy();
exts.set(BFDamageExtensions.CALIBER, 0.076f);  // 76mm 口径
exts.set(BFDamageExtensions.MASS, 6.0f);        // 6kg 弹体

BFDamageContext ctx = BFDamageContext.builder()
    .source(damageSource)
    .baseDamage(baseDamage)
    .hitVelocity(bulletVelocity)
    .hitPoint(resolved.correctedHitPoint())
    .hitNormal(resolved.correctedHitNormal())
    .penetration(penetration)
    .extensions(exts)
    .handler(myHandler)  // 注入回调
    .build();

// 第三步：对真正的目标发起协议伤害
BFDamageApi.hurt(resolved.actualTarget(), ctx);
```

## 与回调的配合

`resolveHitTarget` 返回的扩展数据中可能包含解析器设定的元信息（例如被命中的子部件 ID、命中部位的材质类型等）。这些数据通过 `resolved.extensions()` 传递，并在构造上下文时被拷贝进去。在回调中，你可以通过 `ctx.extensions()` 读取它们：

```java
BFDamageHandler myHandler = new BFDamageHandler() {
    @Override
    public void onPenetrated(BFHurtTarget target, BFDamageContext ctx) {
        // 读取解析器提供的扩展数据
        String partId = ctx.extensions().get(PartIdKey);
        spawnPenetrationEffect(ctx.hitPoint(), partId);
    }
};
```

这使得武器侧可以在不依赖具体代理实体类型的情况下，获得特定于命中部位的上下文信息。

## 没有命中前解析时的降级行为

如果武器模组不调用 `resolveHitTarget`，直接对代理实体调用 `BFDamageApi.hurt()`，会发生什么？这取决于代理实体自身是否实现了防御侧自愈：

- **如果代理实体实现了 `BFHurtTarget` 且 `hurt()` 内有自愈逻辑**（例如通过内部 raycast 将伤害路由到子部件）：伤害仍能正确路由，但几何数据是原版的粗略值，假阳性判断也失效了
- **如果代理实体没有自愈逻辑**：伤害直接作用在代理实体上，可能造成错误的伤害分配

因此，**武器侧调用 `resolveHitTarget` 是最优实践**——它能获得最精确的命中几何和最可靠的假阳性判断。但协议在设计上确保即使武器侧不调用，防御侧也有兜底机制（详见[第 3.7 节](../3-护甲侧开发/3.7-代理实体：实现BFHitResolver.md)）。

## 性能说明

`resolveHitTarget` 的性能开销完全取决于代理实体的 `resolveHit` 实现。简单的实现（如基于预设数据查表）开销极小；基于物理引擎射线检测的实现（如对复杂碰撞体做线段求交）开销会稍高。但无论哪种实现，`resolveHitTarget` 都在单次命中时调用一次，不涉及循环或批量计算。对于大多数武器模组的射速场景（每分钟数百发)，这层开销可以忽略不计。
