# 3.7 代理实体：实现 BFHitResolver

## 设计动机

`BFHitResolver` 与 `BFHurtTarget` 有着明确的职责分离：

- **BFHurtTarget** 回答"打中了之后穿深多少、伤害多少"——在管线内
- **BFHitResolver** 回答"打中了谁"——在管线外

当一个实体充当其他子对象的**代理**时（例如模块化载具的部件宿主、多碰撞箱 BOSS 的碰撞代理），原版的 AABB 碰撞检测只能报告"命中了代理实体"，无法区分弹丸实际打中了哪个子部件、甚至是否真的打中了。`BFHitResolver` 让代理实体能够在伤害管线之外执行一次精确验证，将原始命中重定向到真正应该承受伤害的目标。

## 与 BFHurtTarget 的关系

一个实体**可以同时实现** `BFHitResolver` 和 `BFHurtTarget`，但它们的职责是正交的：

| 接口 | 调用时机 | 回答的问题 | 典型输入 |
|------|---------|-----------|---------|
| `BFHitResolver.resolveHit` | 在 `BFDamageApi.hurt()` 之前 | 打中了谁？真的打中了吗？ | 原版命中点 + 搜索方向 |
| `BFHurtTarget.resolvePenetration` | 在 `BFDamageApi.hurt()` 内部 | 打穿了没有？ | 完整的 BFDamageContext |

典型的代理实体会同时实现两者：`BFHitResolver` 负责将原版命中的代理实体重定向到正确的子部件；`BFHurtTarget` 在管线内为子部件的穿甲判定提供服务。

## 接口方法

`BFHitResolver` 定义了两个方法，但通常只需要实现主方法：

```java
public interface BFHitResolver {

    /** 主方法：执行精确命中验证 */
    @Nullable
    BFHitResolveResult resolveHit(Vec3 hitPoint, Vec3 delta);

    /** 便利重载：从原版 HitResult 提取命中点后委托给主方法 */
    @Nullable
    default BFHitResolveResult resolveHit(HitResult hitResult, Vec3 delta) {
        return resolveHit(hitResult.getLocation(), delta);
    }
}
```

### 参数说明

**`hitPoint`**（或 `HitResult.getLocation()`）是原版碰撞检测报告的命中点世界坐标。通常来自于 `EntityHitResult` 或自定义 raycast。这是你的精确验证的**起点**。

**`delta`** 是武器侧在调用 `resolveHitTarget` 时传入的搜索矢量。它的方向代表弹丸的飞行方向，它的模长代表从命中点继续向前搜索的距离上限（单位：米）。协议不规定这个值应该是多少——它由武器侧根据弹丸速度和帧率决定。你的实现应该以 `hitPoint` 为起点，沿 `delta` 方向搜索，但**不应超出** `delta` 的模长距离。

### 返回值

返回 `null` 表示**实际未命中**——即使原版 AABB 碰撞检测报告了命中，你的精确验证发现弹丸实际上没有碰到任何有效目标。此时调用方应让投射物继续飞行。

返回非 null 的 `BFHitResolveResult` 表示验证通过。结果中包含真正的伤害目标、修正后的命中几何和可选的扩展数据。

## 实现示例

以下展示一个代理实体实现 `BFHitResolver` 的完整模式。假设你的模组有一个模块化实体，其子部件分布在代理实体的 AABB 范围内。你需要通过射线检测来确定弹丸实际命中的子部件：

```java
public class ModularProxyEntity extends Entity implements BFHitResolver, BFHurtTarget {

    private final List<SubPart> parts = new ArrayList<>();

    @Override
    @Nullable
    public BFHitResolveResult resolveHit(Vec3 hitPoint, Vec3 delta) {
        // 从命中点沿 delta 方向执行射线检测，找到第一个有效子部件
        Vec3 searchEnd = hitPoint.add(delta);
        SubPart bestPart = null;
        double bestDist = Double.MAX_VALUE;

        for (SubPart part : this.parts) {
            if (!part.isActive()) continue;

            // 计算射线与子部件碰撞体的交点
            HitResult partHit = part.rayIntersect(hitPoint, searchEnd);
            if (partHit != null) {
                double dist = partHit.getLocation().distanceToSqr(hitPoint);
                if (dist < bestDist) {
                    bestDist = dist;
                    bestPart = part;
                    bestHit = partHit;  // 保存最近交点的结果
                }
            }
        }

        if (bestPart == null) {
            return null;  // 射线穿过所有间隙——假阳性，投射物继续飞行
        }

        // 构造扩展数据，传递子部件标识
        BFDamageExtensions exts = new BFDamageExtensions();
        exts.set(MyModKeys.PART_ID, bestPart.getId());

        return new BFHitResolveResult(
            bestPart,                        // actualTarget：真正的协议伤害目标（实现了 BFHurtTarget）
            bestHit.getLocation(),            // correctedHitPoint：子部件表面的精确命中点
            calculateHitNormal(bestHit),      // correctedHitNormal：子部件表面的精确法线
            exts                              // 扩展数据
        );
    }
}
```

关键要点：

1. **搜索范围**：以 `hitPoint` 为起点，沿 `delta` 方向搜索，不超过 `hitPoint.add(delta)`。因为 `delta` 的模长已经是武器侧根据弹丸速度估算的合理搜索距离。
2. **返回 null 的条件**：当射线穿过了所有子部件的碰撞体而没有命中任何有效目标时，返回 null。这是假阳性判断的核心——投射物应该继续飞行，不应被销毁。
3. **最近命中优先**：如果有多个子部件在搜索路径上，取距离 `hitPoint` 最近的。这也是射线检测的标准做法。
4. **扩展数据**：在 `BFHitResolveResult.extensions` 中携带与命中部位相关的元数据（如部件 ID、材质类型）。武器侧在构造上下文时会 `copy()` 这个容器并追加自己的字段。
5. **幂等无副作用**：`resolveHit` 必须是纯查询。投射物命中通常只被解析一次——`Projectile.onHit` 阶段的结果写入投射物自身的缓存，`Entity.hurt` 阶段直接取用；只有伤害来源的 direct entity 不是那个投射物时（近战、爆炸、伤害延迟结算），`hurt` 阶段才按伤害来源重新解析一次。实现不得依赖调用次数，也不得在解析过程中修改自身状态，且同一组 `(hitPoint, delta)` 必须始终返回同一结果。

## 命中对象不限于实体

`resolveHit` 的调用方经由 `BFDamageApi.resolveHitTarget(Object hit, Vec3 hitPoint, Vec3 delta)` 进入，第一个参数的类型是 `Object`——实体、物理体属主（`PhysicsHost`）、包装体都可以是代理对象。`BFDamageApi.isProtocolAware(Object)` 同理。因此代理对象不必是 `Entity` 子类；只有"需要被原版 AABB 碰撞检测命中"的代理才必须是实体。

代理对象是否承载受击语义，决定了它的接口组合。两条入口对同一个代理的归属并不相同，因此每种组合都要看两列：

| 代理的接口组合 | 协议内伤害（`BFDamageApi.hurt(代理, ctx)`） | 协议外伤害（原版伤害经 Mixin 拦截） |
|--------------|------------------------------------|--------------------------------|
| 仅 `BFHitResolver` | **转发**给 `resolveHit` 解析出的实际目标（分支 1.5）；解析为未命中时返回 0f，伤害不落在代理自身 | 拦截器解析后转发给实际目标，代理自身不受伤 |
| `BFHitResolver` + `BFHurtTarget` | 由代理自身接管（`BFHurtTarget` 分支优先于解析分支） | 先走 `BFHurtTarget` 分支由代理自身接管；其 `createContextFromVanilla` 返回 null 时改走解析分支，由解析出的实际目标决定归属（不会落到护甲适配器分支） |
| 仅 `BFHurtTarget` | 由代理自身接管 | 由代理自身接管；`resolveHitTarget` 会把它直接包装为结果返回 |
| 仅 `BFHitResolver` 且为 `LivingEntity`、穿戴 `BFArmorMaterial` 护甲 | **转发**给实际目标；**代理自身穿戴的协议护甲不参与本次判定** | 转发给实际目标；**代理自身穿戴的协议护甲不参与本次判定**，护甲语义由实际目标承担 |

最后一行需要特别注意：代理只是指向实际目标的一根指针，不是受击者。若你希望护甲参与判定，应把它穿在真正承受伤害的目标上。

两条入口的几何来源也不同：协议内伤害用上下文自带的 `ctx.hitPoint()` 与 `BFHitResolver.searchDelta(ctx.hitVelocity())`（发起方写入的命中点与速度）发起搜索，协议外伤害用 `BFHitResolver.searchRay(代理, source)` 从伤害来源反推；**搜索的入参几何与转发给实际目标的几何是两回事**——后者一律取解析结果的 `correctedHitPoint` / `correctedHitNormal`（`contextForResolvedTarget` 应用）。契约归属：`docs/BFDamageApi-hurt解析器转发计划.md`。

## 协议外伤害的自动转发

上一节说的 `ProjectileHitResolverMixin` 只覆盖投射物，且只解决"假阳性时投射物不该被销毁"。若协议外伤害（原版投射物、近战、爆炸）已经到达代理对象，又由谁把伤害送到实际目标？

答案是拦截器中的一条独立分支：**只要代理对象实现了 `BFHitResolver`，协议外伤害就会自动转发**，代理无需实现 `BFHurtTarget`。流程是：

1. 按伤害类别导出搜索几何——投射物取其位置与速度，活体近战取攻击者眼位与视线，爆炸等其他有源位置伤害取来源位置到代理的连线；无源位置的伤害（虚空、饥饿、`/kill`）没有可复检的几何，直接放行原版
2. 调用 `resolveHitTarget(代理对象, hitPoint, delta)`
3. 解析出实际目标后，走 `actualTarget.createContextFromVanilla(source, amount)` 得到一个只带伤害来源信息的上下文
4. 由 `BFDamageApi.contextForResolvedTarget` 把解析出的 `correctedHitPoint` / `correctedHitNormal` 与 `extensions` 应用到该上下文上
5. `BFDamageApi.hurt(actualTarget, ctx)` 进入穿甲管线

解析判定为假阳性时返回 `false`，不造成伤害（投射物也因此继续飞行）；解析结果就是代理自身、或实际目标不接受协议外伤害（`createContextFromVanilla` 返回 null）时，交回原版流程。

**协议内伤害走另一条转发路径**：`BFDamageApi.hurt(代理, ctx)` 在代理不实现 `BFHurtTarget` 时用上下文自带的命中几何解析出实际目标后转发（分支 1.5），不经过 Mixin，也不需要 `createContextFromVanilla`——上下文已由发起方构造完成，随后同样经 `contextForResolvedTarget` 应用修正几何。两条路径的分工、几何来源差异见上一节的表；重建规则（命中点替换、法线判零回退、扩展合并方向）的契约由 `docs/BFDamageApi-hurt解析器转发计划.md` 持有。

**两条转发路径都必须应用修正几何**，因为护甲侧的 `mapHitToSlot` 拿上下文命中点判定着弹槽位，而入参命中点通常是代理 AABB 的交点：不替换就会按代理外壳的高度分配护甲，而不是子部件的真实着弹位置。

**这条路径只是兜底**：拦截器只能从伤害来源反推搜索几何，命中点与搜索方向都是推测值；武器侧主动调用时则能传入弹道自有的命中点与飞行方向，判定精度高于前者。要让代理获得最可靠的判定，应由武器侧主动解析。

## 三层防御体系

`BFHitResolver` 与自动转发、防御侧自愈机制构成三层互补的防御体系：

```text
上层（攻击侧自动化）： 协议内置的 ProjectileHitResolverMixin
  工作原理：当任何投射物（Projectile）命中一个实现了 BFHitResolver 的对象时，
          协议自动在 onHit 执行前调用 resolveHitTarget，若返回 null 则取消
          原版 onHit 流程，投射物继续飞行。
  解决的问题：框架外武器模组的投射物在命中代理对象时，自动获得假阳性判断。
  前提：代理对象实现了 BFHitResolver。

中层（协议外伤害自动转发）：拦截器的 BFHitResolver 分支
  工作原理：协议外伤害到达代理对象时（onHit 未取消的真实命中、近战、爆炸），
          拦截器按伤害类别构造搜索几何，解析出实际目标后转发伤害。
  解决的问题：代理不必实现 BFHurtTarget 也能承接原版伤害。
  前提：代理对象实现了 BFHitResolver，且实际目标的 createContextFromVanilla 可用。

下层（防御侧自愈）：  代理对象 BFHurtTarget.hurt() 内部的精确路由
  工作原理：当伤害已进入管线时，在 hurt() 内部通过类似 raycast 的方式
          将伤害分配到正确的子部件。
  解决的问题：即使攻击方未调用 resolveHitTarget，伤害也能正确路由。
  前提：代理对象实现了 BFHurtTarget 并在 hurt() 内有自愈逻辑。
```

**三层体系不重复**——它们解决的是不同层次的问题：

- 上层（攻击侧自动化）解决**投射物生命周期**的问题：打空了就该继续飞，不该被销毁
- 中层（协议外伤害自动转发）解决**代理不必承载受击语义**的问题：只回答"打中了谁"也能让伤害落到正确目标
- 下层（防御侧自愈）解决**伤害路由正确性**的问题：打中了就该找对目标

## 完全自动化的 Mixin 支持

协议包含一个内置的 Mixin——`ProjectileHitResolverMixin`——它注入到 `Projectile.onHit(HitResult)` 的 HEAD 阶段。当任何投射物命中一个实现了 `BFHitResolver` 的实体时，此 Mixin 会自动：

1. 检查命中结果是否为 `EntityHitResult` 且目标实现了 `BFHitResolver`
2. 从投射物的 `getDeltaMovement()` 计算搜索矢量：`BFHitResolver.searchDelta` 把速率钳制在 0.5~4.0 后取两倍位移，搜索距离落在 1~8 米
3. 调用 `BFDamageApi.resolveHitTarget(result, delta)` 验证
4. 若返回 null，取消原版 `onHit` 流程——投射物不被销毁，继续飞行
5. 判定为真命中时，把这次命中的解析结果写入投射物自身的缓存，供随后 `Entity#hurt` 阶段的拦截器直接取用

**投射物速率为零时本 Mixin 不做任何解析**（`searchDelta` 返回零矢量即早退），原版 `onHit` 行为保持不变。

这意味着**一旦你的代理对象实现了 `BFHitResolver`，所有投射物（无论来自哪个模组）在命中它时都会自动获得精确命中验证。** 武器模组不需要做任何额外的适配——这就是"自动化"的含义。

此 Mixin 对未实现 `BFHitResolver` 的目标性能影响为零——仅一次 `instanceof` 检查后直接 `return`。

### 命中结果缓存

一次投射物命中会先后经过两个阶段：`ProjectileHitResolverMixin` 在 `onHit` 阶段做一次精确验证（决定投射物去留），拦截器在 `Entity#hurt` 阶段需要知道这次命中归属哪个实际目标。两个阶段掌握的信息并不对等——`onHit` 阶段持有射线与 AABB 的精确交点，而 `hurt` 阶段只能从 `DamageSource` 反推，拿到的是投射物当前坐标（本 tick 移动之前的值，与交点相差最多一个 tick 的位移）。若在 `hurt` 阶段重建几何再解析一次，同一个命中可能得到相反结论，而 `hurt` 阶段的结论会直接决定伤害去向。

因此协议让两个阶段共用一份结果：`onHit` 阶段判定为真命中后，把 `BFHitResolveResult` 写入投射物自身（即实现 `BFHitResolveCache` 的字段），拦截器在 `hurt` 阶段直接取用，不重建几何、不重复判定。缓存的边界如下：

- **只对投射物来源生效**：伤害来源的 direct entity 必须是那个投射物。近战、爆炸等其他来源取不到缓存，一概按伤害来源构造几何后解析。
- **单次命中有效，不跨命中事件复用**：读取即清空。穿透投射物在同一 tick 内对多个实体依次触发 `onHit → hurt`，每次命中各写各读，第二次不会沿用第一次的结果。
- **身份校验**：仅当缓存记录的命中实体与当前受击实体身份相等时返回记录。写与读之间可能夹杂未触发 `hurt` 的命中（`canHitEntity` 为 false、方块命中等），此时缓存对应的是别的命中事件。
- **只有判定为真命中才写入**：假阳性走 `ci.cancel()`，不写缓存。

对实现 `BFHitResolver` 的你来说，这通常意味着 `resolveHit` 在一次投射物命中中只被调用一次。

注意本 Mixin 只覆盖投射物。近战、爆炸等协议外伤害由拦截器的自动转发分支处理（见"协议外伤害的自动转发"）；这些来源取不到缓存，会调用 `resolveHit` 一次，因此实现它时必须幂等。

## 三层防御全貌

将 `ProjectileHitResolverMixin`（上层）、协议外伤害自动转发（中层）和防御侧自愈（下层）合在一起，构成了协议的完整三层防御体系：

```text
上层（Mixin 自动化）:  ProjectileHitResolverMixin
  拦截 Projectile.onHit → resolveHitTarget → null → cancel
  → 解决投射物生命周期问题：打空了就该继续飞

中层（协议外伤害自动转发）:  拦截器的 BFHitResolver 分支
  拦截 Entity.hurt → 按伤害类别构造几何 → resolveHitTarget → hurt(实际目标)
  → 解决代理不必承载受击语义的问题：只回答"打中了谁"也能让伤害落到正确目标

下层（防御侧自愈）:      代理对象的 hurt() 内部精确路由
  已在管线内的伤害 → 自行精确检测 → 路由到正确目标
  → 解决伤害路由问题：打中了就该找对目标
```

## 完整场景一览

以下表格展示了不同攻击路径下、不同代理对象实现时的行为：

| 攻击方 | 代理对象实现 | 触发链 | 结果 |
|--------|------------|--------|------|
| 框架内武器模组（手动调用 resolveHitTarget） | 实现 BFHitResolver | 攻击方手动 resolveHitTarget → 获精确几何 → hurt(实际目标) | 精确命中 + 假阳性判断 |
| 任意投射物 | 实现 BFHitResolver | ProjectileHitResolverMixin 自动拦截 onHit → resolveHitTarget → null → cancel | 全自动，投射物不被销毁 |
| 任意投射物 | 实现 BFHitResolver | ProjectileHitResolverMixin → resolveHitTarget → 找到目标 → 放行 onHit → 拦截器再解析并转发 | 全自动，精确命中 |
| 框架外武器模组（直接 entity.hurt） | 仅实现 BFHitResolver | entity.hurt → 拦截器解析 → 转发给实际目标 | 伤害正确路由；假阳性时不造成伤害 |
| 框架外武器模组（直接 entity.hurt） | 实现 BFHitResolver + BFHurtTarget（有自愈） | entity.hurt → 拦截器走 BFHurtTarget 分支 → 协议管线 → hurt 内自愈路由 | 伤害正确路由（假阳性已在上层解决） |
| 框架外武器模组（直接 entity.hurt） | 仅实现 BFHurtTarget（无自愈） | entity.hurt → 原版流程 | 伤害作用在代理对象自身 |

从表格可以看出，**最坚固的防护是同时实现 `BFHitResolver` 和 `BFHurtTarget`（含自愈）**——这样可以覆盖所有攻击路径，且假阳性在最早的阶段就被拦下。仅实现 `BFHitResolver` 能自动获得上中两层的保护，所有投射物攻击都会经过精确验证。

## BFHitResolver 不是必须的

如果你的对象不是代理——即它的 AABB 就是它的真实碰撞体，没有子部件，不需要假阳性判断——你**不需要**实现 `BFHitResolver`。只需要实现 `BFHurtTarget` 就足够了。`BFHitResolver` 的价值仅在于"代理需要将命中重定向到子目标"的场景。

## 与 BFArmorMaterial 的配合

命中前解析**先于**护甲适配器生效：`BFHitResolver` 决定了"谁被打中"，`BFArmorAdapter` 才决定"这个被打中者穿的东西挡不挡得住"。因此解析返回的 `correctedHitPoint` 和 `correctedHitNormal` 会成为护甲侧部位映射的输入——护甲物品的 `mapHitToSlot` 用修正后的精确命中点判断着弹槽位。

框架内武器侧主动调用时的串联流程：

1. 投射物命中代理对象的 AABB → `ProjectileHitResolverMixin` 触发
2. 武器侧调用 `resolveHitTarget(Object, Vec3, Vec3)` → 代理对象的 `BFHitResolver.resolveHit()` 返回实际目标（如子部件）
3. 武器侧用 `correctedHitPoint` 和 `correctedHitNormal` 构造 `BFDamageContext`
4. `BFDamageApi.hurt(actualTarget, ctx)` → 如果实际目标穿戴了协议护甲，进行双层串联判定

**护甲穿在谁身上，就由谁参与判定。** 代理对象自身穿戴的协议护甲不参与这次判定——它是受击者的指针，不是受击者。在协议外伤害自动转发这条路径上同理：第 2 步由拦截器代劳，第 4 步的实际目标仍然是护甲的归属者。
