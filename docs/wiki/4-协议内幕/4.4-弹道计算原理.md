# 4.4 弹道计算原理

第五章介绍了外弹道工具的使用方式。本章面向想深入理解"解算器内部做了什么、为什么这样做"的读者，拆解两类物理模型的数学细节、数值方法选型理由、退化路径判定逻辑、二分搜索策略和动目标迭代收敛分析。

---

## 物理模型 A：MC 原版速度乘数阻力

### 更新公式

MC 弹射物每 tick 使用以下物理更新（类型 A 计算顺序）：

```
v.y += gravity          (1) 加速度
v.x *= dragH           (2) 水平阻力
v.y *= dragV           (3) 垂直阻力
v.z *= dragH
p += v                 (4) 欧拉积分——位置
```

四个步骤在**同一 tick 内顺序执行**，每一步使用上一步的结果。这意味着步骤 (2) 使用的 `v.y` 已经加过 gravity——阻尼衰减的是"加了重力后的速度"，而非上帧的原始速度。

### 为什么阻力与质量无关

MC 阻力公式是：`v_{new} = v_{old} × drag`。这是一个**无量纲乘法**。drag=0.99 意味着"每 tick 保留 99% 的速度"，无论速度大小。

在真实物理中，阻力加速度 a<sub>drag</sub> = F<sub>drag</sub>/m。当 F<sub>drag</sub> 与速度成正比时，a<sub>drag</sub> 与质量 m 成反比——重物减速慢。但 MC 直接乘 drag 系数，等于假设"m 已经内嵌在 drag 值中了"，或者说假设 a<sub>drag</sub> = (1-drag)·v——加速度只与速度有关，与质量无关。

这对弹道几何有重要影响：**相同 drag/gravity 组合在不同初速下弹道几何完全相同**。因为每 tick 的位移是速度的线性函数，而速度的衰减比例固定——缩放初速只是缩放整个轨迹。

### 终端速度：为何存在

当 gravity 与 drag 达到平衡时，每 tick 速度增量为零：

```
v_terminal + gravity = v_terminal / dragV
v_terminal = gravity × dragV / (1 - dragV)
```

以箭为例（gravity=-0.05, dragV=0.99）：v<sub>terminal</sub> = -0.05×0.99/0.01 = -4.95 m/tick。y 方向速度收敛到 ≈-5 m/tick 后不再变化——无论从多高落下，落速恒定。这解释了为何 MC 中从 256 格高度落下的箭和从 10 格落下的箭末速几乎相同。

水平方向在没有外力的作用下：v<sub>terminal</sub> = 0——水平速度持续衰减到零，弹丸最终垂直下落。但当 gravity 是正值（如火球的 +0.10）时，弹丸会持续向上漂直到水平阻力使其减速为零。

### 解算器中的实现

解算器严格按类型 A 顺序实现：

```java
vel = vel.add(0, gravity, 0);          // (1)
vel = new Vec3(vel.x * dragH, vel.y * dragV, vel.z * dragH);  // (2)(3)
pos = pos.add(vel);                     // (4)
```

MC Wiki 指出不同实体在三步的执行顺序上可能不同。解算器固定使用类型 A 顺序，出于两个理由：第一，武器模组用作弹丸的实体（箭、雪球、火球等）几乎全部是类型 A；第二，即使在类型 C 场景下强行使用类型 A 解算，累积偏差也在 ~0.3m 以内，低于 MC 碰撞检测精度。详见设计文档第四章第 4.1 节的计算顺序差异评估。

## 物理模型 B：二次空气阻力

### 物理方程

标准空气阻力公式来自流体力学。弹丸在流体中受到的阻力与速度平方成正比：

```
F_drag = ½ · ρ · Cd · A · v²    （牛顿阻力公式）

a_drag = F_drag / m
       = ½ · ρ · Cd · A · v² / m
       = ½ · ρ(pos) · Cd · A · |v| · v / m    （带上方向矢量）
```

其中：
- ρ(pos)：空气密度（kg/m³），通过 `DensityFunction` 逐位置查询
- Cd：阻力系数（无量纲），典型弹丸 0.2~0.5
- A：弹丸横截面积（m²），A = π·(d/2)²
- m：弹丸质量（kg）
- |v|·v：速度的方向矢量乘以速度标量——确保阻力方向与速度相反

与 MC 模型的本质差异：**阻力并非速度的线性函数，而是二次函数**。初速翻倍意味着阻力加速度变为四倍——高速弹丸受到不成比例的剧烈减速。

### 积分方法：半隐式欧拉

解算器使用半隐式欧拉法（semi-implicit Euler）进行数值积分——先更新速度，再使用**更新后**的速度更新位置：

```
v_new = v_old + a(v_old) · Δt
p_new = p_old + v_new · Δt         ← 用 v_new 而非 v_old
```

为什么不用显式欧拉（`p_new = p + v_old·Δt`）？显式欧拉在二次阻力场中会系统性地低估位移——速度在 Δt 内已经衰减，但显式欧拉仍用旧速度计算位移。半隐式欧拉用新速度计算位移，自动对速度衰减做了修正，同时保持计算简单——每步仅需一次速度平方运算和一次密度查询。

为什么不直接用更高阶的方法（RK4、Verlet、Velocity Verlet）？MC 的物理是每 tick 离散更新的，解算器只需预测弹丸在每个 tick 结束时的大致位置。Δt=0.05s 的步长和弹丸典型的 100~3000 m/s 速度意味着每步位移 5~150m——在这个尺度上半隐式欧拉与 RK4 的误差差异远小于 MC AABB 碰撞检测的固有误差。

### 密度函数的作用

密度通过 `DensityFunction.getDensity(pos)` 每步查询——密度是位置的函数。为什么不把密度写死在 `BallisticConfig` 中？

如果假设全高度密度恒定，对于几十米内的平射误差忽略不计。但对于几百米的高抛弹道——弹丸飞过 Y 从 62 到 400 再落下——顶点空气密度约等于地表密度的 e<sup>-(400-62)/8500</sup> ≈ 96%——差异不大。但如果弹丸的飞行高度跨越了更大范围（如从 Y=320 的浮空岛射向 Y=64 的地面），密度变化的影响就会显现。

标准大气模型 ρ(y) = 1.225·exp(-(y-seaLevel)/8500) 与实际大气物理规律一致。标高 8500m 意味着密度每上升 8500m 衰减为 1/e ≈ 37%——在 MC 300 格的高度范围内差异只有约 3%，但如果未来出现数千格高的维度或太空场景，密度函数的设计允许用户无需修改解算器即可适配。

## 退化路径：O(1) 优化的原理

解算器在方法入口检查参数，当物理模型退化为可解析求解的简单情况时跳过分步积分。这不是"快速近似"——退化路径的数学精确度等同于积分结果。

### 匀速直线运动（g=0, 无阻力）

弹丸按惯性匀速前进，位移与时间正比。正解直接输出 `p(t) = p₀ + v·t` 的离散采样点。反解直接返回归一化的方向向量 `normalize(target - start)`。

MC 模型判定条件：`gravity == 0 && dragH == 1.0f && dragV == 1.0f`。拟真模型判定：`gravity == 0 && (Cd == 0 || A == 0)`。

### 纯抛物线（g≠0, 无阻力）

有重力无阻力是弹道学的经典解析问题。正解仍走分步积分以保证采样点粒度一致，但速度更新只需加法（无乘法）。反解使用**抛物线仰角解析公式**：

令 `d` = 水平距离，`h` = 高度差，`s` = 初速标量，`g` = 重力加速度绝对值：

```
Δ = s⁴ - g²d² - 2ghs²
```

当 Δ < 0：初速不足，无解。
当 Δ ≥ 0：

```
θ₁ = atan( (s² + √Δ) / (g·d) )    ← 高抛解
θ₂ = atan( (s² - √Δ) / (g·d) )    ← 平射解
```

这是直接通过解抛物线运动方程得到的解析解，不涉及任何迭代搜索。公式对仰角从 0° 到 90° 的所有情况均有效。Δ ≈ 0 时两解收敛为一——这是"刚好能命中"的临界初速状态。

### 直线减速（g=0, 有阻力）

零重力下阻力的方向始终与速度平行（因为只有速度方向一个作用力方向），弹丸沿直线前进。MC 模型下每 tick `v *= drag`，位移是等比数列之和。拟真模型下沿速度方向的标量一维减速方程。此路径比通用积分更快，因为重力项始终为零、方向不需重新计算。

## 反解核心：仰角二分搜索

反解（即"给定初速标量 s，找到命中目标的出射方向"）在退化路径下走解析解或简化搜索。通用情况下走仰角二分搜索。

### 搜索空间划分

解算器将仰角搜索分为两个区间：

| 区间 | 仰角范围 | 对应弹道 |
|------|:---:|------|
| 低区 | (0, 45°] | 平射弹道——弹丸走低弧线，飞行时间短 |
| 高区 | (45°, 90°) | 高抛弹道——弹丸走高抛物线，飞行时间长 |

两个区间分别独立二分搜索，各自返回一个解。当初速不足时某个区间可能无解（二分后的最优解距离目标仍然很远）；临界初速时两个区间都收敛到 45° 附近——此时去重逻辑将两解合并。

### 二分搜索的收敛准则

每迭代一轮：取当前区间的仰角中点、做一次正解、检测弹丸轨迹中离目标最近的点有多远。

核心判定"该扩大还是缩小仰角"的规则是**水平方向超射检测**：沿发射点指向目标的水平方向投影，检测弹道的水平进度是否超过目标。如果超过→仰角过高（打在目标更远处）→缩小搜索区间的上限；如果不足→仰角过低（打在目标更近处）→扩大搜索区间的下限。

```
若 max{ p_i · dir₂D } > target · dir₂D:
    thetaHigh = theta    // 打远了，缩小仰角
否则:
    thetaLow = theta     // 打近了，增大仰角
```

其中 `dir₂D` 是发射点指向目标的水平方向单位向量。

`angleEpsilon`（收敛阈值，默认 0.01 rad ≈ 0.57°）控制精度：当搜索区间宽度小于此值时退出。更小的阈值产生更精确的仰角，但每缩小一半需要增加一次二分迭代。

### 发射者速度的向量合成

解算器在每次正解前将发射者速度合并到初速：

```java
Vec3 worldVelocity = direction.scale(speed).add(shooterVelocity);
```

这在数学上等价于相对速度变换。发射者速度将弹丸的出口速度从"相对于发射者"转换为"相对于世界"，使得移动平台上的弹道预测与游戏实际行为一致。

## 动目标提前量：迭代收敛分析

### 迭代递归关系

提前量算法（第 5.4 节）的核心是一个递归关系：

```
P₀ = targetPos + V_target × roughTime      ← 粗略外推起点
P_{n+1} = targetPos + V_target × t_flight(P_n)
```

其中 `t_flight(P)` 是对瞄准点 P 做反解后得到的飞行时间。当 P 收敛时，弹丸将恰好命中目标在 t_flight 时到达的位置。

这个递归关系的**收缩因子**大约是 `|V_target| / |V_projectile|`（目标速度与弹丸速度之比）。当弹丸速度远大于目标速度时，t_flight 对 P 的微小变化不敏感——因为弹丸飞得快，P 的移动不会显著改变飞行时间。收缩因子小 → 快速收敛。

### 粗略外推的意义

第一轮直接用 `distance/speed` 估算飞行时间（忽略重力、阻力）并做位置外推。这不是精确计算——直线距离小于弹道弧长，实际飞行时间通常比这个估计长 5%~20%。但这个外推已经让 predictedPos 比当前位置更靠近真实命中点。第一轮正式反解从外推位置开始，后续仅需 1~2 轮微调。

### 为什么迭代可能发散

当 `|V_target| / |V_projectile|` 接近或超过 1 时（目标比弹丸快，或弹丸极慢），t_flight 对 P 高度敏感。P 的微小变化会显著改变飞行时间，从而大幅移动下一次外推位置——可能形成"来回摆动"的振荡。

解算器的三层保护在前文已描述。实际武器模组中弹丸速度几乎总是远大于目标速度（100~3000 m/s vs 5~10 m/s），收缩因子在 0.003~0.1 之间。这意味着每次迭代后预测误差缩减为上一次的 0.3%~10%，3~4 次迭代即可达到亚像素精度。

### 最大迭代次数与精度的关系

maxIterations 与收敛精度的关系取决于收缩因子 r：

| r | 典型场景 | 3 次迭代后预测误差 |
|:---:|------|:---:|
| 0.1 | 低速弹丸（100 m/s）vs 快速目标（10 m/s） | 初始误差的 0.1% |
| 0.01 | 中速弹丸（1000 m/s）vs 步行目标（5 m/s） | 初始误差的 0.0001% |
| 0.001 | 高速弹丸（3000 m/s）vs 步行目标（5 m/s） | 已低于浮点精度 |

实操中 maxIterations=4 对绝大多数场景完全足够。将 maxIterations 设为 8 是给极端场景留安全余量——初速临界、目标高速、大角度预测位置剧烈变化的组合才会用完。

## 两类解算器的计算量对比

| 组件 | MC 模型 | 拟真模型 |
|------|------|------|
| 每步计算 | 3 次浮点乘法 + 1 次加法 | 1 次 sqrt + 1 次密度查询 + 多次乘法 |
| 主要开销 | 创建新 Vec3 对象（阻力步） | 密度函数调用 + sqrt |
| 典型耗时（40 步） | ~5 μs | ~15 μs |
| 退化路径（匀速直线） | 无迭代，直接构造采样点 | 同 |
| 退化路径（抛物线反解） | 用解析公式，O(1) | 同 |

拟真模型每步额外开销来自 `DensityFunction.getDensity(pos)` 调用——这取决于密度函数的复杂度。对于 `DensityFunction.SEA_LEVEL`（返回常量），JIT 会内联消除调用开销。对于自定义 lambda，每步有一次 lambda 调用成本——在 40 步的积分中仅约 40 次间接调用，完全可以接受。

二分搜索的反解中同一正解会被反复调用。MC 模型下 30 次反解迭代 = 30×40 = 1200 步正解 ≈ 150 μs；拟真模型下 ≈ 450 μs。这些数值表明：AI 瞄准（每目标 5 Hz）和炮塔控制（每 tick 数个目标）完全在实时性能预算内；但若每 tick 为数百个实体同时做反解，建议分帧处理。正解本身耗时可忽略，适合每帧调用做弹道预览。
