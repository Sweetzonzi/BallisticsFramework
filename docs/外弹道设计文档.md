# 外弹道解算模块（External Ballistics）技术设计文档

## 一、模块定位与设计目标

外弹道解算模块是 BallisticsFramework 的新增子模块，位于 `api/trajectory/` 包下。它提供弹道前向解算（正解）、出射方向搜索（反解）和动目标提前量预测三大能力，将框架的覆盖范围从"命中后怎么办"（终点弹道）向前延伸至"如何命中"（外弹道）。

设计目标：

1. **零外部依赖**：所有计算基于 `net.minecraft.world.phys.Vec3` 完成，不引入任何第三方数学/物理库。
2. **双物理模型**：Minecraft 原版物理解算（每 tick 速度乘数阻力）与二次空气阻力拟真解算（Cd·ρ·A·v²/m）各自独立，用户按需选用。两者使用相同的输出数据结构，下游代码零切换成本。
3. **纯函数，全线程安全**：所有解算器方法均为 `static`、无内部状态。服务器端 AI 瞄准、客户端弹道预览、物理线程异步计算均可安全调用。
4. **从 BFDamageExtensions 消费数据**：`CALIBER` 和 `MASS` 预定义 key 直接作为拟真模型的输入参数，形成"终点弹道扩展 → 外弹道参数 → 弹道解算 → 命中上下文"的完整数据流闭环。
5. **解耦碰撞判断**：前向解算是纯物理模拟——初条件进，轨迹出。"是否命中目标"不是解算器的职责，由用户根据 `TrajectoryResult` 自行判断。

### 单位约定

所有输出数据结构（`TrajectorySample`、`TrajectoryResult`、`FiringSolution`）**统一采用国际单位制（SI）**：

| 物理量 | 单位 | 说明 |
|--------|:--:|------|
| 位置 | m | 等同 MC 世界坐标，1 格 = 1 m |
| 速度 | **m/s** | 所有输出速度矢量均为此单位，包括末速、采样点速度 |
| 时间 | s | 1 tick = 0.05 s |
| 质量 | kg | |
| 加速度 | m/s² | |
| 密度 | kg/m³ | |

`MinecraftTrajectory` 的入参（初速、重力、目标速度）为方便起见接受 **m/tick**——与 MC 原版 `Entity.getDeltaMovement()` 返回的单位一致。解算器内部以 m/tick 计算，**输出时自动换算为 m/s（×20）**，确保与 `RealisticTrajectory` 输出无缝互操作。

`BFDamageContext.hitVelocity` 记录以 **m/s** 为单位，与外弹道输出一致，无需换算。

## 一（补充） 意义与必要性分析

### 为什么需要外弹道模块

BallisticsFramework 当前只覆盖**终点弹道**——从命中瞬间开始的穿甲判定与伤害协商。这回答了"命中后怎么办"，但没有回答"如何命中"。

武器模组的开发者面临一个高频问题：已知目标位置和初速，子弹该往哪个方向打？这不仅仅是"枪口指向目标"——在有重力、有空气阻力的弹道下，枪口必须向上抬高，抬高多少取决于距离、初速和弹道参数。这是一个典型的**两点边值问题**（已知起止位置，求初速方向），没有显式解析解，需要数值方法求解。

写出一个正确的弹道解算器不是简单的事。需要考虑：

| 陷阱 | 说明 |
|------|------|
| 时间步长 | 太大失准、太小浪费。MC 解算需要对齐 tick 驱动更新顺序 |
| 数值方法 | 显式欧拉发散快，半隐式欧拉才稳定 |
| 高抛/平射双根 | 二分搜索需要正确的搜索区间，临界初速时双根收敛需去重 |
| 动目标收敛 | 目标速度与弹丸速度相近时迭代可能振荡发散 |
| 模型匹配 | 解算模型与模拟物理不一致时预测偏移 |

大多数小型武器模组的作者不具备处理这些问题的经验。结果是：每个武器模组各自实现弹道解算，实现质量参差不齐，不同模组的弹道行为不可比，AI 和炮塔脚本无法统一预测任何武器的弹道。

### 完成弹道学闭环

```
外弹道（本模块）                    终点弹道（现有）
┌──────────────────┐         ┌──────────────────┐
│ 弹道正解          │ ──────→ │ 穿甲判定           │
│ 瞄准反解          │   ctx   │ 伤害计算           │
│ 动目标提前量       │         │ 回调触发           │
└──────────────────┘         └──────────────────┘
    子弹飞行中                    命中瞬间
```

项目名为 "BallisticsFramework"，但当前只有终点弹道。加入外弹道后，框架才真正覆盖了弹道学的完整范畴，名称与功能才名副其实。

### 降低武器模组开发门槛

有了标准解算器后，武器模组的弹道逻辑从"自行实现数值方法"简化为"调一个方法"：

```java
// 之前：每个武器模组自己写 ~200 行解算代码
// 之后：一行调用
var solutions = MinecraftTrajectory.arrowFiringAngle(
    pos, target, speed, shooterVel, maxTicks);
```

对于最常用的 MC 原版弹射物（箭、火球、雪球），直接使用预设便捷方法即可，零参数配置。

### 标准化弹道行为，提升模组间一致性

当前状态：A 枪模组用欧拉法 + 线性阻力，B 枪模组用 Verlet + 二次阻力，C 枪模组干脆忽略阻力——三把枪的弹道行为完全不同，玩家感受到的是碎片化的射击体验。

有了标准解算器后：
- 所有武器共享相同的物理模型（或显式选择模型）
- 不同模组的不同武器可以**比较弹道性能**
- AI/炮塔脚本可以**统一预测任何武器的弹道**

这种标准化与 BallisticsFramework 的设计理念一脉相承：用协议消解碎片化。

### 解锁高级功能

| 功能 | 依赖的解算能力 |
|------|--------------|
| AI 炮塔自动瞄准 | 瞄准反解 + 动目标提前量 |
| 弹道指示器/瞄具辅助 HUD | 弹道正解 → 轨迹点坐标列表 |
| 弹道轨迹可视化 | 弹道正解 + 轨迹采样点 |
| 炮兵射击诸元计算 | 高抛弹道二分搜索 |
| 防空武器提前量计算 | 动目标迭代收敛预测 |
| 弹道计算机物品（游戏中） | 完整瞄准反解 |
| Physical Thread 异步验证 | 正解纯函数，线程安全 |

这些功能是终端用户愿意为此类 lib 装上的理由——不仅仅是"让模组作者写代码更方便"，更是"让玩家玩到更好的内容"。

### 必要性判断

| 维度 | 结论 |
|------|------|
| **核心使命必需？** | 否。终点弹道协议已完整可用，外弹道是增强而非替换 |
| **增强库的独特价值？** | 是。当前 MC modding 生态中外弹道各自实现，无统一标准 |
| **是否应独立为单独模组？** | 否。`TrajectoryResult` → `BFDamageContext` 的数据流自然衔接，分开反而增加适配层 |
| **工作量 vs 收益？** | 高收益。7 个文件，纯数学代码，无 Mixin、无事件、无状态，实现成本低 |

一句话总结：**从"终点弹道协议"升级为"完整弹道学框架"——外弹道和终点弹道的组合是项目定位的自然延伸。**

## 二、软件包架构

### 2.1 包路径

```
io.github.sweetzonzi.ballistics_framework/
├── api/
│   ├── (现有 12 个终弹类，零变更)
│   ├── trajectory/                              ← 新增子包
│   │   ├── TrajectorySample.java                ← 采样点 record
│   │   ├── TrajectoryResult.java                ← 正解结果 record
│   │   ├── FiringSolution.java                  ← 反解结果 record
│   │   ├── DensityFunction.java                 ← 空气密度函数式接口
│   │   ├── BallisticConfig.java                 ← 拟真参数 record
│   │   ├── MinecraftTrajectory.java             ← MC 原版物理解算器
│   │   └── RealisticTrajectory.java             ← 二次阻力拟真解算器
│   └── chamber/                                 ← 内弹道（未来预留）
├── internal/
├── mixin/
└── example/
```

### 2.2 设计原则

- **api/ 下的新子包**：`trajectory/` 作为 `api/` 的第二级包存在，不破坏现有一切导入路径。终弹 12 个类完全不碰。
- **api/ 作为统一入口**：用户 import `api.*` + `api.trajectory.*`。终弹是核心 → 平铺，外弹道是辅助工具 → 子包。主从关系通过包结构表达。
- **trajectory/ 内平铺，不做 api/internal 分层**：外弹道全部是纯函数，无私有实现需要隐藏。不做空壳分层。
- **类型职责分离**：数据 records（`TrajectorySample`、`TrajectoryResult`、`FiringSolution`、`BallisticConfig`）与计算逻辑（`MinecraftTrajectory`、`RealisticTrajectory`）分离。接口（`DensityFunction`）独立成文件。

### 2.3 文件职责一览

| 文件 | 类型 | 体积 | 职责 |
|------|------|:--:|------|
| `TrajectorySample` | record | 小 | 单个采样点：发射后时间、位置、速度 |
| `TrajectoryResult` | record | 小 | 正解结果：采样点列表 + 便捷查询方法 |
| `FiringSolution` | record | 小 | 反解结果：出射方向、飞行时间、末速度、弹道类型 |
| `BallisticConfig` | record | 中 | 拟真参数组 + 从 BFDamageExtensions 读取的工厂方法 |
| `DensityFunction` | 函数式接口 | 中 | 空气密度按位置查询 + 常用工厂/常量 |
| `MinecraftTrajectory` | 静态方法类 | 大 | MC 原版物理解算（正解、反解、提前量） + 实体预设常量 |
| `RealisticTrajectory` | 静态方法类 | 大 | 二次阻力拟真解算（正解、反解、提前量） |

### 2.4 文件依赖关系

```
         TrajectorySample ◄─── TrajectoryResult ◄───┬── MinecraftTrajectory
                           │                        └── RealisticTrajectory
                           │                                  │
                    FiringSolution ◄──────────────────────────┤
                                                      BallisticConfig
                                                      DensityFunction
```

箭头方向 = 被引用方向。数据 records 在左侧，被右侧的解算器消费。`TrajectorySample` 同时被 `TrajectoryResult` 和解算器内部使用。

## 三、核心数据结构

### 3.1 TrajectorySample —— 采样点

```java
/**
 * 弹道单个采样点——某一时刻的完整运动状态。
 * <p>
 * 采样点按时间升序排列，相邻两点的 time 差即积分步长。
 * 第一个采样点 time=0（发射时刻），最后一个 time=总飞行时间。
 *
 * @param time     自发射起经过的时间（s），MC 模型下 1 tick = 0.05s
 * @param position 世界坐标（m）
 * @param velocity 瞬时速度矢量（m/s，统一输出单位）
 */
public record TrajectorySample(
    float time,
    Vec3 position,
    Vec3 velocity
) {}
```

**为什么要同时存速度和位置**：弹道可视化需要轨迹点坐标，但计算命中穿深时需要末速。将两者放在同一条记录中，用户不必重新计算速度衰减。

### 3.2 TrajectoryResult —— 正解结果

```java
/**
 * 弹道正解计算结果。
 * <p>
 * 包含从发射时刻到模拟终止的全部采样点，按时间升序排列。
 * 不包含"是否命中目标"的判断——正解是纯物理模拟，命中判定由用户自行完成。
 * <p>
 * 若模拟在到达 maxSteps 前因落地（y ≤ 0）停止，
 * 最后一个采样点即为落地状态。
 *
 * @param samples 轨迹采样点列表（至少包含发射点一项）
 */
public record TrajectoryResult(
    List<TrajectorySample> samples
) {
    /** 发射时刻采样点 */
    public TrajectorySample first() { return samples.get(0); }

    /** 终止时刻采样点（落地/超时） */
    public TrajectorySample last()  { return samples.get(samples.size() - 1); }

    /** 总飞行时间（s） */
    public float totalTime()        { return last().time(); }

    /** 终点位置——可用于构造 BFDamageContext.hitPoint */
    public Vec3 terminalPoint()     { return last().position(); }

    /** 末速度——用于计算残余穿深 */
    public Vec3 terminalVelocity()  { return last().velocity(); }

    /** 命中面法线近似（末速度反方向归一化） */
    public Vec3 approximateHitNormal() {
        return last().velocity().normalize().scale(-1);
    }
}
```

**为什么没有地平面高度参数**：MC 中地平面高度因维度、地形而异。发射者在山顶打山谷中的目标，轨迹穿过 y=62 是正常的。将"落地"判定留给用户，比内置一个固定基准面更合理。

### 3.3 FiringSolution —— 反解结果

```java
/**
 * 瞄准解算结果——通过初速反解获得的出射方向与弹道信息。
 * <p>
 * 当初速充足时，solveFiringAngle 返回两个解（先平射后高抛）。
 * 临界初速时两解收敛为一点，仅返回平射解。初速不足时返回空列表。
 *
 * @param direction        出射方向（单位向量，世界坐标），含方位角和仰角
 * @param flightTime       预计飞行时间（s）
 * @param terminalVelocity 命中目标时的弹丸末速度（m/s）
 * @param isHighArc        高抛弹道（true）还是平射弹道（false）
 * @param iterations       二分搜索收敛迭代次数
 */
public record FiringSolution(
    Vec3 direction,
    float flightTime,
    Vec3 terminalVelocity,
    boolean isHighArc,
    int iterations
) {}
```

**为什么不用枚举而用布尔**：弹道类型只有两种——平射和高抛。两个值的枚举退化为布尔即可。

**为什么反解有 terminalVelocity 而正解的 TrajectoryResult 不做命中判定**：反解的目标是"打到某个点"，因此命中状态的计算内嵌在搜索过程中——二分收敛成功后末速自然可知，无需额外计算。正解没有目标概念，是通用的物理模拟。

### 3.4 BallisticConfig —— 拟真参数

```java
/**
 * 二次阻力模型下的弹丸固有参数。
 * <p>
 * 注意：空气密度不由此配置控制——弹道解算时通过 {@link DensityFunction}
 * 逐位置获取，以适应不同维度/高度的气压变化。
 * <p>
 * 所有值均使用国际单位制（SI）：质量 kg，长度 m，速度 m/s，加速度 m/s²。
 * <p>
 * 便捷工厂方法可从 {@code BFDamageExtensions} 预定义 key 构造，
 * 使武器模组只需额外提供 Cd 即可使用拟真解算器。
 *
 * @param dragCoefficient  阻力系数 Cd（无量纲），典型弹丸 0.2~0.5
 * @param mass             弹丸质量 m（kg），可从 BFDamageExtensions.MASS 读取
 * @param crossSectionArea 弹丸横截面积 A（m²），可从 BFDamageExtensions.CALIBER 计算
 * @param gravity          重力加速度 g（m/s²），MC 主世界 ≈ 0.04×20 = 0.8
 * @param timeStep         时间步长 Δt（s），默认 0.05（= 1 MC tick）
 * @param maxSteps         最大模拟步数
 */
public record BallisticConfig(
    float dragCoefficient,
    float mass,
    float crossSectionArea,
    float gravity,
    float timeStep,
    int maxSteps
) {
    /**
     * 从 BFDamageExtensions 预定义 key 读取 MASS 和 CALIBER，自动计算截面积。
     * 其余参数需手动指定。
     *
     * @param exts            命中上下文扩展容器
     * @param dragCoefficient 阻力系数 Cd
     * @param gravity         重力加速度（m/s²）
     * @param timeStep        时间步长（s）
     * @param maxSteps        最大步数
     */
    public static BallisticConfig fromExtensions(
        BFDamageExtensions exts, float dragCoefficient,
        float gravity, float timeStep, int maxSteps
    ) {
        float mass = exts.get(BFDamageExtensions.MASS);
        float caliber = exts.get(BFDamageExtensions.CALIBER);
        float area = (float)(Math.PI * (caliber / 2) * (caliber / 2));
        return new BallisticConfig(dragCoefficient, mass, area, gravity, timeStep, maxSteps);
    }

    /** 便捷构造：仅需 Cd + 口径 + 质量 + 重力（其余使用推荐默认值） */
    public static BallisticConfig simple(
        float dragCoefficient, float caliber, float mass, float gravity
    ) {
        float area = (float)(Math.PI * (caliber / 2) * (caliber / 2));
        return new BallisticConfig(dragCoefficient, mass, area, gravity, 0.05f, 200);
    }
}
```

**为什么只有拟真有配置类而 MC 原版没有**：MC 原版物理参数只有 3 个独立标量（dragH、dragV、gravity），且项目已按实体类型预设 6 组常量。这些参数直接作为方法参数传递比再套一个 record 更直观。拟真模型的 6 个参数数量多、互相耦合，封装为 record 是合适的。

## 四、物理模型

### 4.1 Minecraft 原版模型

MC 弹射物（箭、雪球、火球等）每 tick 物理更新使用以下通用形式：

```
加速度 → 阻力 → 位置

v.y += gravity          // 加速度（m/tick²）
v.x *= dragH            // 水平阻力（无量纲，每 tick 速度乘数）
v.y *= dragV            // 垂直阻力（无量纲）
v.z *= dragH
p += v                  // 欧拉积分
```

#### 计算顺序差异评估

Minecraft Wiki 指出不同实体在每 tick 中对加速度、阻力、位置这三步的**执行顺序可能不同**。原版实体大致分为三种：

| 计算顺序 | 代表实体 | 是否为弹射物 |
|---------|------|:---:|
| 加速度 → 阻力 → 位置（类型 A） | 箭、雪球、火球、药水等 | ✅**绝大多数** |
| 位置 → 加速度 → 阻力（类型 B） | 玩家、僵尸等生物 | ❌ 不是弹射物 |
| 位置 → 阻力 → 加速度（类型 C） | 羊驼唾沫 | ⚠️ 是弹射物，但极少用作武器 |

**数值差异分析**：以类型 A 与类型 C 对比——

```
类型 A: v += g;  v *= drag;  p += v_new    // 用衰减后的速度移动
类型 C: p += v_old;  v *= drag;  v += g    // 用未衰减的旧速度移动
```

单 tick 位置差 = `|v| × (1 - drag)`。以羊驼唾沫为例（drag=0.99），此项为速度的 1%。速度 6 m/tick 时单 tick 差约 0.06m，40 tick（2 秒）累积约 0.1~0.3m——**在 MC 尺度下完全可忽略**。

**结论**：武器模组用作弹丸的实体几乎全部是类型 A。解算器**固定使用类型 A 顺序（加速度→阻力→位置）**，不参数化计算顺序。理由：

- 类型 B 是生物，不适用于弹道解算场景
- 类型 C 仅羊驼唾沫一例，且极少被用作武器弹丸
- 即使在类型 C 场景下强行使用类型 A 解算，累积偏差也在 ~0.3m 以内，低于 MC 碰撞检测精度（AABB 膨胀本身就有 0.1m 以上的误差）
- 增加"计算顺序枚举"参数会使 API 复杂度成倍增加，而收益仅覆盖一个极其小众的场景

关键特征：
- 阻力是**速度乘数**，与质量、速度大小无关。drag = 0.99 意味着每 tick 减速 1%。
- 相同的 drag/gravity 组合在不同速度下的弹道几何完全相同。
- 步长固定为 1 tick（0.05s）。
- **入参单位**：初速、重力等均为 m/tick（与 MC 原版 `deltaMovement` 一致）。解算器内部用 m/tick 计算，**输出采样点时速度自动换算为 m/s（×20）**。

实体预设参数（来自 Minecraft Wiki）：

| 实体类型 | gravity | dragH | dragV | 终端速度 (m/tick) | 终端速度 (m/s) |
|---------|---------|-------|-------|:---:|:---:|
| 箭/三叉戟 | -0.05 | 0.99 | 0.99 | 5.00 | 100.0 |
| 雪球/鸡蛋/末影珍珠 | -0.03 | 0.99 | 0.99 | 2.97 | 59.4 |
| 喷溅药水 | -0.05 | 0.99 | 0.99 | 4.95 | 99.0 |
| 附魔之瓶 | -0.07 | 0.99 | 0.99 | 6.93 | 138.6 |
| 火球/凋灵之首 | +0.10 | 0.95 | 0.95 | 1.90 | 38.0 |
| 蓝色凋灵之首 | +0.10 | 0.73 | 0.73 | ~0.27 | ~5.4 |
| 羊驼唾沫 | -0.06 | 0.99 | 0.99 | 6.00 | 120.0 |

### 4.2 二次阻力拟真模型

基于牛顿力学 + 标准空气阻力方程，半隐式欧拉法积分：

```
每步 Δt:
  v_mag = |v|
  a_drag = -0.5 · ρ(pos) · Cd · A · v_mag · v / m    // 二次阻力项
  v_new = v + (g + a_drag) · Δt                       // 半隐式欧拉
  p_new = p + v_new · Δt
```

其中：
- `ρ(pos)` 通过 `DensityFunction` 逐位置获取，支持高度衰减
- `Cd`、`A`、`m` 来自 `BallisticConfig`
- `g` = (0, -gravity, 0)，来自 `BallisticConfig`

关键特征：
- 阻力与**速度平方**成正比（高速下阻力急剧增大）
- 阻力与**质量成反比**（越重的弹丸减速越慢）
- 阻力与**空气密度**成正比（高空空气稀薄，阻力减小）
- 与 MC 原版模型**不在同一个数学家族**，不可共用一个解算器核心

### 4.3 特殊边界优化——退化模型的短路路径

当重力为零或阻力可忽略时，弹道退化为简单模型。对以下三种特殊组合，解算器提供 **O(1) 解析解**作为快速路径，跳过逐步积分循环：

| 条件 | 退化模型 | 正解 | 反解 | 典型场景 |
|------|---------|------|------|------|
| g = 0, 无阻力 | **匀速直线运动** | p = p₀ + v·t | 出射方向直接指向目标（单解） | 激光/近光速武器、量子弹丸 |
| g ≠ 0, 无阻力 | **纯抛物线** | 解析式：p = p₀ + v·t + ½g·t² | 仰角解析解（不二分搜索） | 高尔夫球模组、慢速巨弹、下界 |
| g = 0, 有阻力 | **直线减速运动** | 阻力项沿速度方向，一次 1D 积分 | 沿目标方向二分搜索初速仰角（单解） | 太空/零重力环境、特殊维度 |

**判定逻辑**：方法入口首先检查参数是否为特殊组合，若是则走对应退化路径，否则走完整数值积分。用户无需手动识别——解算器自动选择最优路径。

#### 匀速直线运动（g=0, 无阻力）

最简单的退化场景。正解为一次向量加法，反解为一次向量归一化——速度向量直接指向目标。

```
正解: p(t) = p₀ + v·t,  v(t) = v₀
反解: direction = normalize(target - start)
      flightTime = distance / speed
      返回 [FiringSolution(direction, flightTime, v0, isHighArc=false)]
```

- 高抛弹道不存在（无重力则无抛物线顶点），始终返回单选
- 用户无需检查初速是否"足够"——只要 speed > 0 就能命中任意距离

#### 纯抛物线（g ≠ 0, 无阻力）

有重力无阻力是弹道学的经典解析问题。两条分支：

**正解**：每步 p += v; v.y += g——即使有解析式，仍按标准积分循环计算以保证采样点粒度与通用路径一致。但 v.y 的更新可从乘法简化为加法。

**反解**：仰角有解析解，无需二分搜索：

```
令 d = 水平距离, h = 高度差, s = 初速标量
判别式 Δ = s⁴ - g²d² - 2ghs²
若 Δ < 0: 初速不足 → 无解
若 Δ ≥ 0:
  θ₁ = atan( (s² + √Δ) / (gd) )   → 平射弹道
  θ₂ = atan( (s² - √Δ) / (gd) )   → 高抛弹道
若 Δ ≈ 0: 两解收敛 → 仅返回平射解
```

此解析解比二分搜索快约 100 倍（无迭代循环），且数学上精确。

#### 直线减速运动（g = 0, 有阻力）

零重力下有阻力的运动简化为沿速度方向的一维减速问题。在 MC 模型下每 tick 速度乘以 drag，弹丸沿直线前进。

```
正解: 每步 v *= drag; p += v（速度方向不变）
反解: 沿目标方向展开，仰角搜索仅为标量二分（不必每次重新计算方向）
```

- 仅返回平射解（无重力 → 无弧形弹道 → 无高抛）
- 对拟真模型，BFS（直线减速）比通用二次阻力积分更快（无需密度查询）

### 4.4 退化路径的自动选择

```java
// 解算器入口逻辑（伪代码）
if (gravity == 0 && isNoDrag(...)) {
    return solveLinearMotion(start, velocity, maxSteps);          // 匀速直线
}
if (gravity != 0 && isNoDrag(...)) {
    return solveParabolicMotion(start, velocity, gravity, maxSteps); // 纯抛物线
}
if (gravity == 0 && !isNoDrag(...)) {
    return solveStraightDeceleration(start, velocity, drag, maxSteps); // 直线减速
}
return solveFullIntegration(start, velocity, ...);                  // 完整积分
```

`isNoDrag()` 判定规则：

- **MC 模型**：`dragH == 1.0f && dragV == 1.0f`——速度乘数等于 1 即无阻力（每 tick 速度不变）
- **拟真模型**：`Cd == 0f || crossSectionArea == 0f`——阻力系数或截面积为零，或外部传入的 `DensityFunction` 恒返回 0（即 `VACUUM`）

判定在方法入口执行，开销为一次浮点比较，不会对性能产生可察觉影响。

**性能收益**（以 MC 模型 40 tick 飞行为例）：

| 路径 | 耗时 | 相比完整积分 |
|------|:---:|:---:|
| 完整积分（迭代 40 步） | ~5 μs | 基准 |
| 匀速直线（O(1)） | ~0.05 μs | **100×** |
| 纯抛物线（O(1) 解析反解） | ~0.1 μs | **50×** |
| 直线减速（迭代但简化） | ~2 μs | **2.5×** |

对激光武器（匀速）和高尔夫球（抛物线），这是"默认就对"的优化——用户零配置即可享受最优路径。

## 五、DensityFunction —— 空气密度函数式接口

### 5.1 设计动机

空气密度随海拔高度指数衰减。在 MC 中，同一个维度的 Y 坐标差异可达 300+ 格（== 300m），高抛弹道顶点的空气密度与地表差异显著。将密度写死在 `BallisticConfig` 中意味着假设全高度密度恒定——对几十米内的平射误差可忽略，但对几百米高抛弹道误差可观。

### 5.2 接口定义

```java
/**
 * 空气密度函数——根据世界坐标返回当前空气密度。
 * <p>
 * 函数式接口，lambda 友好。解算器每积分步调用一次以获取该位置密度。
 * <p>
 * 常见构造方式：
 * <pre>{@code
 * // 海平面常数
 * DensityFunction constant = DensityFunction.constant(1.225f);
 *
 * // 标准大气指数衰减（闭包捕获 Level 信息）
 * Level level = ...;
 * DensityFunction mcAtmo = pos ->
 *     DensityFunction.standardBarometric(pos.y, level.getSeaLevel(), 8500);
 * }</pre>
 */
@FunctionalInterface
public interface DensityFunction {

    /**
     * 根据世界坐标返回空气密度（kg/m³），标准海平面 ≈ 1.225。
     * 下界等无大气维度可返回 0。
     */
    float getDensity(Vec3 position);

    /** 恒定密度，不随位置变化 */
    static DensityFunction constant(float value) {
        return pos -> value;
    }

    /**
     * 标准大气指数衰减模型：ρ = ρ₀ · exp(-(y - seaLevel) / scaleHeight)。
     * <p>
     * ρ₀ = 1.225 kg/m³（海平面标准密度）。
     * scaleHeight 为标高（m）——密度每衰减为 1/e ≈ 37% 所需的高度差。
     * 地球标准大气的标高约 8500m。
     */
    static DensityFunction standardBarometric(float seaLevel, float scaleHeight) {
        return pos -> 1.225f * (float) Math.exp(-(pos.y - seaLevel) / scaleHeight);
    }

    /** MC 主世界参考模型（海平面 Y=62，标高 8500m） */
    DensityFunction MC_OVERWORLD = standardBarometric(62f, 8500f);

    /** 海平面常数 1.225（低弹道快捷方式） */
    DensityFunction SEA_LEVEL = constant(1.225f);

    /** 真空（无阻力，用于激光/近光速武器或测试） */
    DensityFunction VACUUM = constant(0f);
}
```

### 5.3 为什么不传 Level 参数

轨迹解算是纯数学操作——在弹道预览、AI 预判循环中，可能根本没有 `Level` 实例。`DensityFunction` 是 `Vec3 → float` 的纯净映射，与 `Level` 的耦合由用户在外部通过闭包完成：

```java
Level level = ...;
DensityFunction density;
if (level.dimension() == Level.NETHER) {
    density = DensityFunction.VACUUM;   // 下界无大气
} else {
    density = DensityFunction.standardBarometric(level.getSeaLevel(), 8500);
}
```

### 6.4 动目标提前量反解

```java
/**
 * 动目标瞄准点迭代收敛求解。
 * <p>
 * 算法：
 * <ol>
 *   <li>以目标当前位置反解弹道 → 获得飞行时间 t_flight</li>

 *   <li>以 P_predicted 为新目标位置，重复步骤 1</li>
 *   <li>当 |P_predicted 变化量| < convergeEpsilon 时收敛</li>
 * </ol>
 * <p>
 * 典型场景下 3~5 次迭代即可收敛。
 * 极端情况（目标速度接近弹丸速度）可能发散——设 maxIterations 保护。
 *

 * @param targetPosition   目标当前位置
 * @param targetVelocity   目标速度矢量（m/tick）
 * @param targetAcceleration 目标加速度矢量（m/tick²），可为 Vec3.ZERO
 * @param speed            初速标量（m/tick）
 * @param shooterVelocity  发射者速度（m/tick）
 * @param dragH / dragV / gravity  弹道参数
 * @param maxTicks         最大模拟 tick 数
 * @param maxIterations    最大迭代次数（推荐 5~8）
 * @param convergeEpsilon  收敛阈值（m），推荐 0.1
 * @return 最优瞄准解（即使未收敛也返回最优猜测）
 */
public static FiringSolution solveWithLead(
    Vec3 start,
    Vec3 targetPosition, Vec3 targetVelocity, Vec3 targetAcceleration,
    float speed, Vec3 shooterVelocity,
    float dragH, float dragV, float gravity,
    int maxTicks, int maxIterations, float convergeEpsilon
);
```

**发散保护策略**：
- `maxIterations` 硬限制（推荐 5~8）
- `convergeEpsilon` 收敛阈值（推荐 0.1m）
- 即使达到最大迭代次数仍未收敛，返回最后一轮的解作为最优猜测（而非报错/空值）
- 日志警告建议增大 maxIterations 或检查输入合理性

```java
// 1. 构造弹道参数（从扩展读取）
BFDamageExtensions baseExts = new BFDamageExtensions();
baseExts.set(BFDamageExtensions.CALIBER, 0.12f);   // 120mm 口径
baseExts.set(BFDamageExtensions.MASS, 8.5f);        // 8.5kg 弹丸

BallisticConfig config = BallisticConfig.fromExtensions(
    baseExts, 0.35f,   // Cd
    0.8f,              // g（MC 主世界等效值 m/s²）
    0.05f,             // Δt = 1 tick
    200                 // maxSteps
);

// 2. 反解出射方向
var solutions = RealisticTrajectory.solveFiringAngle(
    shooterPos, targetPos, 1500f,   // 初速 1500 m/s
    shooterVelocity,                  // 发射者自身速度
    config,
    DensityFunction.MC_OVERWORLD,
    0.01f                              // 仰角收敛阈值 ~0.57°
);

if (solutions.isEmpty()) return; // 初速不足，无法命中

FiringSolution sol = solutions.get(0); // 取平射解

// 3. 前端正解验证（可选）
TrajectoryResult traj = RealisticTrajectory.forwardSolve(
    shooterPos,
    sol.direction().scale(1500f).add(shooterVelocity),
    config,
    DensityFunction.MC_OVERWORLD
);

// 4. 计算残余穿深（用户自行实现，此处为示意）
float residualPen = calcResidualPenetration(initialPen, sol.flightTime());

// 5. 构造终点弹道上下文（hitVelocity 与外弹道输出同为 m/s，无需换算）
BFDamageContext hitCtx = BFDamageContext.builder()
    .source(damageSource)
    .baseDamage(500f)
    .hitPoint(traj.terminalPoint())
    .hitVelocity(traj.terminalVelocity())            // 同为 m/s，直传
    .hitNormal(traj.approximateHitNormal())
    .penetration(residualPen)
    .extensions(baseExts.copy())            // 拷贝基础扩展
    .build();

// 6. 发起协议伤害
float dealt = BFDamageApi.hurt(target, hitCtx);
```

## 九、性能分析

### 9.1 单次调用耗时估算

| 操作 | 耗时 | 计算量 |
|------|:---:|--------|
| MC 正解（40 tick，2 秒飞行） | ~5 μs | 40 × (3 次乘法 + 1 次加法 + 重力) |
| 拟真正解（40 步，2 秒飞行） | ~15 μs | 40 × (密度查询 + sqrt + 向量乘除) |
| 二分搜索反解（30 次迭代） | ~150 μs (MC) / ~450 μs (拟真) | 30 × 正解 |
| 动目标预测（3 轮收敛） | ~500 μs (MC) / ~1.5 ms (拟真) | 3 × 反解 |

### 9.2 适用场景

| 场景 | 推荐模型 | 频率 |
|------|---------|:---:|
| 弹道预览 HUD（每帧） | 正解，缓存结果 | 60 Hz |
| AI 瞄准（每个目标） | 反解 | ~1~5 Hz |
| 自动炮塔（多个目标） | 提前量反解 | ~2~10 Hz |
| 弹道轨迹渲染 | 正解 | 按需 |
| 物理线程同步验证 | 正解 | 异步 |
| 触发射击 | 动目标预测 | 按需 |

**大量并发场景建议**：当每 tick 需要为数百个实体同时解算时，考虑分帧（每 tick 处理 N 个目标）或缓存（目标速度未明显变化时复用上一帧结果）。

## 十、边界条件与误差说明

### 10.1 MC 离散物理与连续解算的差异

MC 物理在 20 ticks/s 下离散更新。弹丸速度 300 m/s 时，单 tick 位移达 15 米——长距离射击中解算结果与游戏实际行为可能产生微小偏差（< 1 个 tick 的误差）。这不是解算器的错误，而是离散物理的本质限制。

缓解措施：
- 解算器使用 Δt = 1 tick（0.05s），与游戏物理对齐
- 文档明确说明：解算结果是基于数学模型的近似，不是精确预测
- 未来可添加子步精度选项（如每 tick 再细分 4 步）供精度敏感场景使用

### 10.2 阻力模型不匹配

如果武器模组的物理引擎使用不同的阻力模型（线性、高阶、自定义曲线），解算结果会偏移。这是解算器与物理引擎模型不一致导致的，不是 bug。此时武器模组应自行实现解算。

### 10.3 动目标预测发散

场景：目标速度与弹丸速度接近（如弹丸 50 m/s，目标 30 m/s）。迭代可能振荡甚至发散。`maxIterations` 和 `convergeEpsilon` 提供保护。

### 10.4 明确不处理的范围

以下物理效应不在本模块范围内：
- 风偏（MC 无标准风系统）
- 科里奥利力（地球自转，对 MC 不必要）
- 马格努斯效应（旋转弹体的升力）
- 超音速/跨音速阻力突变
